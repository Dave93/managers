# tests/helpers — обвязка для тестов уровня HTTP

`http.ts` даёт `withSession()`, `callApi()` и `TEST_DB_URL` для тестов,
которые зовут реальный роут через `app.handle()`, а не читают код глазами.

- **Отдельная база.** `TEST_DB_URL` всегда указывает на
  `managers_tickets_test` (создана и смигрирована вручную, см.
  `task-1-report.md`); модуль бросает исключение при импорте, если это не
  так. Никакой тест не должен уметь достучаться до продовой `managers`.
  Пересоздать: `DROP DATABASE managers_tickets_test; CREATE DATABASE ...;
  DATABASE_URL=... bunx drizzle-kit migrate`.

- **Сессия кладётся в redis, а не через логин.** Макрос `permission`
  (`src/context/index.ts`) читает `user_data:<sessionId>` и кэш ролей
  (`cacheController.getPermissionsByRoleId`). `withSession()` пишет оба
  напрямую — поднимать настоящий логин ради проверки доступа значит
  тестировать логин, а не доступ.

- **Redis-неймспейс изолирован от прода.** `http.ts` подменяет
  `process.env.PROJECT_PREFIX` на `managers_test_` (и `DATABASE_URL` на
  тестовую базу) ДО первого импорта `src/app`. Это не только про ключи,
  которые пишет сам хелпер: импорт `src/app` тянет `context/index.ts`,
  который на module-scope конструирует `CacheControlService`; её
  конструктор без ожидания шлёт ~15 SET'ов в redis (`cacheRoles`,
  `cachePermissions`, `cacheTerminals`, ...), читая данные из базы, на
  которую в этот момент указывает `DATABASE_URL`. Без подмены префикса
  эти SET'ы залили бы продовые ключи (`managers__roles`,
  `managers_permissions`, ...) пустыми данными из тестовой базы при первом
  же `callApi()`. Из-за этого:
  - **Любой тестовый файл обязан импортировать `./helpers/http` первой
    строкой**, раньше любого прямого `import app from "../../src/app"`.
    Импорты в JS/TS поднимаются в порядке следования в файле — если
    где-то раньше стоит статический импорт `src/app`, подмена `env`
    опоздает.
  - `cleanup()` в `withSession()` — это гигиена (не даём мусорным ролям
    копиться в тестовом неймспейсе между запусками), а не защита прода:
    прод больше не задет никаким ключом благодаря изоляции префикса.
    Реальный `${PROJECT_PREFIX}_roles` (заметьте подчёркивание — не
    `${PROJECT_PREFIX}roles`) в продовом неймспейсе `managers_` этим
    хелпером не трогается вообще.

- **`callApi(path, init)`** лениво импортирует `src/app` (через
  `ensureApp()`) и после импорта повторно ждёт `cacheRoles()`, чтобы
  погасить гонку: неawait-нутый вызов из конструктора `CacheControlService`
  может дописаться в `${prefix}_roles` уже после того, как `withSession()`
  туда что-то положил.

- **Упавший тест не обязан гарантированно вызвать `cleanup()`.**
  `cleanup()` — это `filter(r => r.id !== roleId)` поверх текущего
  `${rolesKey}`, а не восстановление снапшота: он безопасен даже рядом с
  параллельной записью, но если тест упал ДО `await s.cleanup()`, фейковая
  роль останется висеть в `${rolesKey}` до следующего запуска. Две
  страховки от этого:
  1. Оборачивайте тело теста в `try { ... } finally { await s.cleanup(); }`.
  2. Вызывайте `sweepTestRoles()` в `afterAll` набора — она разом убирает
     все роли с `code === __http_test__`, даже если конкретный `roleId`
     потерян.
  Ключ сессии (`${prefix}user_data:<sessionId>`) сам себя подчищает: он
  пишется с `EX 300`, так что упавший тест максимум на 5 минут оставляет
  мёртвый sessionId — телом это не воспользуется никто, ключ просто истечёт.

- **`ensureApp()` сносит весь `managers_test_*` неймспейс перед импортом
  `src/app`** (один раз за процесс — `appPromise` закэширован), а не
  полагается на TTL/self-heal по частям. Это подчищает мусор от прошлого
  упавшего прогона (протухшую сессию, забытую фейковую роль, старые
  cache_control-ключи), а не только текущий.

- Если когда-нибудь `bun test` в этом модуле станет запускаться сразу на
  нескольких файлах — Bun гоняет их в одном процессе, поэтому подмена
  `process.env` в `http.ts` применится один раз, к тому файлу, который
  импортируется первым; `ensureApp()`'s cold start (~30с на пустой машине)
  тоже платится один раз на процесс, а не на файл. `test:http` сейчас
  запускает ровно один файл, так что это пока не актуально.
