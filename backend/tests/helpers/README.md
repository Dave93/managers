# tests/helpers — обвязка для тестов уровня HTTP

`http.ts` даёт `withSession()`, `callApi()` и `TEST_DB_URL` для тестов,
которые зовут реальный роут через `app.handle()`, а не читают код глазами.

## Как запускать

**Всегда через `bun run test:http`** (или скопировав его env-префикс себе).
Скрипт в `backend/package.json`:

```
"test:http": "PROJECT_PREFIX=managers_test_ DATABASE_URL=$TEST_DATABASE_URL bun test src/modules/tickets/routes.test.ts"
```

`PROJECT_PREFIX` и `DATABASE_URL` выставляются СНАРУЖИ процесса, до старта
`bun`. Раньше `http.ts` подменял их сам, в начале модуля — но это работало,
только если сам `http.ts` гарантированно первый импорт во всём тестовом
файле; статический `import app from "../../src/app"`, случайно оказавшийся
выше по файлу, тихо обходил подмену (import hoisting поднимает такие
импорты вне зависимости от порядка строк). Правило теперь не "следите за
порядком импортов", а "запускайте через скрипт": `http.ts` на старте
проверяет обе переменные и падает с понятной ошибкой, если что-то не так —
независимо от порядка импортов в тестовом файле. Если запускаете
`bun test <file>` напрямую (не через `test:http`), задайте оба env
вручную:

```
PROJECT_PREFIX=managers_test_ DATABASE_URL=postgresql://.../managers_tickets_test bun test <file>
```

## Зачем это всё

- **Отдельная база.** `DATABASE_URL` (провалидированный в `TEST_DB_URL`)
  всегда указывает на `managers_tickets_test` (создана и смигрирована
  вручную, см. `task-1-report.md`); модуль бросает исключение при импорте,
  если это не так. Никакой тест не должен уметь достучаться до продовой
  `managers`. Пересоздать: `DROP DATABASE managers_tickets_test; CREATE
  DATABASE ...; DATABASE_URL=... bunx drizzle-kit migrate`.

- **Сессия кладётся в redis, а не через логин.** Макрос `permission`
  (`src/context/index.ts`) читает `user_data:<sessionId>` и кэш ролей
  (`cacheController.getPermissionsByRoleId`). `withSession()` пишет оба
  напрямую — поднимать настоящий логин ради проверки доступа значит
  тестировать логин, а не доступ.

- **Redis-неймспейс изолирован от прода.** Реальный ключ кэша ролей —
  `PROJECT_PREFIX + "_roles"` (заметьте подчёркивание — не
  `PROJECT_PREFIX + "roles"`). В проде (`PROJECT_PREFIX=managers_`) это
  `managers__roles`. Импорт `src/app` тянет `context/index.ts`, который на
  module-scope конструирует `CacheControlService`; её конструктор без
  ожидания шлёт ~15 SET'ов в redis (`cacheRoles`, `cachePermissions`,
  `cacheTerminals`, ...), читая данные из базы, на которую в этот момент
  указывает `DATABASE_URL`. Без изолированного `PROJECT_PREFIX` эти SET'ы
  залили бы продовые ключи (`managers__roles`, `managers_permissions`, ...)
  пустыми данными из тестовой базы при первом же `callApi()`. Поэтому весь
  тестовый процесс живёт под `PROJECT_PREFIX=managers_test_`.

## Уборка за собой

Три уровня, от явного к аварийному:

1. **`withSession(...).cleanup()`** — read-modify-write, убирает свою сессию
   и свою роль из общих тестовых ключей. Не гарантированно вызывается, если
   тест упал до него — оборачивайте в
   `try { ... } finally { await s.cleanup(); }`.
2. **`sweepTestRoles()`** — разом убирает все роли с `code ===
   "__http_test__"` из `${prefix}_roles`, даже если конкретный `roleId`
   потерян. Вызывайте явно в `afterAll` набора, если хотите более раннюю
   гарантию, чем п.3.
3. **`afterAll()` внутри самого `http.ts`** — при импорте модуля
   регистрирует `bun:test`'овский `afterAll()` на верхнем уровне (не внутри
   `describe`), который зовёт `teardownTestNamespace()` — полный снос ВСЕГО
   неймспейса `managers_test_*` (не только ролей/сессий, но и
   cache_control-ключей вроде `managers_test_terminals`). Это безусловная
   страховка: она сработает, даже если тестовый файл вообще не позвал
   `cleanup()`/`sweepTestRoles()`/`closeTestRedis()`.

   **Важно про механизм:** `process.on("beforeExit")` / `process.on("exit")`
   здесь НЕ РАБОТАЮТ — проверено эмпирически (повесил `console.error` на оба
   хендлера, прогнал тест без единого явного cleanup: ни один не
   напечатался, хотя процесс завершился кодом 0, оставив мусорные ключи).
   Похоже, `bun test` завершает процесс жёстко сразу после прогона файла, не
   давая Node-стилю событий процесса произойти — вероятно, из-за открытых
   хендлов (наши redis-подключения и BullMQ Queue из `iiko_sync/controllers.ts`,
   который `http.ts` закрыть не может, см. ниже). Рабочий механизм — именно
   `bun:test`'овский `afterAll()`, вызванный на верхнем уровне модуля: он
   гарантированно отрабатывает после всех тестов файла, до печати итога
   прогона. Если когда-нибудь придётся переносить этот хелпер на другой test
   runner — этот пункт нужно перепроверить заново, а не копировать вслепую.

   `ensureApp()` дополнительно сносит весь неймспейс на СТАРТЕ (до импорта
   `src/app`) — на случай, если предыдущий прогон убили настолько резко, что
   даже `afterAll()` не успел сработать (SIGKILL, упавшая машина).

- `closeTestRedis()` явно зовёт `teardownTestNamespace()` и закрывает ОБЕ
  redis-подключения, которые тестовый процесс открывает: собственный клиент
  `http.ts` и общий `getRedisClient()` из `lib/shared-instances`, которым
  пользуются `context/index.ts` и `CacheControlService`. Вызывайте его в
  `afterAll`, если хотите, чтобы процесс завершился без задержки на
  таймауте открытого сокета — но даже если забудете, `teardownTestNamespace()`
  идемпотентна, так что модульный `afterAll()` не продублирует работу.

## Известные ограничения

- **Конкурентные `withSession()` в одном тесте небезопасны.** `cleanup()` и
  сам push роли в `withSession()` — это read-modify-write без блокировки
  поверх общего `${prefix}_roles`. Две параллельные `withSession()` (или
  `withSession()` и `cleanup()` от другого теста, летящие одновременно)
  могут потерять одну из записей (classic lost update). Пишите тесты,
  которые трогают `withSession`/`cleanup`, последовательно — не
  `Promise.all([withSession(...), withSession(...)])`.

- **Зависимость от `SESSION_EXPIRES_IN`.** Макрос `permission`
  (`src/context/index.ts`) при каждом запросе проверяет TTL ключа
  `user_data:<sessionId>`; если он меньше 600 секунд (а наша фейковая сессия
  пишется с `EX 300` — то есть ВСЕГДА меньше), макрос продлевает его через
  `redis.expire(key, parseInt(process.env.SESSION_EXPIRES_IN ?? "0"))`. Если
  `SESSION_EXPIRES_IN` отсутствует в окружении, это `EXPIRE key 0` — сессия
  удаляется СРЕДИ запроса, между `beforeHandle` (где уже прочитанные
  `role`/`permissions` использованы для проверки прав) и `resolve()` (который
  читает ключ заново для `user`/`role`/`terminals` в хендлере). Хендлер в
  этом случае получит `terminals: []`, что для большинства модулей означает
  "все филиалы" — то есть тест на скоуп по терминалам может тихо не
  сработать, вместо честного отказа. В `backend/.env` `SESSION_EXPIRES_IN`
  сейчас задан (`86400`), и `bun test` подхватывает `.env` автоматически, так
  что на практике это не стреляет — но если когда-нибудь тесты будут
  гоняться в окружении без `.env` (CI-контейнер с чистым env), это всплывёт
  молча, а не с понятной ошибкой. Стоит иметь в виду при отладке
  неожиданного "видит все филиалы" в тестах на скоуп.

- **`iiko_sync/controllers.ts` регистрирует BullMQ Queue на module-scope.**
  Импорт `src/app` (через `controllers.ts` → `iikoSyncController`)
  конструирует `const iikoDocumentSyncQueue = new Queue(...)` на верхнем
  уровне файла — это открывает ещё одно, отдельное от `getRedisClient()`,
  подключение к тому же redis (используя `REDIS_HOST`/`REDIS_PORT`
  напрямую, в обход `PROJECT_PREFIX`, так что изоляции namespace это не
  касается). `http.ts` не может закрыть это подключение — переменная
  модульная, не экспортирована. На практике это не создаёт данных (мы
  никогда не вызываем `.add()` на этой очереди), но означает, что после
  `closeTestRedis()` у процесса может остаться повисшее соединение; `bun
  test`, судя по всему, завершает процесс всё равно (см. выше про
  `afterAll`/`beforeExit`). Если после `test:http` процесс начнёт зависать
  на выходе — смотреть сюда в первую очередь.

- **`callApi(path, init)`** лениво импортирует `src/app` (через
  `ensureApp()`) и после импорта повторно ждёт `cacheRoles()`, чтобы
  погасить гонку: неawait-нутый вызов из конструктора `CacheControlService`
  может дописаться в `${prefix}_roles` уже после того, как `withSession()`
  туда что-то положил.

- Если когда-нибудь `bun test` в этом модуле станет запускаться сразу на
  нескольких файлах — Bun гоняет их в одном процессе, поэтому `ensureApp()`'s
  cold start (~30-35с на этой машине — импорт `src/app` поднимает весь
  Elysia-граф: десятки контроллеров, `puppeteer` и т.д.) платится один раз
  на процесс, а не на файл. `test:http` сейчас запускает ровно один файл.
