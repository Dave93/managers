# KPI — План 2: экраны админки

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Раздел «KPI сотрудников» в админке: экраны «Оценки», «Нарушения», «Споры», «Месяц», «Повышения», «Настройки KPI», группа в боковом меню и два пункта в «Ещё» мобильного `ManagerLayout`.

**Architecture:** Клиентские страницы под `admin/app/[locale]/kpi/`. Раздел закрыт гейтом `kpi/layout.tsx` по `kpi_layout`, каждый экран — `ScreenGate` по набору «любое из прав». Все запросы идут через написанный руками клиент `admin/lib/kpi-api.ts`: один `as any`, фабрика `createKpiApi(root)` ради контрактного теста, типы ответов из `@backend/modules/kpi/types`. Всё, что проверяется без DOM (баллы, комментарии, периоды и кварталы по Ташкенту, тексты ошибок, сборка multipart, решения по повышению), лежит в `admin/lib/kpi/*.ts` с `bun test` рядом.

**Tech Stack:** Next.js 15 (canary), React 19, TanStack Query 5, @tanstack/react-form 1, shadcn/ui + Tailwind, sonner, lucide-react 0.545, Eden treaty 1.4, bun:test.

**Spec:** `docs/superpowers/specs/2026-10-25-kpi-design.md` (раздел 10; поведение — разделы 7–9)

Предыдущий план: `docs/superpowers/plans/2026-10-25-kpi-1-backend-core.md`. Его блоки Interfaces задают роуты, тела запросов, коды ошибок и типы ответов. Админка потребляет их как есть и backend не меняет.

## Пробелы плана 1, которые задевают админку

Пункты 1, 2, 3 и 8 закрыты задачей 10 плана 1 (до начала этого плана): `KpiUserOption` есть в `types.ts`, `include_uncarded=1` работает для `kpi.manage`, `kpi.approve` читает формы, события, нарушения и фото, у `ReviewForm` есть `open_dispute`. Админка импортирует `KpiUserOption` из `@backend/modules/kpi/types` и берёт `open_dispute` из формы. Пункт 4 закрыт задачей 5 плана 1. Остальные пункты админка обходит так, как написано ниже.

1. `GET /kpi/users?search=` без типа ответа. Админка ждёт `{ id: string; name: string; login: string }[]` (`KpiUserOption` в `kpi-api.ts`). В `types.ts` нужен такой же `export interface`.
2. `GET /kpi/employees` отдаёт только сотрудников с картой. Тогда HR не найдёт техничку (у неё нет роли с картой по умолчанию) и не вернёт к «авто» того, кому поставили «не оценивается». Админка шлёт `include_uncarded=1` во вкладке «Сотрудники». Нужен флаг (только `kpi.manage`): все активные сотрудники в видимости, `card = null`, `card_source` как есть. Без него Elysia молча отбросит параметр, и вкладка покажет только сотрудников с картой.
3. У `kpi.approve` нет чтения. `GET /kpi/reviews/form`, `GET /kpi/reviews/:id/events` и `GET /kpi/violations` пускают только evaluate/view. HR с одним `kpi.approve` не откроет форму для разбора спора по оценке и для правки в закрытом месяце. Нужно добавить `kpi.approve` в наборы этих роутов или при деплое выдавать HR `kpi.view` вместе с `kpi.approve`.
4. `GET /kpi/cards?include_inactive=1` должен отдавать и неактивные пункты. Иначе отключённый пункт нельзя включить обратно.
5. `PeriodSummary.close_blockers: string[]` без перечня значений. Админка считает их кодами ошибок (`dispute_window_open`, `open_disputes`, `already_closed`) и показывает через `codeText`.
6. Минимальная длина не задана для причины отмены нарушения, комментария разбора спора, комментария открытия месяца заново и комментария решения по повышению. Админка требует хотя бы один непробельный символ. Для спора и изменения оценки минимум равен `change_comment_min`, для записи нарушения 3, как в плане 1.
7. `KpiSettings` и `ItemSource` объявлены в `rules.ts`, а не в `types.ts`. Админка импортирует их `import type` из `@backend/modules/kpi/rules`.
8. В `ReviewForm` нет `open_dispute`. Форма, открытая со списка, берёт флаг из `EmployeeRow.open_dispute`; иначе кнопка «Оспорить» не узнает, что спор уже открыт.
9. Тела ответов `POST/PUT` карт, пунктов, назначений и `PUT /employees/:id/card` не заданы. Админка их не читает, только сбрасывает кэш (тип `unknown`).

## Review Focus

1. Пустое поле балла. Оценщик стёр число: это «нет оценки» (`null`), а не 0. `Number("") === 0` превратил бы пустоту в ноль и испортил среднюю за квартал (анти-цель спеки). Тест `parseScoreInput` в задаче 3.
2. Eden превращает даты в `Date`. Reviver Eden делает из `"2026-10-01"` объект `Date`, и сравнение периодов, `periodLabel` и ключи запросов ломаются. Каждый ответ проходит `normalizeDates`; тест «даты остаются строками» в задаче 1.
3. Пустые необязательные фильтры. `terminal_id: undefined` или `search: ""` не должны попасть в URL как `undefined` или пустой параметр, иначе сервер ответит 422 или пустым списком. Тест «без пустых фильтров» в задаче 1.
4. Браузер не в Ташкенте. У HR ноутбук в UTC или по Москве: месяц, сроки и время нарушения всё равно показываются по Asia/Tashkent. Тесты `calendarPeriod` и `formatTashkent` в задаче 1.
5. Двойное нажатие и обрыв связи на телефоне. Повторный тап на «Зафиксировать» не создаёт второе нарушение (сервер их не склеивает). При неизвестном исходе (сеть, таймаут, 5xx) защёлка не снимается, экран предлагает проверить журнал. Тесты `createLatch` (задача 4) и `outcomeKnown` (задача 1).
