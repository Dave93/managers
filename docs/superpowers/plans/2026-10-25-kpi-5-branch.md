# KPI — План 5: балл филиала

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Балл филиала по пяти показателям (продажи к плану, перерасход сырья, сервис, санитария, дисциплина) с версиями расчёта, предложения автопунктов `sales_plan`, `food_cost`, `cooking_speed` в форме оценки и экраны «Сеть», «Филиал», «План выручки», «Санитарная проверка», «Балл филиала» в настройках.

**Architecture:** Факты читаются из `orders`, `product_cooking_time`, `inventory_reconciliations`, `kpi_sanitary_checks` и `kpi_attendance` пачкой по всем филиалам (`branch-facts.ts`). Чистые правила в `branch-rules.ts` превращают входы филиала в факты, баллы, балл и ступень; там же контрольный пример спеки. `POST /kpi/branch/compute` под advisory-блокировкой месяца пишет новую версию `kpi_branch_results` и `kpi_branch_scores`, чтение всегда берёт последнюю. Форма оценки берёт предложения автопунктов из последней версии через `loadSuggestions` плана 3. Админка: клиент `admin/lib/kpi-api.ts`, чистые помощники `admin/lib/kpi/{branch,revenue-plans,sanitary}.ts`, четыре экрана и вкладка настроек.

**Tech Stack:** Bun 1.4, Elysia 1.4, Drizzle ORM 0.44 / drizzle-kit 0.31, PostgreSQL, bun:test; админка Next.js 15, React 19, TanStack Query 5, shadcn/ui, sonner.

## Решения плана

Спека их не задаёт или оставляет плану фазы 5. Каждое помечается в `docs/superpowers/kpi-handoff.md` как «наше решение».

1. Выручка. `SUM(orders.dish_discount_sum_int)` за месяц по iiko-группам филиала. Это поле графиков выручки (`revenue_*_aggregation` в `backend/drizzle/timescale_scripts.sql`). Фильтров по статусу нет: синхронизация (`cron/src/modules/olap/getOrders.ts:120-135`) уже кладёт только `OrderDeleted = NOT_DELETED`, `DeletedWithWriteoff = NOT_DELETED`, не сторно, `DishDiscountSumInt > 0`, `DISH`/`MODIFIER`. Число совпадает с дашбордом.
2. Сервис. Доля заказов, приготовленных в норматив:
   - строки `product_cooking_time` с `0 < guest_wait_time_avg ≤ 14400` секунд (верхняя граница как у графика `cooking-time-distribution`), ноль означает «не замерено»;
   - ожидание заказа равно максимуму по его строкам (гость ждёт самое долгое блюдо, повторы строк от пересинхронизации гасятся сами);
   - тип заказа берётся из `orders.order_service_type` (связь `orders.id = uniq_order_id` и одинаковый `open_date_typed`): `DELIVERY_BY_COURIER` и `DELIVERY_PICKUP` идут по нормативу доставки, `COMMON`, пустой и прочие типы по нормативу зала;
   - заказ без строки в `orders` не считается;
   - в норматив, если `ожидание ≤ норматив × 60` (граница включительно).

   `cooking_finish_time` не используется: синхронизация пишет туда `Delivery.CookingFinishTime`, у заказов зала он, скорее всего, пуст. Нормативы: `service_norm_hall_min` 8 и `service_norm_delivery_min` 12.
3. Перерасход сырья. В сверке инвентаризации C означает учётный остаток iiko после списаний по техкартам, B означает факт инвентаризации iiko. Перерасход = `max(0, −Σ diff_bc_sum)` по принятым сверкам складов филиала за месяц. Сумма берётся из снимка `accepted_totals->>'diff_bc_sum'`, сделанного при «принято», а не из живой колонки. Сумма чистая: недостачи минус излишки. Факт = перерасход ÷ выручка × 100. Сверка ищется по `period` = последний день месяца. Если хоть одна сверка склада филиала за месяц не `accepted`, данных нет.
4. Округление. Факт округляется до 0,01. Баллы хранятся до 0,01, экран показывает до 0,1. Вклад показателя считается из баллов, округлённых до 0,1, половина вверх до 0,01, целыми числами (алгоритм в задаче 2). Балл филиала равен сумме вкладов. Так считает план HR (`kpi-filialov.source.html`: «91,7 балла × 20 % = 18,34», итог 95,79). В таблице спеки 7.7 стоит 18,33, и её столбец даёт в сумме 95,78. Это описка, тест закрепляет 95,79.
5. «Не хватает до ступени» = `max(0,1; round1(порог следующей ступени − балл))`, у ступени 120 % — нет. 95,79 → 9,2.
6. Версия. Одна на запуск расчёта за месяц (`max + 1`). Старые версии хранятся, чтение берёт последнюю без отката на прошлые. Пустой расчёт (ни у одного филиала нет данных) ничего не пишет.
7. Какие филиалы считаются. Набор строится из данных, а не из `terminals`: `credentials.model_id` (`iiko_id`, `iiko_store_id`), планы месяца, санитарные проверки месяца, посещаемость месяца. Филиал без единого показателя с данными в версию не попадает. Нуля вместо «нет данных» не бывает.
8. Цвет ячейки «Сети» по баллам показателя: от 100 зелёный (цель взята), больше 0 жёлтый, 0 красный (на пороге и ниже), без данных серый.
9. Показатели. Коды и направления фиксированы. HR меняет вес, порог, цель, максимум и «активен». Сумма весов активных ровно 100. Изменения действуют со следующего пересчёта, посчитанные версии хранят снимок порогов и весов.
10. Настройки балла. Три ключа в `kpi_settings` вне `KpiSettings` плана 1: `service_norm_hall_min` (8), `service_norm_delivery_min` (12), `sanitary_items`. `GET /kpi/settings` их не отдаёт, `PUT /kpi/settings` по-прежнему отвечает на них 422 `unknown_setting`.
11. Шаблон санитарной проверки. Пять пунктов из регламента HR: «Чистота», «Санитария», «Форма персонала», «Хранение продуктов», «Маркировка». Процент проверки: отмеченные «да» ÷ все пункты. Санитарная проверка в закрытом месяце KPI получает 409, как нарушение.
12. Кто проводит проверку: `kpi.manage` или `kpi.evaluate` с назначением, у которого филиал совпадает или пуст (карта любая). `GET/PUT /kpi/branch-indicators` остаются за `kpi.manage`, а проверяющий получает шаблон отдельным `GET /kpi/sanitary-checks/template` (`kpi.evaluate` или `kpi.manage`).
13. План выручки. Целые сум от 1 до 10¹², `null` удаляет план. Подсказка «от прошлого года»: выручка того же месяца год назад × (1 + рост/100), округление до 1 000 сум, рост от −50 до 200 %, в форме по умолчанию 10 %.
14. Предложение автопункта = `min(100, round(points))` из последней версии по филиалу сотрудника (спека 7.3): `sales_plan` ← `sales`, `food_cost` ← `food_cost`, `cooking_speed` ← `service`. Если показатель без данных или филиала нет в последней версии, предложения нет.

Правила, которые тесты не определяют однозначно:
- `indicatorPoints` — шкала раздела 7.7 спеки, затем `round2`. `lower_better` зеркально: `fact ≥ floor → 0`; `target ≤ fact < floor → 50 + (floor − fact)/(floor − target) × 50`; `max ≤ fact < target → 100 + (target − fact)/(target − max) × 20`; `fact < max → 120`. Деления на ноль нет: порядок порогов строгий (`validateIndicators`).
- `scoreTerminal`. Для активного показателя с `fact !== null`: `points = indicatorPoints(fact)`, иначе `no_data` с `points` и `weighted` `null`. Σw — сумма весов показателей с данными. Вклад и балл считаются целыми, без плавающей арифметики на половинах:
  ```ts
  // p10 — баллы до 0,1; n/d — вклад в сотых; половина вверх
  const p10 = Math.round(points * 10);
  const n = p10 * weight * 10, d = sumW;
  const hundredths = Math.floor((2 * n + d) / (2 * d));
  // weighted = hundredths / 100; score = Σ hundredths / 100
  ```
  Нет ни одного показателя с данными → `score` и `tier_pct` `null`.
- `tierFor`: `< 75 → 0`, `< 90 → 60`, `< 105 → 100`, иначе `120`. `nextTier`: ближайшая ступень выше, `points_needed = max(0.1, Math.round((min − score) × 10) / 10)`; при `score ≥ 105` — `null`.
- `disciplineMultiplier`: 0 → 1; 1–2 → 0,9; 3–4 → 0,75; 5 и больше → 0,5. `branchBonus = Math.round(base × tierPct / 100 × multiplier)`.
- `terminalFacts` — причины по порядку проверки:
  - `sales`: `!has_iiko` → `no_iiko_link`; `plan` пуст или ≤ 0 → `no_plan`; `revenue ≤ 0` → `no_orders`; иначе `pct2(revenue, plan)`, `details { revenue, plan }`;
  - `food_cost`: `!has_store` → `no_store`; `recons` пуст → `no_reconciliation`; есть не `accepted` → `not_accepted`; есть `diff_bc === null` → `no_iiko_document`; `!has_iiko` → `no_iiko_link`; `revenue ≤ 0` → `no_orders`; иначе `overspend = max(0, −Σ diff_bc)` (до 0,01), `pct2(overspend, revenue)`, `details { revenue, overspend }`;
  - `service`: `!has_iiko` → `no_iiko_link`; `orders = 0` → `no_cooking_rows`; иначе `pct2(on_time, orders)`, `details { orders, on_time, hall_min, delivery_min }`;
  - `sanitary`: `checks = 0` → `no_checks`; иначе `avg`, `details { checks }`;
  - `discipline`: `days = 0` → `no_attendance`; иначе `pct2(on_time, days)`, `details { days, on_time, late, absent }`.

  У `no_data` в `details` лежат те же ключи, что есть (например, выручка без плана).
- `validateIndicators` — первый найденный код:
  - не массив из пяти объектов, код не из `BRANCH_CODES` или повтор → `unknown_indicator`;
  - `weight` не целое 0..100, или 0 у активного → `bad_indicator_weight` с `{ code }`;

- `validateBranchSettingsPatch`: ключи только из `DEFAULT_BRANCH_SETTINGS`, иначе `unknown_setting`. Нормативы — целые 1..120, иначе `bad_value`. `sanitary_items` — массив строк 1..30, после `trim` длиной 1..200 и без повторов, иначе `bad_sanitary_items`.
- `branchSuggestion`: `score = Math.min(100, Math.round(points))`. Факт — до 0,01 с запятой и без хвостовых нулей, баллы — с одним знаком после запятой. Тексты в тесте.
- `planSuggestion`: `base` пуст или ≤ 0 → `null`; иначе `Math.round(base × (100 + g) / 100 / 1000) × 1000`.

```sql
  SELECT lower(p.restoraunt_group) AS grp, p.uniq_order_id, p.open_date_typed, MAX(p.guest_wait_time_avg) AS wait_sec
  FROM product_cooking_time p
  WHERE lower(p.restoraunt_group) IN (:groups)
    AND p.open_date_typed >= :from::timestamp AND p.open_date_typed < :to::timestamp
    AND p.guest_wait_time_avg > 0 AND p.guest_wait_time_avg <= 14400
  GROUP BY 1, 2, 3
)
SELECT w.grp, COUNT(*)::int AS orders,
  COUNT(*) FILTER (WHERE w.wait_sec <= CASE WHEN o.order_service_type IN ('DELIVERY_BY_COURIER', 'DELIVERY_PICKUP')
                                            THEN :delivery ELSE :hall END)::int AS on_time
FROM w
JOIN orders o ON o.id = w.uniq_order_id AND o.open_date_typed = w.open_date_typed
WHERE o.open_date_typed >= :from::timestamp AND o.open_date_typed < :to::timestamp
GROUP BY w.grp
```

Остальные источники:
- сверки: `SELECT lower(store_id::text) AS store, status, accepted_totals->>'diff_bc_sum' AS diff_bc FROM inventory_reconciliations WHERE store_id IN (:stores) AND period = :last_day`. `diff_bc` — `Number`, если статус `accepted` и строка не пустая, иначе `null`;

- посещаемость: по `terminal_id` за `day >= P AND day < P+1`: `days = count(*)`, `on_time` — `not absent and late_minutes = 0`, `late` — `not absent and late_minutes > 0`, `absent` — `absent`;
- планы: `amount` по `terminal_id` за `period = P`.

Правила `computeBranch`:
1. `period > periodOf(now())` → 422 `future_period`. Текущий месяц считать можно («предварительно»).
2. Транзакция, первым — `pg_advisory_xact_lock(hashtext('kpi_branch:' || :period))`.
3. Активных показателей нет → 409 `no_indicators`.
4. Набор филиалов — объединение ключей `terminalLinks()`, `plansByTerminal`, `sanitaryByTerminal`, `attendanceByTerminal` (решение 7). Все источники читаются пачкой, по запросу на источник.
5. Для каждого филиала `TerminalInputs`: `has_iiko`/`has_store` по связкам, `revenue = sumOver(iiko, выручка)`, `service` — суммы по его группам плюс нормативы, `recons` — сверки его складов, остальное — по `terminal_id` (нет строки → нули или `null`).
6. `terminalFacts` → `scoreTerminal(loadIndicators, …)`. `score === null` → филиал пропускается.
7. Нет ни одного филиала → ничего не пишется, ответ `{ period, version: null, terminals: 0, computed_at }`.
8. Иначе `version = coalesce(max(version) из kpi_branch_scores за period, 0) + 1`. Строки `kpi_branch_results` по каждому активному показателю: снимок веса, порогов и направления, `reason`, `details`. Строка `kpi_branch_scores`. `computed_at = now()`, `computed_by = actor.userId`.
