## Общее для всех фаз

### Проверки до деплоя

1. Миграции. В `origin/main` последняя миграция — `0034_inventory_turnover`, KPI начинается с `0036_kpi_core`. `0035_hanging_orders_sync` догоняет дрейф: в `schema.ts` были таблицы `hanging_orders` без миграции; она идемпотентная. Номера и содержимое нужно сверить с прод-`main` (прод опережает `origin/main`, там могла появиться своя миграция с тем же номером).
2. Метки времени в журнале. `drizzle-kit migrate` сравнивает только `created_at` последней записи в `drizzle.__drizzle_migrations`. Поэтому поле `when` у `0035`–`0038` в `backend/drizzle/migrations/meta/_journal.json` должно быть строго больше, чем у последней применённой на проде миграции, иначе новые файлы молча пропустятся. Проверка на проде: `select max(created_at) from drizzle.__drizzle_migrations;`. Число строк в таблице с числом записей в журнале не совпадает (на проде нет записей для idx 0–8), это нормально; смотреть нужно на максимум.
3. Табельные номера. Фаза 3 сопоставляет сотрудников с файлом Workly по `employees.external_id`. До сих пор поле заполняла только форма аттестации. Выполнить `select count(*) from employees where external_id is not null;` и, если не ноль, сначала понять, что там лежит.
4. Redis. На проде Redis общий для всех сервисов и работает с `maxmemory-policy volatile-lru`. BullMQ при каждом старте воркера пишет предупреждение, что хочет `noeviction`. Политику не менять в рамках этого деплоя: она влияет на все сервисы, решать владельцу.

## Фаза 4. Telegram

### BotFather

1. Создать бота, записать токен и имя.
2. `/setcommands` для этого бота: `my - Моя сводка`.
3. `/setjoingroups` → Disable. Бот работает только в личных чатах: сообщения из групп он игнорирует, но добавлять его туда незачем.

### Переменные окружения

`backend/.env`:

| Переменная | Значение |
|---|---|
| `KPI_BOT_TOKEN` | токен бота из BotFather |
| `KPI_BOT_USERNAME` | имя бота без `@`; из него собирается ссылка-приглашение `https://t.me/<имя>?start=kpi_<код>` |
| `KPI_WEBHOOK_SECRET` | случайная строка, например `openssl rand -hex 32`; Telegram пропускает только `A-Z a-z 0-9 _ -` |
| `KPI_UPLOADS_DIR` | каталог фото, если нужен не стандартный |
| `KPI_NOTIFY_QUEUE` | не задавать: имя очереди по умолчанию `kpi-notify`, backend и воркер должны совпадать |

Перед дописыванием в `.env` выполнить `tail -c 1 .env`: если файл не заканчивается переводом строки, новая переменная приклеится к последней.

`cron/.env` (читает `office_kpi_worker`):

| Переменная | Значение |
|---|---|
| `KPI_BOT_TOKEN` | тот же токен |
| `DATABASE_URL`, `REDIS_HOST`, `REDIS_PORT` | те же, что в `backend/.env` |
| `PROJECT_PREFIX` | тот же, что в backend: с ним строится ключ отметки «ежедневная задача за сегодня выполнена» |
| `KPI_NOTIFY_QUEUE` | не задавать |

`KPI_WEBHOOK_SECRET` воркеру не нужен. Без `KPI_BOT_TOKEN` воркер стартует, но уведомления получают статус `skipped` (`no_token`).

### Миграция

`0038_kpi_telegram` (таблицы привязок и приглашений) применяется вместе с остальными KPI-миграциями, см. выше. Номер перед запуском сверить с прод-`main`.

### Вебхук

Токен и секрет брать из `backend/.env` по одной переменной, в командах они не пишутся. Весь файл в оболочку не загружать (см. «Состояние прода»):

```bash
cd /home/davr/managers/backend
KPI_BOT_TOKEN=$(grep -E '^KPI_BOT_TOKEN=' .env | cut -d= -f2-)
KPI_WEBHOOK_SECRET=$(grep -E '^KPI_WEBHOOK_SECRET=' .env | cut -d= -f2-)
curl -sS "https://api.telegram.org/bot$KPI_BOT_TOKEN/setWebhook" \
  -d "url=https://api.office.lesailes.uz/api/kpi/bot/webhook" \
  -d "secret_token=$KPI_WEBHOOK_SECRET" \
  --data-urlencode 'allowed_updates=["message","callback_query"]'
curl -sS "https://api.telegram.org/bot$KPI_BOT_TOKEN/getWebhookInfo"
```

Префикс `/api` в адресе обязателен. В ответе `getWebhookInfo` смотреть `url`, `pending_update_count` и `last_error_message`.

Вебхук отвечает Telegram 200 на любой апдейт, кроме запроса с неверным секретом (401). Если `KPI_WEBHOOK_SECRET` или `KPI_BOT_TOKEN` на backend не заданы, он тоже отвечает 200 и пишет `console.error`: так Telegram не копит повторы из-за нашей конфигурации. Поэтому «нет ответов от бота» ищется в логе `office_api`, а не в `last_error_message`.

### Воркер office_kpi_worker

Процесс описан в `cron/pm2.config.js` и запускается из исходников (`bun kpi_worker.ts`). Запустить его нужно до того, как выдавать приглашения. Старые строки `kpi_notifications` в `pending` (до включения Telegram их никто не отправлял) воркер при первом проходе закроет как `skipped` (`no_binding`), пока ни у кого нет привязки. Если выдать приглашения раньше, человек сразу после `/start` получит пачку устаревших уведомлений. Первый запуск:

```bash
cd /home/davr/managers/cron
PATH=/root/.bun/bin:$PATH pm2 start pm2.config.js --only office_kpi_worker
pm2 save
```

В логе должна появиться строка `kpi worker started (queue kpi-notify, token: есть)`. Если там `token: нет`, воркер не нашёл `KPI_BOT_TOKEN` в `cron/.env`.

Что делает воркер: доставляет уведомления из `kpi_notifications` в Telegram, раз в 2 минуты подбирает застрявшие строки, в 10:00 по Ташкенту ставит напоминания оценщикам и сводку HR. Если ежедневный прогон упал, его повторит ближайший тик подметалки (после 10:00, пока за сегодня нет отметки в Redis). Для закрытого месяца напоминания и сводка не создаются.

Тексты сообщений и правила доставки лежат в `backend/src/modules/kpi`, а воркер их исполняет. Поэтому после каждого деплоя backend перезапускать оба процесса: `office_api` (с пересборкой бинарника) и `office_kpi_worker`:

```bash
pm2 restart office_kpi_worker
```

Без `--update-env`: из неинтерактивной ssh-сессии он подменяет окружение процесса и может потерять путь к нужной версии Node. Если он всё же нужен, сначала выставить правильный `PATH`, затем `pm2 save`.

В воркере и backend подключены разные версии `bullmq` (в `cron` 5.80.9, в `backend` 5.81.5). Формат ключей Redis у них совместим; после первого запуска достаточно посмотреть лог на ошибки очереди.

Предупреждение BullMQ про `maxmemory-policy` (см. «Проверки до деплоя», пункт 4) в логе воркера будет, это известно.

### Проверка после запуска

1. В админке: «Настройки KPI» → «Оценщики» (или сотрудники) → выдать себе приглашение.
2. Открыть ссылку в Telegram с телефона, нажать Start. Бот отвечает «Готово!» и предлагает выбрать язык.
3. Выбрать язык. Бот подтверждает выбор.
4. Отправить `/my`. Для сотрудника бот присылает последние оценки и нарушения месяца, для оценщика число сотрудников, которые ждут оценки.
5. Повторное открытие той же ссылки тем же телефоном снова отвечает «Готово!» и второй привязки не создаёт. Ссылка с другого телефона после использования считается недействительной.
6. Спор из бота: отправить сотруднику оценку, нажать «Оспорить», ответить сообщением с причиной (не короче `change_comment_min` символов). В админке в «Спорах» появится запись с источником telegram, оценщик получит уведомление.

### Проверки данных на проде до первого расчёта

Все запросы только на чтение. Вывод приложить к передаче HR: по нему видно, какие показатели у каких филиалов вообще смогут посчитаться. Подставить прошлый месяц вместо `2026-09`/`2026-10`, если расчёт идёт за другой.

Замеры кухни по типам заказа. Если у `COMMON` почти все `guest_wait_time_avg = 0`, сервис зала не замеряется, и показатель «Сервис» у филиалов будет без данных:

```sql
select o.order_service_type,
       count(*) filter (where p.cooking_finish_time is null) as no_finish,
       count(*) filter (where p.guest_wait_time_avg = 0) as zero_wait,
       count(*) as all_rows
from product_cooking_time p
join orders o on o.id = p.uniq_order_id
 and o.open_date_typed >= '2026-09-01' and o.open_date_typed < '2026-10-01'
where p.open_date_typed >= '2026-09-01' and p.open_date_typed < '2026-10-01'
group by 1;
```

Связки складов и групп iiko. Число строк каждого типа должно быть не меньше числа действующих филиалов; филиал без `iiko_id` остаётся без «Продаж» и «Сервиса», без `iiko_store_id` без «Себестоимости»:

```sql
select type, count(*) from credentials
where model = 'terminals' and type in ('iiko_id', 'iiko_store_id')
group by 1;
```

Принятые сверки инвентаризации. «Себестоимость» считается только по статусу `accepted`; сумма берётся из снимка при «принято»:

```sql
select status, count(*) from inventory_reconciliations
where period = '2026-09-30'
group by 1;
```

Если один ключ `iiko_id` или `iiko_store_id` записан у двух филиалов, каждому из них засчитывается вся выручка по этому ключу. Это нормально для расчёта балла, но итог по сети из таких строк складывать нельзя.

### Как запустить расчёт

1. HR заранее вносит планы выручки на экране «План выручки» (без плана «Продажи» остаются без данных).
2. Первый расчёт: кнопка «Пересчитать» на экране «Сеть» за прошлый месяц. Права: `kpi.manage` или `kpi.approve`.
3. То же без экрана: `POST /api/kpi/branch/compute` с телом `{"period": "2026-09-01"}` и cookie сессии HR. Ответ: `{ period, version, terminals, computed_at }`.

Каждый запуск создаёт новую версию, старые версии остаются в базе, экраны показывают последнюю. Два нажатия подряд дают две версии, ошибки нет. Если ни у одного филиала нет данных, ответ `version: null, terminals: 0`, и ничего не записывается. Будущий месяц отклоняется (`future_period`); текущий считать можно, это предварительный балл. Изменение весов и порогов действует со следующего пересчёта, посчитанные версии хранят свой снимок.

## Мини-приложение «Мой KPI»

Статическое приложение для сотрудников и оценщиков, открывается из Telegram кнопкой меню бота. Спека: `docs/superpowers/specs/2026-10-26-kpi-employee-miniapp-design.md`, разделы 10 и 11. Отдельного сервиса нет: backend отвечает на `/api/kpi/tg/...`, nginx раздаёт собранную статику с того же origin.

Требования к клиенту. Бандл собран под ES2018 и использует spread объектов и юникод-свойство `\p{L}` в регулярных выражениях. Ему нужны Android WebView / Chrome 64+ и iOS Safari 11.1+. На более старом клиенте бандл не запускается, но экран не пустой. Остаётся заставка из `index.html` (серые бруски на месте главного экрана), через 8 секунд под ней появляется подсказка на двух языках «Связь плохая, ещё пробуем» / «Aloqa yomon, yana urinib koʻryapmiz», и дальше ничего не меняется. Сеть тут ни при чём. Если сотрудник жалуется, что приложение бесконечно грузится при нормальной связи, спросить версию Telegram и Android System WebView (на iPhone — версию iOS) и попросить обновить.

Порядок выкладки. Backend выкладывается раньше клиента или вместе с ним. Клиент без поля `who` в ответе backend держит кэш экранов только в памяти. Без `tiers` в ответах `/review` и `/history` проценты «Вся оценка» (заголовок и строки изменений) и истории (баллы месяцев и средние за квартал) округляются обычным образом, без защиты порога ступени: там может стоять «90,0 %», когда главный экран пишет «89,9 %». Карточка прибавки на главном берёт шкалу из своего ответа и от этого поля не зависит.

### Миграция

Один Telegram-аккаунт может быть привязан и как сотрудник, и как оценщик. Других миграций нет: `opened_via = 'miniapp'` пишется в существующий `varchar(16)`.

Поле `when` новой записи должно оставаться больше максимума на проде (правило выше, «Проверки до деплоя», пункт 2), иначе файл молча пропустится. SQL прочитать до запуска:

```bash
PATH=/root/.nvm/versions/node/v20.20.2/bin:$PATH ./node_modules/.bin/drizzle-kit migrate
```

Откат. Код нельзя откатить без отката миграции: прежний код рассчитан на один уникальный индекс по `telegram_id`, и с двумя частичными индексами приглашения ломаются. Порядок. Пока шаги 2–3 меняют базу, а прежний код ещё не выложен, погашение приглашений падает с ошибкой Postgres 42P10: у нового кода нет индекса, на который он опирается. Поэтому перед шагом 2 остановить `office_api` (`pm2 stop office_api`) или заранее принять это окно.

1. Проверить, нет ли Telegram-аккаунтов с двумя строками привязок (сотрудник и оценщик одновременно, активные или нет): `select telegram_id from kpi_tg_bindings group by 1 having count(*) > 1;`. Старый индекс не частичный и считает все строки, в том числе неактивные, поэтому на таких данных он не создастся. Какую привязку оставить, решает HR; лишние строки удалить.
2. Вернуть индекс: `drop index kpi_tg_bindings_tg_employee_uq; drop index kpi_tg_bindings_tg_user_uq; create unique index kpi_tg_bindings_telegram_uq on kpi_tg_bindings using btree (telegram_id);`.
3. Удалить запись `0040` из `drizzle.__drizzle_migrations` (последняя по `created_at`), иначе повторная выкладка её пропустит.
4. Выложить прежний код, пересобрать бинарник `office_api`, перезапустить `office_api` и `office_kpi_worker`.

### nginx

Vhost `api.office.lesailes.uz` (`/etc/nginx/sites-available/api.office.lesailes.uz`). Блок вставляется внутрь `server { … }` с `listen 443 ssl`, до `location /`. До правки сделать бэкап `<vhost>.bak.kpi_app_<YYYYMMDD-HHMMSS>`, после неё выполнить `nginx -t` и `systemctl reload nginx`.

```
    # KPI MINIAPP START #
    location ^~ /kpi-app/ {
        alias /home/davr/managers/kpi_miniapp/dist/;
        index index.html;
        try_files $uri $uri/ /kpi-app/index.html;
        add_header Cache-Control "no-cache";
    }
    # KPI MINIAPP END #
```

`add_header` внутри `location` отменяет все `add_header`, унаследованные из `server {}` и `http {}`. Без следующего шага ответы `/kpi-app/` уйдут без HSTS и прочих общих заголовков vhost. До вставки блока посмотреть, какие заголовки действуют сейчас, вместе с подключёнными через `include`:

```bash
nginx -T 2>/dev/null | grep -n -E '^# configuration file|add_header'
```

Строки `# configuration file` показывают, из какого файла заголовок. Каждый `add_header` из `http {}` и из `server {}` этого vhost повторить внутри `location ^~ /kpi-app/` рядом с `Cache-Control`, с тем же `always`, если он там есть. Три заголовка в блок не копировать, даже если они есть в vhost:

- `X-Frame-Options`: Telegram Web (`web.telegram.org`) открывает мини-приложение во фрейме, и с этим заголовком там будет пустое окно;
- `Content-Security-Policy` в любом виде: политика API-хоста почти наверняка не пускает SDK с `telegram.org`, встроенные `style` (полоски баллов) и `blob:` (фото нарушений), и приложение не стартует или теряет часть экрана;
- `Cross-Origin-Embedder-Policy`: при `require-corp` браузер грузит скрипт с чужого origin, только если тот отвечает заголовком `Cross-Origin-Resource-Policy`, и SDK с `telegram.org` может не загрузиться.

Если какой-то из них в vhost есть, записать это в передаче.

Приложение должно жить на том же origin, что и API: запросы идут относительными путями `/api/kpi/tg/...`, без CORS. Значения `base` в `kpi_miniapp/vite.config.ts`, `location` и `KPI_MINIAPP_URL` совпадают буква в букву, включая хвостовой слэш. Почему слэши в `location` и `alias` обязательны и как работает `try_files`, описано в `docs/superpowers/passport-1c-c5-deploy-spec.md` (блок про `location ^~ /passport-app/`). Откат nginx: вернуть бэкап и сделать `nginx -t` и `reload`.

Проверка после reload:

| Проверка | Ожидание |
|---|---|
| `curl -s -o /dev/null -w '%{http_code}' https://api.office.lesailes.uz/` | `200`, как до правки: остальной vhost не задет |
| `.../kpi-app/` | `200`, `Content-Type: text/html` |
| `.../kpi-app/assets/<имя из dist>.js` | `200`, `application/javascript` |
| `.../kpi-app/nosuchpath` | `200`: запасной путь `try_files` отдаёт `index.html` |
| `curl -s -o /dev/null -w '%{http_code}' -X POST https://api.office.lesailes.uz/api/kpi/tg/auth` (без тела) | `401` или `422`, а не `404` и не HTML: статика не перехватила API на том же origin |

### Переменные окружения

`backend/.env`:

| Переменная | Значение |
|---|---|
| `KPI_MINIAPP_URL` | `https://api.office.lesailes.uz/kpi-app/` |
| `KPI_ADMIN_URL` | адрес админки только со схемой и хостом, без пути; по нему оценщик попадает в админку из приложения. Не задан или не годится: ссылки в приложении нет |
| `KPI_BOT_TOKEN` | настоящий токен бота (уже задан в фазе 4) |

`cron/.env`: тот же `KPI_MINIAPP_URL`. Кнопки «Открыть» в уведомлениях собирает воркер, а не backend.

Правила для `KPI_MINIAPP_URL`: только `https://`, непустой хост, без `?` и `#`; хвостовой слэш дописывается сам. Если переменная не задана или не годится, уведомления уходят без кнопок «Открыть», а `set-menu.ts` завершается с кодом 1.

`KPI_BOT_TOKEN` должен быть настоящим. Backend считает тестовым токен, который после обрезки пробелов начинается с `123456:kpi-` (`tokenAllowed` в `backend/src/modules/kpi/tg-app/init-data.ts`). Такой токен принимается, только когда `PROJECT_PREFIX` целиком равен `managers_test_` или `managers_smoke_`: значение сравнивается со строкой полностью, а не по началу, и без обрезки пробелов. Остальные токены проверка пропускает при любом префиксе. С тестовым токеном на боевом префиксе `/api/kpi/tg/auth` отвечает 503 `not_configured`, и приложение не входит ни у кого. Бот, вебхук и воркер этого токена не проверяют.

Перед дописыванием в `.env` выполнить `tail -c 1 .env`: если файл не заканчивается переводом строки, новая переменная приклеится к последней.

### Кнопка меню

Разовый ручной скрипт. Запускать после того, как `KPI_MINIAPP_URL` задан в `backend/.env`, и после каждой его смены:

```bash
cd /home/davr/managers/backend
/root/.bun/bin/bun run src/modules/kpi/tg/set-menu.ts
```

Скрипт сам читает `backend/.env`.

Скрипт ставит кнопку по умолчанию «Мой KPI», своя кнопка для чатов, привязанных на узбекском, и сбрасывает русские чаты на кнопку по умолчанию. Ожидаемый вывод: `kpi menu: default ok, uz chats N/N, ru chats M/M` и код выхода 0. Каждая неудача печатается отдельной строкой с причиной, токен в ней заменён на `***`. Код 1 значит, что кнопка по умолчанию не встала: разобраться до проверки с телефона. Повторный запуск безопасен.

Смена языка в приложении или кнопками языка в боте сама ставит кнопку меню этого чата: узбекский даёт «Mening KPI», русский возвращает кнопку по умолчанию. Это происходит только при настоящей смене языка (повтор того же выбора ничего не шлёт) и по возможности: неудача лишь пишется в лог `office_api`, язык при этом сохраняется. Скрипт `set-menu.ts` нужен после установки или смены `KPI_MINIAPP_URL` и чтобы поправить устаревшие чаты.
