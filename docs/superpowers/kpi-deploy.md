# KPI: заметки к деплою

Деплой выполняет человек. Здесь собрано то, что нужно проверить и запустить, и в каком порядке. Команды с `pm2`, `ssh` и `curl` против боевых сервисов эта разработка не запускала.

Каталог проекта на проде: `/home/davr/managers`. Спека: `docs/superpowers/specs/2026-10-25-kpi-design.md`, раздел 14.

## Общее для всех фаз

### Проверки до деплоя

1. Миграции. В `origin/main` последняя миграция — `0034_inventory_turnover`, KPI начинается с `0036_kpi_core`. `0035_hanging_orders_sync` догоняет дрейф: в `schema.ts` были таблицы `hanging_orders` без миграции; она идемпотентная. Номера и содержимое нужно сверить с прод-`main` (прод опережает `origin/main`, там могла появиться своя миграция с тем же номером).
2. Метки времени в журнале. `drizzle-kit migrate` сравнивает только `created_at` последней записи в `drizzle.__drizzle_migrations`. Поэтому поле `when` у `0035`–`0038` в `backend/drizzle/migrations/meta/_journal.json` должно быть строго больше, чем у последней применённой на проде миграции, иначе новые файлы молча пропустятся. Проверка на проде: `select max(created_at) from drizzle.__drizzle_migrations;`. Число строк в таблице с числом записей в журнале не совпадает (на проде нет записей для idx 0–8), это нормально; смотреть нужно на максимум.
3. Табельные номера. Фаза 3 сопоставляет сотрудников с файлом Workly по `employees.external_id`. До сих пор поле заполняла только форма аттестации. Выполнить `select count(*) from employees where external_id is not null;` и, если не ноль, сначала понять, что там лежит.
4. Redis. На проде Redis общий для всех сервисов и работает с `maxmemory-policy volatile-lru`. BullMQ при каждом старте воркера пишет предупреждение, что хочет `noeviction`. Политику не менять в рамках этого деплоя: она влияет на все сервисы, решать владельцу.

### Права

```bash
cd /home/davr/managers/backend
bun run src/modules/kpi/seed-permissions.ts
```

Скрипт заводит пять прав: `kpi_layout`, `kpi.evaluate`, `kpi.view`, `kpi.manage`, `kpi.approve`. Повторный запуск печатает `skip` для существующих.

Права ролям выдаются SQL-ом. Пример для роли `admin`; другим ролям выдавать по решению HR:

```sql
insert into roles_permissions (role_id, permission_id)
select r.id, p.id
from roles r
join permissions p on p.slug in ('kpi_layout', 'kpi.evaluate', 'kpi.view', 'kpi.manage', 'kpi.approve')
where r.code = 'admin'
on conflict do nothing;
```

После выдачи перезапустить `office_api`: кэш ролей в Redis перестраивается при старте backend. `office_api` работает из собранного бинарника `backend/app`, поэтому правки backend не подействуют, пока бинарник не пересобран.

## Фаза 4. Telegram

### BotFather

1. Создать бота, записать токен и имя.
2. `/setcommands` для этого бота: `my - Моя сводка`.
3. `/setjoingroups` → Disable. Бот работает только в личных чатах: сообщения из групп он игнорирует, но добавлять его туда незачем.

### Переменные окружения

`backend/.env`:

| Переменная | Значение |
|---|---|
| `KPI_BOT_TOKEN` | токен бота из BotFather |
| `KPI_BOT_USERNAME` | имя бота без `@`; из него собирается ссылка-приглашение `https://t.me/<имя>?start=kpi_<код>` |
| `KPI_WEBHOOK_SECRET` | случайная строка, например `openssl rand -hex 32`; Telegram пропускает только `A-Z a-z 0-9 _ -` |
| `KPI_UPLOADS_DIR` | каталог фото, если нужен не стандартный |
| `KPI_NOTIFY_QUEUE` | не задавать: имя очереди по умолчанию `kpi-notify`, backend и воркер должны совпадать |

Перед дописыванием в `.env` выполнить `tail -c 1 .env`: если файл не заканчивается переводом строки, новая переменная приклеится к последней.

`cron/.env` (читает `office_kpi_worker`):

| Переменная | Значение |
|---|---|
| `KPI_BOT_TOKEN` | тот же токен |
| `DATABASE_URL`, `REDIS_HOST`, `REDIS_PORT` | те же, что в `backend/.env` |
| `PROJECT_PREFIX` | тот же, что в backend: с ним строится ключ отметки «ежедневная задача за сегодня выполнена» |
| `KPI_NOTIFY_QUEUE` | не задавать |

`KPI_WEBHOOK_SECRET` воркеру не нужен. Без `KPI_BOT_TOKEN` воркер стартует, но уведомления получают статус `skipped` (`no_token`).

### Миграция

`0038_kpi_telegram` (таблицы привязок и приглашений) применяется вместе с остальными KPI-миграциями, см. выше. Номер перед запуском сверить с прод-`main`.

### Вебхук

Токен и секрет брать из окружения, в командах они не пишутся:

```bash
curl -sS "https://api.telegram.org/bot$KPI_BOT_TOKEN/setWebhook" \
  -d "url=https://api.office.lesailes.uz/api/kpi/bot/webhook" \
  -d "secret_token=$KPI_WEBHOOK_SECRET" \
  --data-urlencode 'allowed_updates=["message","callback_query"]'
curl -sS "https://api.telegram.org/bot$KPI_BOT_TOKEN/getWebhookInfo"
```

Префикс `/api` в адресе обязателен. В ответе `getWebhookInfo` смотреть `url`, `pending_update_count` и `last_error_message`.

Вебхук отвечает Telegram 200 на любой апдейт, кроме запроса с неверным секретом (401). Если `KPI_WEBHOOK_SECRET` или `KPI_BOT_TOKEN` на backend не заданы, он тоже отвечает 200 и пишет `console.error`: так Telegram не копит повторы из-за нашей конфигурации. Поэтому «нет ответов от бота» ищется в логе `office_api`, а не в `last_error_message`.

### Воркер office_kpi_worker

Процесс описан в `cron/pm2.config.js` и запускается из исходников (`bun kpi_worker.ts`). Первый запуск:

```bash
cd /home/davr/managers/cron
pm2 start pm2.config.js --only office_kpi_worker
pm2 save
```

В логе должна появиться строка `kpi worker started (queue kpi-notify, token: есть)`. Если там `token: нет`, воркер не нашёл `KPI_BOT_TOKEN` в `cron/.env`.

Что делает воркер: доставляет уведомления из `kpi_notifications` в Telegram, раз в 2 минуты подбирает застрявшие строки, в 10:00 по Ташкенту ставит напоминания оценщикам и сводку HR. Если ежедневный прогон упал, его повторит ближайший тик подметалки (после 10:00, пока за сегодня нет отметки в Redis). Для закрытого месяца напоминания и сводка не создаются.

Тексты сообщений и правила доставки лежат в `backend/src/modules/kpi`, а воркер их исполняет. Поэтому после каждого деплоя backend перезапускать оба процесса: `office_api` (с пересборкой бинарника) и `office_kpi_worker`:

```bash
pm2 restart office_kpi_worker
```

Без `--update-env`: из неинтерактивной ssh-сессии он подменяет окружение процесса и может потерять путь к нужной версии Node. Если он всё же нужен, сначала выставить правильный `PATH`, затем `pm2 save`.

В воркере и backend подключены разные версии `bullmq` (в `cron` 5.80.9, в `backend` 5.81.5). Формат ключей Redis у них совместим; после первого запуска достаточно посмотреть лог на ошибки очереди.

Предупреждение BullMQ про `maxmemory-policy` (см. «Проверки до деплоя», пункт 4) в логе воркера будет, это известно.

### Проверка после запуска

1. В админке: «Настройки KPI» → «Оценщики» (или сотрудники) → выдать себе приглашение.
2. Открыть ссылку в Telegram с телефона, нажать Start. Бот отвечает «Готово!» и предлагает выбрать язык.
3. Выбрать язык. Бот подтверждает выбор.
4. Отправить `/my`. Для сотрудника бот присылает последние оценки и нарушения месяца, для оценщика число сотрудников, которые ждут оценки.
5. Повторное открытие той же ссылки тем же телефоном снова отвечает «Готово!» и второй привязки не создаёт. Ссылка с другого телефона после использования считается недействительной.
6. Спор из бота: отправить сотруднику оценку, нажать «Оспорить», ответить сообщением с причиной (не короче `change_comment_min` символов). В админке в «Спорах» появится запись с источником telegram, оценщик получит уведомление.
