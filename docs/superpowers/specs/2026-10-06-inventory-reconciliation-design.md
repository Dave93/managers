# Сверка инвентаризаций с iiko — Design Doc

Дата: 2026-10-06. Статус: одобрен по разделам, ждёт ревью спеки.

Подпроект 2 к `docs/superpowers/specs/2026-10-02-inventory-counts-design.md` (ввод инвентаризации в админке). Там же, в разделе 3, первые факты об источнике. Здесь они уточнены и проверены на живых данных.

## 1. Цель

Менеджер филиала раз в месяц вслепую вводит пересчёт склада в админке, потом тот же пересчёт вводит в iiko (документ инвентаризации). Офису нужно сравнить:

- **A** — факт из админки (слепой пересчёт);
- **B** — факт, введённый в iiko;
- **C** — учётный остаток iiko до инвентаризации.

A ≠ B означает, что в iiko ввели не то, что посчитали (ошибка или подгонка под учёт). A − C и B − C — недостача или излишек против учёта, в количестве и деньгах. Офис разбирает расхождения и принимает сверку.

## 2. Зафиксированные решения

| # | Вопрос | Решение |
|---|--------|---------|
| 1 | Что сравниваем | На экранах — только A (админка филиала) и B (инвентаризация iiko) по каждому товару, строки A ≠ B подсвечены. Суммы, учёт C и разницы в деньгах не показываются (решение 07.10.2026); сервер их по-прежнему считает и хранит |
| 2 | Что делает офис | Разбор: статус «на разбор» / «принято» с комментарием. Объяснения филиала — не сейчас |
| 3 | Когда данные из iiko | Cron с 1-го по 7-е число ежедневно + кнопка «Загрузить из iiko» на месяц + «Обновить из iiko» по складу. Результат — снимок в БД |
| 4 | Защита от подгонки | Журнал правок после первой отправки (виден офису в сверке). Срока ввода нет — убран 07.10.2026 по решению пользователя (см. §8) |
| 5 | Какой документ iiko | Проведённый, `INVENTORY_CORRECTION` с номером, датой последнего дня месяца и словом «месяц» в комментарии (регистр не важен) |
| 6 | Несколько документов или ни одного «Месяц» | Статус «нужен выбор документа», офис выбирает из кандидатов |
| 7 | Непроведённый документ | Недоступен (см. п. 3). Сверка показывает A − C со статусом «ждём документ iiko» |
| 8 | Документ распровели после загрузки | Данные последней загрузки остаются, пометка «документ распроведён после загрузки» |
| 9 | Несколько пересчётов в админке за месяц | A = сумма по отправленным пересчётам, строка с пометкой «в нескольких пересчётах» |
| 10 | Товар только с одной стороны | В отчёте: товары админки ∪ ненулевой C ∪ ненулевая корректировка. Нет в админке — «не считали в админке», `skipped` — «не считали» |
| 11 | Подсветка | Любая A − B ≠ 0. Сортировка по сумме расхождения |
| 12 | Цена единицы | Корректировка: `sum ÷ qty`; иначе учёт: `sum ÷ amount` при `amount > 0`; иначе денег нет, только количество |
| 13 | Обновление после «принято» | Разрешено. Статус остаётся, ставится `changed_after_accept` |
| 14 | Не отправленный пересчёт | В обзоре — «черновик». Автоотправки нет |
| 15 | Постоянный процесс | Филиал проводит документ «Месяц» к началу месяца, распроводить для исправлений может только офис. Временное проведение ради снимка — ручное решение офиса, система его не требует |

## 3. Что известно об источнике (проверено 06.10.2026, только чтение)

**Публичный API iiko (`les-ailes-co-co.iiko.it`, сервер 9.4.8049, chain) не отдаёт документы инвентаризации** ни проведённые, ни черновики: 12 вариантов путей (`v2/documents/incomingInventory`, `documents/export/incomingInventory`, `…/byNumber`, `v2/documents/inventory` и др.) → 404. Тем же способом приходные накладные выгружаются (200). Внутренний протокол iikoOffice (`/resto/services/…`) не используем: недокументирован, а исследование заблокировано политикой доступа.

**Список документов с комментарием — `GET /resto/api/reports/storeOperations`** (`dateFrom`/`dateTo` в формате `dd.MM.yyyy`, `documentTypes=INCOMING_INVENTORY`, `productDetalization=false`). XML `storeReportItemDto`: `documentId`, `documentNum`, `documentComment`, `primaryStore` (= `corporation_store.id`), `date` (без времени), `type`, `sum`. Видны только проведённые документы.

- Строки `type = STORE_COST_CORRECTION` без номера — автоматическая корректировка себестоимости, бывают каждый день. Это не инвентаризация, отбрасываются.
- Июнь—август: 55 / 56 / 58 документов, все на последний день месяца. С «Месяц» — 52 / 54 / 56 (все филиалы). Без комментария — «1001 Центральный склад Chain» и «Ошхона». Двух инвентаризаций на один склад за месяц не было.
- На 06.10 за 30.09 проведено 2 документа (№2420 «Ошхона», №2387 Центральный склад), оба без комментария. Сентябрьские документы филиалов (например, №2395 у 19004) не проведены и в API не видны.
- Поле `Comment` в OLAP `TRANSACTIONS` комментарий складских документов **не переносит** (проверено на 5 актах списания с комментарием) — для отбора не годится.

**Корректировки по товарам — OLAP `TRANSACTIONS`**, фильтр `TransactionType = INVENTORY_CORRECTION`, `DateTime.DateTyped` = [период, период + 1 день). Группировка `Account.Id`, `Document`, `DateTime.Typed`, `Product.Id`; агрегаты `Amount`, `Sum.ResignedSum`.

- У каждой проводки две стороны. Сторона склада — строки, где `Account.Id` = id склада; за 31.08 все 58 складов документов совпали с `corporation_store.id`. Сопоставлять по названию не нужно.
- Документ содержит почти всю номенклатуру, включая нулевые корректировки (19004, №2115: 650 строк, 213 ненулевых).
- `Sum.ResignedSum` — сумма корректировки со знаком (недостача < 0).
- `StartBalance.Amount` / `FinalBalance.Amount` — **не** остаток на момент документа, не использовать.
- Время документов — 23:59 последнего дня (все 162 документа июня—августа).

**Учёт — `GET /resto/api/v2/reports/balance/stores?timestamp=…&store=<id>`** → `[{store, product, amount, sum}]`. Отрицательный `amount` нормален (19004 на 30.09: 63 товара).

**Формула B = C + корректировка проверена:** 19004, 31.08, документ №2115. Учёт на 23:58 + корректировка = учёт на 01.09 00:00 у всех 651 товара, расхождений 0, отрицательных B нет. Суммы `storeOperations` (недостача −9 905 579, излишек 14 379 599) совпали с OLAP.

**Лицензии:** каждый токен resto API занимает слот, `logout` всегда в `finally`. Одна задача — один токен.

## 5. Загрузка из iiko

Логика — в `backend/src/modules/inventory/reconcile/`: чистые функции (выбор документа, расчёт строк, цена, разница версий) отдельно от клиента iiko и от записи в БД. Одна точка входа `runReconcile({ period, storeId?, userId?, stage })`.

### Этап 1 — документы и корректировки (секунды)
1. `storeOperations` за `period` → документы `INVENTORY_CORRECTION` с номером, сгруппированные по `documentId`.
2. OLAP `TRANSACTIONS` за [`period`, `period` + 1) → строки стороны склада.
3. Область — склады, от которых ждём сверку за `period`:
   - склады с документом «Месяц» за `period` или за любой из 3 предыдущих месяцев (тот же `storeOperations` за последние дни этих месяцев);
   - склады с отправленным или черновым пересчётом в админке за `period`.

   При `storeId` — один склад. Для каждого склада области upsert `inventory_reconciliations`.

   Почему не все склады exord: из 74 складов `store_product_links` у 18 за июнь—август не было ни одного документа «Месяц» — тестовые («00000/00001 Тестирование склад»), «Офис», «4000 Pizza Pizza», «6000/7000/8000 United» и филиалы без ежемесячной инвентаризации в iiko (19012, 19014, 19016, 19018, 19029, 19033, 19043, 21017, 21021, 21025, 21031). Они бы вечно висели в «не получено». Новый филиал попадает в область с первым пересчётом в админке или первым документом «Месяц». Склады вне exord без «Месяц» (Центральный склад, «Ошхона») не попадают. Документы «Месяц» вне exord за июнь—август: 0. Для каждого склада upsert `inventory_reconciliations`.
4. Выбор документа:
   - ровно один документ с «месяц» в комментарии → он;
   - несколько с «месяц» или ни одного при других инвентаризациях склада на эту дату → `needs_choice`, кандидаты в `iiko_candidates` (ранее выбранный офисом документ сохраняется, если он всё ещё в списке);
   - документов нет → если документа не было и раньше: `waiting_iiko`; если был: строки не трогаем, `iiko_doc_state = unposted_after_fetch`, событие `doc_missing`.
5. Документ найден: сравнить его корректировки с текущими `iiko_lines`, заменить, записать `fetched` со списком изменений (только если документ новый или корректировки изменились — без ежедневного шума). Статус `waiting_iiko` / `needs_choice` → `ready`. `iiko_document_at` — `DateTime.Typed` этого документа в OLAP. Если сверка `accepted` и итоги изменились — `changed_after_accept = true`.
6. Записать результат этапа в статус задачи (п. «Очередь»). Это сигнал «данные сохранены».

### Этап 2 — учёт и расчёт (около минуты)
1. Для каждого склада области: `balance/stores` на `book_at` (запросы по одному, один токен на задачу).
2. A — из `inventory_counts` склада за `period` со статусом `submitted`: сумма `fact_qty` по товару, `skipped` → «не считали». Черновики не входят, `admin_state = draft`.
3. Строки: товары админки ∪ ненулевой C ∪ ненулевая корректировка. Снимок названия, единицы и папки — как в `counts.ts` (`GROUP_NAME_SQL`).
4. B = C + корректировка (только при выбранном документе), цена и суммы по п. 2.12, итоги в шапку, событие `calculated`.
5. Статусы этап 2 не меняет. `calculated` пишется, только если итоги изменились; у `accepted` при этом ставится `changed_after_accept`.

### Очередь и запуск
- BullMQ-очередь `inventory_reconcile`, воркер `cron/inventory_reconcile_worker.ts`, новый процесс PM2 `inventory_reconcile_worker`, `concurrency: 1` (по образцу `iiko_document_worker.ts`). Задача выполняет этап 1, затем этап 2.
- Одна задача на месяц: `jobId` = `reconcile:<period>`, склад (если есть) — в данных задачи. `removeOnComplete: true`, `removeOnFail: true` (иначе завершённая задача с тем же `jobId` молча блокирует следующие запуски за месяц — BullMQ не добавляет задачу с существующим id и не сообщает об ошибке). Перед постановкой API сам проверяет `queue.getJob(jobId)`: состояние `waiting` / `active` / `delayed` / `prioritized` → 409 `already_running`. Пока идёт любая загрузка месяца, вторую (по всем складам или по одному) запустить нельзя. Попыток — 1, без повторов: следующая попытка — cron завтра или кнопка.
- Имя очереди — `INVENTORY_RECONCILE_QUEUE` (по умолчанию `inventory_reconcile`), чтобы тесты не попадали в рабочую очередь. Ключ статуса в Redis передаётся в данных задачи: у воркера в `cron/` может быть другой `PROJECT_PREFIX`.
- Статус задачи в Redis `${PROJECT_PREFIX}inventory_reconcile:<period>`: `{stage, started_at, stage1_done_at, finished_at, received: [...], missing: [...], error}`.
- Cron в `cron/src/index.ts`: `"0 7 1-7 * *"` с `timezone: "Asia/Tashkent"` — задача «все склады, прошлый месяц».
- iiko-клиент: логин/пароль из `IIKO_LOGIN` / `IIKO_PASSWORD`, `logout` в `finally`, повтор при сетевой ошибке по образцу `fetchWithRetry`.

## 6. Права и API

Новое право **`inventory.reconcile`** (офис), сид в `backend/src/modules/inventory/seed-permissions.ts`. Даёт всё в таблице ниже. У филиала (`inventory.count`, `inventory.manage`) маршрутов сверки нет — C и B ему недоступны никогда.

| Маршрут | Что делает |
|---|---|
| `GET /inventory/reconciliations?period=` | Обзор: склады области (п. 5, этап 1, шаг 3), пересчёт админки (сдан / черновик / нет пересчёта), документ iiko, статус, итоги |
| `POST /inventory/reconciliations/fetch` `{period}` | Ставит задачу «все склады». 409, если уже идёт |
| `GET /inventory/reconciliations/fetch-status?period=` | Статус задачи из Redis |
| `GET /inventory/reconciliations/:id` | Шапка, строки, события, журнал правок филиала |
| `POST /inventory/reconciliations/:id/refresh` | Задача по одному складу |
| `POST /inventory/reconciliations/:id/document` `{document_id}` | Выбор документа из `iiko_candidates`, затем этап 2 по складу |
| `POST /inventory/reconciliations/:id/status` `{status, comment}` | `ready`/`in_review` → `in_review`/`accepted`; `accepted` → `in_review`. Комментарий обязателен для `in_review` |

Маршруты — Elysia-плагин `backend/src/modules/inventory/reconcile/routes.ts`, который подключается `.use()` внутри `inventoryControllerImpl` (`backend/src/modules/inventory/controller.ts`). Цепочку `app.ts` / `apiController` не удлиняем: она у предела глубины типов TS (TS2589), поэтому `inventoryController` уже экспортируется с расширенным типом. Фронт ходит так же, как сейчас инвентаризации: через `admin/lib/inventory-api.ts` с типами ответов из `backend/src/modules/inventory/reconcile/types.ts`, не через Eden. Ответы фиксированной формы, без `fields`.

## 7. Экраны (admin)

### 7.1 Обзор — `/<locale>/inventory/reconciliation`
- Выбор месяца (по умолчанию прошлый), кнопка «Загрузить из iiko».
- Во время задачи — прогресс по этапам. После этапа 1 — сообщение «Данные iiko сохранены: получено N, не получено M» и список неполученных складов. Формулировка нейтральная, без указаний что делать с документами в iiko.
- Таблица складов: склад, пересчёт админки, документ iiko (№, комментарий, «распроведён после загрузки»), статус сверки, строк A ≠ B, суммы A − B, A − C, B − C, «изменено после принятия».
- Фильтры: статус, бренд (Les / Chopar по организации). Сортировка по сумме A − B.

### 7.2 Склад — `/<locale>/inventory/reconciliation/[id]`
- Шапка: склад, период, документ, время загрузки и расчёта, «Обновить из iiko», смена статуса с комментарием. При `needs_choice` — список кандидатов с суммами и выбор.
- Вкладка «Расхождения»: группы — папки iiko; колонки A, B, C, A − B, сумма A − C, сумма B − C; пометки «не считали», «не считали в админке», «в нескольких пересчётах», «нет цены». Фильтр «только A ≠ B».
- Вкладка «Журнал»: загрузки и изменения корректировок между ними; правки филиала после первой отправки; возвраты в черновик; смены статуса.

## 8. Срок ввода — убран (07.10.2026)

Первая версия закрывала ввод 2-го числа следующего месяца в 12:00 (Ташкент) с разблокировкой офисом. По решению пользователя срок убран полностью:
- `allowedPeriods` — всегда текущий и прошлый месяц;
- правка, отправка, возврат в черновик и отмена пересчёта — без ограничения по времени;
- разблокировки офисом нет (маршрут и колонка `unlocked_until` удалены).

Защита от подгонки — журнал правок филиала после первой отправки: записи с `created_at` или `deleted_at` позже первого события `submitted` и события `reopened`.

## 9. Ошибки и пограничные случаи

| Случай | Поведение |
|---|---|
| iiko недоступен / ошибка авторизации | Задача падает, ошибка в статусе задачи, данные прошлых загрузок не меняются. Cron повторит завтра |
| Нет свободной лицензии | То же, текст ошибки iiko в статусе |
| Этап 1 прошёл, этап 2 упал | Корректировки сохранены, расчёт повторяется следующим запуском или кнопкой |
| Документ распровели и провели заново с другими цифрами | Новая загрузка, событие `fetched` со списком изменений |
| Склад не из exord, но с документом «Месяц» | Попадает в область, A пусто |
| Товар удалён в iiko | Название из OLAP или снимка |
| Время документа не 23:59 | `book_at` = время документа − 1 мин |
| Пересчёт админки отправлен после расчёта | Пересчитывается следующей загрузкой или кнопкой «Обновить из iiko» |

## 10. Проверки

**Первая задача плана — проверка формулы на всех складах августа** (около 56 документов «Месяц» за 31.08): учёт на `время документа − 1 мин` + корректировка = учёт через минуту после документа. Данные исторические, только чтение. Ловит склады, где в ту же минуту попала другая проводка.

`bun test` в `backend/` (`bun:test`, по образцу `inventory/rules.test.ts`), на локальной БД:
- периоды: текущий и прошлый месяц в любой день; пересчёт давнего периода можно править, отправлять и возвращать; маршрута разблокировки нет;
- выбор документа: один «Месяц», два «Месяц», только без комментария, строки `STORE_COST_CORRECTION` отбрасываются, ранее выбранный документ сохраняется;
- расчёт: B = C + корректировка; цена из корректировки / учёта / нет; объединение строк; несколько пересчётов; `skipped`;
- версии: изменение корректировок даёт событие со списком; пропавший документ не стирает строки; `changed_after_accept`;
- данные в тестах синтетические. Реальные выгрузки iiko в репозиторий не кладём; проверка на реальных данных — отдельные задачи плана (формула на всех складах августа и прогон сверки за август на локальной базе с чтением из iiko);
- доступ: пользователь с `inventory.count` + `inventory.manage` получает 403 на всех маршрутах сверки; ответы ввода по-прежнему без цифр iiko.

Запросы к iiko в тестах не ходят — клиент подменяется фикстурами.

- Объяснения филиала по строкам расхождений.

## 12. Изменение 07.10.2026: экраны без сумм

По решению пользователя экраны сверки показывают только то, что записано в инвентаризации iiko (B), и то, что филиал ввёл в админке (A):
- обзор: склад, пересчёт админки, документ iiko, статус, число строк A ≠ B (сортировка по нему);
- склад: число строк A ≠ B; таблица «Товар / Админка филиала (A) / Инвентаризация iiko (B)», расходящиеся значения подсвечены, фильтр «Только A ≠ B»;
- выбор документа: номер, дата, комментарий — без сумм.

Учёт C, суммы A − C / B − C / A − B и цена единицы на экраны не выводятся. Модель данных и расчёт (§4–5) не менялись.

### Дополнение 07.10.2026: разница и отметка «проверено»
- Таблица склада: «Товар / Админка филиала (A) / Инвентаризация iiko (B) / ± разница / Проверено». Разница = A − B в количестве, со знаком («+» — в админке больше). Над таблицей — «Проверено N из M расхождений».
- Отметка — галочка офиса по строке, хранится в `inventory_reconciliation_line_marks` (сверка, товар, кто, когда; миграция 0031). Отдельная таблица, потому что строки сверки пересоздаются при каждом расчёте. Маршрут `POST /inventory/reconciliations/:id/lines/:productId/mark {checked}` под `inventory.reconcile`. Отмеченная строка с расхождением перестаёт подсвечиваться целиком, подсветка остаётся на разнице.

## 13. Изменение 08.10.2026: отправленный пересчёт филиал не меняет

После «Отправить» менеджер филиала ничего не может изменить: ввод, добавление позиций и «не считали» закрыты для отправленного пересчёта (было и раньше), а «Вернуть в черновик» теперь доступно только офису с правом `inventory.reconcile` (`can_reopen` в ответе, 403 для филиала). Возврат пишется событием `reopened` и виден в журнале сверки. На странице сверки склада пересчёты в блоке «Пересчёты в админке» — ссылки на страницу пересчёта, где офис возвращает его в черновик.
