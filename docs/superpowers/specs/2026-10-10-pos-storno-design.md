# Возврат закрытого чека с кассы из админки (POS storno)

Дата: 2026-10-10. Статус: черновик, ждёт согласования.

## Задача

Кассир пробил чек неверно (например, Les Ailes Chilonzor, касса 15, чек 112, 10.10 15:59,
Longer ×3 = 72 000, HUMO). Сейчас исправить можно только на кассе: возврат + новый чек.
Нужно, чтобы admin вернул чек из админки, а новый чек кассир пробил сам.

## Почему так, а не иначе

- **iikoCloud**: методов возврата закрытого заказа нет (`order/cancel` — только открытый заказ
  зала, `deliveries/cancel` — только доставка). Заказы зала, созданные на кассе, облако
  вообще не видит: `order/init_by_table` на Chilonzor падает с «already in use»,
  `order/by_table` за день — 0 заказов (проверено 10.10).
- **iikoServer resto/api**: методов возврата не нашлось.
- **iikoFront API V8** (плагин на кассе) умеет: `StornoOrder` (заказ текущей смены),
  `StornoPastOrder` (заказ закрытой смены), `DeleteOrder`. Плагин `tablo_plugin`
  (`C:\projects\tablo_full`) уже на V8, с лицензией модуля, установщиком и автообновлением —
  возврат добавляем в него.
- HUMO возвращается без банковского терминала (проверено пользователем).

## Решения пользователя (10.10)

- Новый чек пробивает кассир; админка только возвращает.
- Возврат **без списания** (продукты возвращаются на склад) — право `F_SWWOFF`.
- Возврат делает **служебный сотрудник** «API-возврат» в iikoChain; его PIN хранится на
  сервере и уходит на кассу только внутри команды.

## Как найти чек

iikoServer OLAP `SALES` даёт всё нужное (проверено на чеке 112):

```
UniqOrderId.Id          23c37166-3731-493d-ad3c-70c8b5bef91f   ← id заказа на кассе
OrderNum                112
CashRegisterName        19002 Chilonzor targoviy kassa
CashRegisterName.Number 15                                     ← куда слать команду
RestaurantSection       19002 Чиланзар Зал
SessionID / SessionNum  f44bea00-… / 176                       ← текущая или закрытая смена
PayTypes, OrderType, CloseTime, DishDiscountSumInt, Storned, OrderDeleted
```

`Department` в OLAP — бренд («Les Ailes» / «Chopar пицца»), филиал — по кассе / залу.

## Поток

```
Админка: поиск чека (OLAP) → «Вернуть чек» → подтверждение (сумма, позиции, касса)
backend: команда в managers_pos_commands (pending), одна активная на заказ
плагин на кассе №15 раз в 15 с: POST /api/pos/commands/claim   (свой токен)
   → перечитать заказ; уже возвращён → done без действий
   → смена открыта → StornoOrder; иначе → StornoPastOrder (без списания)
   → POST /api/pos/commands/:id/result {ok, message}
backend: done/failed, журнал; через ~1 мин сверка с OLAP (Storned = TRUE)
админка: статус команды; кассир пробивает новый чек
```

## Backend (managers)

- `managers_pos_terminals`: машина кассы (iiko terminal id, номер кассы, название кассы,
  бренд), **свой токен** (хранится хэш), `approved` — включает admin вручную.
- `managers_pos_commands`: id, тип `storno`, iiko order id, номер чека, касса, сумма,
  кто создал, статус `pending → claimed → done | failed | expired`, `claimed_at`,
  результат, время. Уникальность: одна незавершённая команда на заказ.
- Регистрация кассы: плагин с общим токеном бренда просит регистрацию → получает свой
  токен → касса ждёт `approved`. Общий токен лежит на каждой кассе, поэтому команды им
  не выдаются.
- `claim` выдаёт команду только кассе с тем же номером и тем же iiko terminal id;
  лиза 2 мин — если результат не пришёл, команда не переотдаётся, а уходит в
  `failed (нет ответа)`: повторять возврат вслепую нельзя, admin смотрит OLAP и решает.
- Права: новый permission `pos.storno`, только admin. Журнал — кто, когда, что вернул.
- Срок: команда, не забранная за 10 мин (касса выключена) → `expired`.
- PIN служебного сотрудника — в env backend, отдаётся только в ответе `claim`.

## Плагин (tablo_plugin) — делает сессия tablo_full

- Отчёт о кассе дополнить номером и именем кассы (`GetHostTerminal()`, номер кассы).
- Опрос `claim` раз в 15 с, только при наличии своего токена и `approved`.
- Идемпотентность: id выполненных команд — в реестре/SQLite; перед возвратом перечитать
  заказ, уже возвращён → сообщить `done`.
- `AuthenticateByPin(pin)` → credentials; PIN не сохранять.
- `StornoOrder` если смена заказа открыта и принадлежит этой кассе, иначе
  `StornoPastOrder` с типом удаления `WriteoffType.None` и типом оплаты из
  `GetPaymentTypesToStornoPastOrderItems`.
- Ошибки (`PaymentActionFailedException.Reason`) — текстом в результат.
- Плагин ставится на все кассы, где пробивают чеки (сейчас Chilonzor без плагина).

## Проверка

1. Одна касса с плагином, один реальный чек на маленькую сумму, пробитый для теста.
2. Сверить в iikoOffice и OLAP: `Storned = TRUE`, деньги и склад.
3. Повторный `claim` той же команды не делает второй возврат.
4. Только потом — раскатка плагина и включение кнопки.

## Ревью плагинной части (сессия tablo_full, 2026-10-12, SDK 8.7 / iikoFront 9.4)

Не проверено живьём. Что уточнено и добавлено:

- **Идентификаторы:** `ICashRegisterInfo.Number` (≈ `CashRegisterName.Number` из OLAP), `.Name`, `.Id`;
  терминал → `GetHostTerminalPointsOfSale()` (касс может быть несколько — сверять все).
- **Поиск заказа на кассе:** `TryGetOrderById` нашёл → `StornoOrder` (заказ, оплаченный на ЭТОЙ кассе);
  иначе `GetPastOrder(orderId)` (с сервера) → `StornoPastOrder`. Сверять `SessionID` с OLAP не нужно.
- **Полная сигнатура** `StornoPastOrder(PastOrder, IPaymentType, IRemovalType, IRestaurantSection, IOrderType,
  ICredentials, ChequeAdditionalInfo, TaxationSystem?, OrganizationDetailsInfo)`: секция — из
  `GetHostTerminalRestaurantSections()`, тип заказа — из заказа; без фискализации остальное, видимо, null.
- **«Без списания»** = `IRemovalType` с `WriteoffType.None` из `GetRemovalTypesToStornoPastOrderItems()`;
  такой тип должен быть заведён в iikoOffice, иначе вернуть без списания нельзя.
- **Тип оплаты возврата** — из `GetPaymentTypesToStornoPastOrderItems()`, ищем HUMO исходного заказа;
  нет в списке → `failed`, другой не подставляем.
- **Открытая смена** на исполняющей кассе, скорее всего, нужна (возврат создаёт заказ в текущей смене).
- **Права служебного сотрудника:** F_SWWOFF + право на возврат и закрытые заказы + доступ к группе терминалов.
  PIN — только в памяти, в лог не писать (логи заливаются на сервер).
- **Побочки:** возможна печать чека и модальный диалог на кассе → таймаут и `failed`.
- **Идемпотентность:** id команды в SQLite ДО вызова (`in_progress`), затем `done/failed`; перед вызовом
  перечитать заказ (`StornedOrderId` / `Storned`).
- **Опрос:** backoff при ошибках + jitter. Токен кассы — в реестре HKLM (`.dll.config` перезаписывается обновлением).
- **Оценка плагина:** 4–6 рабочих дней без раскатки.

## Тестирование (решение пользователя 2026-10-12)

«Ofis Test» (машина пользователя, iikoFront → боевой RMS chopar) — тестовая касса, можно проводить любые
операции. Заказы там уходят в боевые отчёты, поэтому тест — на заказах с малой суммой.
Порядок: 1) вручную в iikoFront: есть ли тип удаления без списания, проходит ли возврат HUMO при открытой
и закрытой смене; 2) пробная сборка плагина с локальным вызовом возврата (без очереди с сервера) только
на Ofis Test; 3) только после этого — очередь команд.
