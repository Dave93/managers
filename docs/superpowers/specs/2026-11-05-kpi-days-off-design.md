# Выходные дни в KPI: выдача управляющим в мини-приложении

Дата: 2026-11-05. Ветка `feature/kpi-days-off` от `origin/main` (e9452f91).

## Зачем

HR подтвердил 2026-11-05: выходные сотрудникам выдаёт управляющий филиала и фиксирует причину. В графиках Workly выходных нет: у 269 из 344 сотрудников Les Ailes и 112 из 133 Chopar все 31 день месяца помечены рабочими. Отчёт T12 поэтому считает выходные прогулами (20–26% ложных за октябрь), а формула балла `ontime/days` засчитывает их против сотрудника. Создать выходной в Workly через API нельзя (раздел «Отгулы» только читается), так что источником правды становится наша база.

## Цели

- Управляющий (оценщик с `kpi.evaluate`) выдаёт выходной сотруднику своего филиала из мини-приложения: сотрудник, даты «с–по», причина.
- Выходной не считается прогулом: ни в балле «Приход и уход», ни в баллах филиала, ни в списке «Сотрудники KPI», ни в табеле, ни в «Моей посещаемости».
- Выходной виден как отдельный статус в табеле `/kpi/timesheet`, карточке сотрудника и мини-приложении сотрудника.
- Выданный выходной можно отменить (автор, пока месяц не закрыт).

## Не цели

- Отмена выходных HR-ом из админки (следующий шаг). В этой итерации HR их только видит.
- Telegram-уведомление сотруднику о выданном выходном.
- Лимит выходных в месяц и согласование с HR (решение владельца: лимита пока нет, согласования нет).
- Запись выходных обратно в Workly.
- Любые изменения синхронизации Workly (`workly/attendance.ts`) и `workly/quality.ts`.

## Решения владельца (2026-11-05)

Причины: болезнь, семейные обстоятельства, отгул, отпуск, по графику, другая (текст от 3 символов). Окно дат: назад, пока месяц KPI не закрыт; вперёд не дальше 31 дня от сегодня. Лимита нет. HR не согласует: выходной действует сразу. Причину видят управляющий и HR; сотруднику в его приложении показывается только «Выходной». Отмена: автор в мини-приложении. Уведомление сотруднику в Telegram не делаем.

## Решения исполнителя (проверьте при чтении)

1. **Наложение при чтении, синхронизация не меняется.** `kpi_attendance` пересобирается каждой синхронизацией Workly (импорт заменяется), флаг там не удержится. Workly по-прежнему пишет `absent`; выходные накладываются при чтении. Отмена работает без пересинхронизации, а если HR позже заведёт выходные в графики Workly, ничего не ломается.
2. **Знаменатель балла.** День, который Workly считает прогулом, но на который есть выходной, выпадает из `days` и из прогулов. Балл `ontime/days` считается по оставшимся дням; основание получает хвост «, выходных N». Если все дни выходные, балла нет (как «нет данных»).
3. **Пришёл в выходной.** Если на день с выходным в Workly есть присутствие (`absent = false`), строка Workly главнее: день считается обычным.
4. **Диапазон.** Не больше 31 дня за запрос. Дни, где у сотрудника уже есть активный выходной, пропускаются без ошибки (повтор запроса безопасен); ответ перечисляет созданные.
5. **Назначение.** Проверка `canEvaluate` по текущим филиалу и карте сотрудника, как у нарушений. Если назначение оценщика ограничено картой, выходные доступны только сотрудникам этой карты. Неактивному сотруднику выходной не выдаётся.
6. **Права на чтение причины в админке** те же, что у табеля (`kpi.view`, `kpi.manage`, `kpi.approve`, видимость по филиалам). Отдельного права нет.

## Данные

Миграция `0042_kpi_days_off.sql` (на проде и в origin последняя 0041; номер сверить с продом перед генерацией). Таблица `kpi_days_off`, одна строка на день:

| поле | тип | |
|---|---|---|
| `id` | uuid pk | |
| `employee_id` | uuid not null | |
| `day` | date not null | |
| `terminal_id` | uuid not null | филиал сотрудника на момент выдачи (снимок, как в `kpi_attendance`) |
| `reason_code` | varchar(16) not null | `sick` `family` `time_off` `vacation` `schedule` `other` |
| `reason_text` | text null | обязателен (≥3 символов после trim) при `other`, иначе null |
| `given_by` | uuid not null | пользователь |
| `created_at` | timestamptz default now() | |
| `cancelled_at` | timestamptz null | мягкая отмена |
| `cancelled_by` | uuid null | |

Индексы: уникальный частичный `(employee_id, day) where cancelled_at is null`; `(terminal_id, day)`; `(given_by, day)`. После отмены тот же день можно выдать заново.

Миграции не идемпотентны: перед применением просмотреть сгенерированный SQL; номер и `meta/_journal.json` сверить с продом.

## Единое наложение

Два новых файла в `backend/src/modules/kpi/` владеют всей логикой выходных (по образцу пары `attendance-parse.ts` / `attendance.ts`): `days-off-rules.ts` без БД (константы причин, разбор дат и причины, окно) и `days-off.ts` (`giveDaysOff`, `cancelDayOff`, `listGivenDaysOff`, `dayOffForm`) с двумя читателями для наложения:

- `activeDaysOff(db, {employeeIds?, terminalIds?, from, to})` → набор пар `(employee_id, day)` с причиной и автором;
- SQL-фрагмент `absentWithDayOff(attendanceAlias)` для агрегатов: условие «строка прогул и на неё есть активный выходной».

Места, куда подключается наложение (эти шесть читают `absent`):

| где | что меняется |
|---|---|
| `kpi/attendance.ts` `attendanceStats` + `attendance-parse.ts` `attendanceSuggestion` | строки «прогул + выходной» отбрасываются, их число идёт в `off`; `AttendanceStats` получает необязательное поле `off`; в основание «, выходных N» |
| `kpi/people.ts` | в агрегате `absent` и в `ontime/late` такие строки не считаются |
| `kpi/branch-facts.ts` (балл филиала) | такие строки не входят ни в `days`, ни в `absent` |
| `kpi/attendance-board.ts` | `BoardDay` получает статус 3 «выходной» (`[3, 0, null, null]`) для дня с выходным, где в Workly прогул или записи нет; `BoardEmployee.off` — карта «число дня → причина, текст, кто выдал» только для таких дней |
| `kpi/tg-app/attendance.ts` | `TgAttendanceDay.day_off: boolean`; день с выходным без присутствия приходит как `day_off: true, absent: false`, причина не отдаётся |
| `workly/quality.ts` | не меняется: он оценивает качество данных Workly, а не посещаемость |

## API мини-приложения (оценщик, `/kpi/tg/ev/*`)

Тот же Bearer-guard `kpiTgCtx` и `evaluatorActor`. Типы в `ev-types.ts` (файл без импортов, его берёт `kpi_miniapp`).

- `GET /kpi/tg/ev/day-off-form?employee_id` → сотрудник, список причин, окно дат (`min`, `max`), активные выходные сотрудника за окно.
- `POST /kpi/tg/ev/days-off` `{employee_id, from, to, reason_code, reason_text?}` → `{created: EvDayOff[]}`.
- `GET /kpi/tg/ev/days-off?period=` → мои выданные выходные месяца, с `can_cancel`.
- `POST /kpi/tg/ev/days-off/:id/cancel` → `EvDayOff`.

Коды ошибок (добавить в `EvErrorCode`): `bad_dates`, `bad_reason`, `reason_text_required`; остальные из существующих: `not_found`, `bad_id`, `forbidden`, `out_of_scope`, `period_closed`, `already_cancelled`, `bad_period`. Закрытый месяц блокирует выдачу и отмену за его дни (`isPeriodClosed`). Отменить может только автор (чужое — `forbidden`).

## Мини-приложение (`kpi_miniapp`)

- Маршруты: `ev_dayoff` (форма выдачи, `#/ev/dayoff/<employee_id>`), `ev_daysoff` (список выданных, `#/ev/daysoff` или `#/ev/daysoff/<YYYY-MM>`).
- Кнопка «Выходной» на экране оценки сотрудника, строка «Выданные выходные» рядом с «Мои нарушения» в списке.
- Форма: две нативные даты (с, по), причина списком, поле текста при «Другая причина». Подтверждение с итогом «N дней».
- «Моя посещаемость» (экран сотрудника): отдельная подпись и цвет для `day_off`.
- Тексты ru и uz в `i18n.ts`. Новый вид экрана — по образцу `ev-violation` / `ev-violations` (`view/` чистая модель + `screens/` DOM).

## Админка

- `lib/kpi/timesheet.ts`: статус `dayoff` (из `BoardDay[0] === 3`), итоги `off`, фильтры без изменений; прогулы в шапке уже без выходных.
- Цвет и подпись в `day-style.ts`, легенда и подсказки матрицы и списка, причина и автор в боковой панели.
- Карточка сотрудника `/kpi/employee/[id]` и обзор: тот же статус там, где она рисует дни посещаемости.
- Тексты в 4 локалях (`en`, `ru`, `uz-Latn`, `uz-Cyrl`); узбекские варианты проверить носителем.
