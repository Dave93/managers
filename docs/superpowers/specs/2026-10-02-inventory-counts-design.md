# Инвентаризации: ввод остатков в админке — Design Doc

Дата: 2026-10-02. Статус: одобрен по секциям, ждёт финального ревью спеки.

## 1. Цель

Раз в месяц менеджер филиала пересчитывает склад. Сейчас пересчёт вводится только в iiko, в документ инвентаризации. Там видно расчётный остаток, поэтому факт легко «подогнать» под учёт.

Нужно место в админке, где филиал **слепо** вводит фактические остатки: без цифр iiko, быстро, с телефона, планшета или POS-экрана, в несколько человек параллельно и при плохом интернете на складе. Эти данные потом сравниваются с iiko.

Работа разбита на два подпроекта:

1. **Ввод инвентаризации** (эта спека): шаблоны, экран ввода, хранение результатов.
2. **Сверка с iiko** (отдельная спека позже): учётный остаток, факт из проведённой инвентаризации iiko, отчёт расхождений и разбор офисом. Пункт 3 фиксирует, что уже известно, чтобы модель данных подпроекта 1 подошла без переделок.

## 2. Зафиксированные решения

| # | Вопрос | Решение |
|---|--------|---------|
| 1 | Назначение | Сверка с iiko. Движение товаров по-прежнему ведётся в iiko, админка собирает независимый факт |
| 2 | Кто вводит | Менеджер и помощники (повара, кладовщик), у каждого свой логин. Ежемесячно, **до** ввода инвентаризации в iiko |
| 3 | Слепой ввод | Учётных цифр iiko нет на экранах ввода и в ответах API для ввода |
| 4 | Состав пересчёта | Шаблоны инвентаризаций на организацию, их ведёт офис |
| 5 | Запуск | Вручную менеджером: выбрать шаблон, подтвердить период |
| 6 | Единицы | Только основная единица товара (`mainUnit`: кг / л / шт и т. п.), дробные значения разрешены |
| 7 | Группировка | Папки номенклатуры iiko (`nomenclature_element.parent_id` → `nomenclature_group`) |
| 8 | Параллельный ввод | Да, несколько человек с разных устройств в одной инвентаризации |
| 9 | Один товар в нескольких местах | Несколько записей на позицию, итог — сумма. Каждая запись помнит автора и время |
| 10 | Интернет | Нужен офлайн-буфер: записи копятся на устройстве и досылаются при появлении сети |
| 11 | Товар вне шаблона | Можно добавить поиском по номенклатуре. Такая позиция помечается «добавлено» |
| 12 | Устройства | Телефон (портрет), планшет и POS-экран (альбом). Один адаптивный экран |
| 13 | Компоновка ввода | Таблица с полями: группа → позиция → единица → факт |

## 3. Что известно об источнике (проверено 02.10.2026)

Эти данные нужны подпроекту 2. Здесь они объясняют выбор ключей в модели.

- **Филиалы уже проводят инвентаризации в iiko ежемесячно**, датой последнего дня месяца, 23:59. OLAP `TRANSACTIONS`, тип `INVENTORY_CORRECTION`: 31.07.2026 — 56 складов, 31.08.2026 — 58 складов, за сентябрь на 02.10 документов ещё нет.
- **Учётный остаток на любой момент:** `GET /resto/api/v2/reports/balance/stores?timestamp=…&store=<id>` на `les-ailes-co-co.iiko.it`. Ответ: `[{store, product, amount, sum}]`. `store` = `corporation_store.id`, `product` = `nomenclature_element.id` (сошлись 164 из 164). Бывают отрицательные `amount` и `sum = 0`.
- **Разница по каждой позиции из проведённой инвентаризации** приходит через OLAP `TRANSACTIONS` с полями `Product.Id`, `Product.Num`, `Product.Name`, `Product.MeasureUnit`, `Document`, `Amount` (на складе 19004, 31.08 — документ №2115, 650 строк). В OLAP склад отдаётся названием (`Store`), id склада там нет.
- **Непроведённые инвентаризации iiko** через API не нашлись: `v2/documents/incomingInventory`, `documents/export/incomingInventory` и `v2/documents/inventory` возвращают 404.
- **Ловушка со временем:** после проведения инвентаризации iiko учётный остаток становится равным факту iiko. Учёт для сверки нужно брать строго до документа (документ в 23:59 → остаток на 23:58).
- Каждый токен resto API занимает лицензионный слот, поэтому `logout` нужно вызывать в `finally`.
- `balance_store` — мёртвая синхронизация (786 тыс. строк, 03.2024–09.2024), не используется и не трогается.

**Что из этого следует для подпроекта 1:** `inventory_counts.store_id` = id склада iiko, `lines.product_id` = id товара iiko, `period` = последний день месяца, итог фиксируется в `lines.fact_qty` при отправке. Колонки сверки (`book_qty`, `iiko_fact_qty`, `unit_cost`) добавит подпроект 2.

## 4. Данные о номенклатуре (прод, 02.10.2026)

- Товаров `GOODS`/`PREPARED`, не удалённых: 652. У 647 заполнен `parent_id` (папка iiko).
- Папки: «Склад / Мясные продукты» (31), «Склад / Приправы, соусы, сиропы, пасты» (40), «Склад / Хозтовары» (39), «Les Ailes / Коробки, стаканы Les Ailes» (27), «Chopar / Полуфабрикаты Chopar» (19) и т. д. Родительская папка + папка дают понятное название группы.

### Правила
- Итог строки в `draft` — сумма `qty` живых записей (`deleted_at is null`). Строка считается «посчитанной», если у неё есть хотя бы одна живая запись или стоит `skipped`.
- Чтобы исправить запись, её удаляют и вводят заново. Запись не редактируется, поэтому параллельные участники не затирают друг друга.
- Если поставить `skipped` позиции с записями, нужно подтверждение, а записи сохраняются. Если поставить `skipped = false`, позиция снова считается обычной.
- Период по умолчанию: последний день текущего месяца. В первые 5 дней месяца предлагается и прошлый месяц: пересчёт за 31.10 могут начать вечером 31-го и закончить 1-го утром.

## 6. Права и доступ

Новые права в `permissions` (миграцией): `inventory.count`, `inventory.manage`, `inventory.templates`. Привязку к ролям делает администратор вручную.

| Действие | Право |
|---|---|
| Видеть инвентаризации своих складов, добавлять и удалять записи, добавлять позицию, ставить «не считали» | `inventory.count` |
| Начать, отправить, вернуть в черновик, отменить | `inventory.manage` |
| CRUD шаблонов, блок «Добавляли при пересчёте» | `inventory.templates` |

**Склад проверяется на сервере в каждом запросе:** `store_id` инвентаризации должен быть в `users_stores` текущего пользователя, иначе 403. Исключение — пользователь с `inventory.templates`: ему доступны все склады в режиме чтения для обзора. Это отличается от текущих накладных, где склад просто приходит из фильтра.

Удалить запись можно свою или, при наличии `inventory.manage`, любую. Удалять записи в `submitted` нельзя никому.

## 8. Синхронизация и офлайн

**Операции:**
```ts
type Op =
  | { op: "add"; id: string; line_id: string; qty: number; client_created_at: string }
  | { op: "delete"; id: string };
```

**Сервер** (`entries/sync`), одна транзакция на пачку:
- `add`: `INSERT … ON CONFLICT (id) DO NOTHING`. Строка должна принадлежать этой инвентаризации.
- `delete`: ставит `deleted_at`/`deleted_by`, если запись жива. Если записи нет или она уже удалена, ничего не происходит.
- Если инвентаризация не `draft`, ответ 409 `{status}` и ничего не применяется.
- Ответ: `{applied: string[], rejected: [{id, reason}]}`. Причины: `not_found_line`, `forbidden` (чужую запись удалить нельзя без `inventory.manage`), `invalid_qty`.

**Клиент:**
- Очередь операций хранится в IndexedDB по `count_id`. Сначала операция ставится в очередь и сразу отражается в таблице (оптимистично), потом отправляется.
- Отправка: сразу после ввода, при событии `online` и по таймеру раз в 5 с, пока очередь не пуста. Отправка последовательная, по одной пачке за раз.
- `GET /inventory/counts/:id` каждые 10 с (TanStack Query `refetchInterval`). Ответ сливается с локальной очередью: неотправленные операции накладываются поверх серверного состояния.
- Последний ответ `GET` сохраняется в IndexedDB, поэтому таблица открывается без сети.
- Индикаторы: «● онлайн / ○ офлайн», «не отправлено: N».
- На 409 записи из очереди помечаются «не принято (инвентаризация отправлена)» и остаются видны этому участнику. Подсказка: «Попросите менеджера вернуть в черновик».
- Позицию вне шаблона (`POST lines`) и «не считали» добавить без сети нельзя: кнопки неактивны, есть подсказка. Офлайн работают только записи количества.
- «Отправить» неактивна, пока у этого устройства непустая очередь.

## 9. Экраны

### 9.1 Список инвентаризаций (`/<locale>/inventory`)
- Менеджер: выбор склада (если их несколько) и карточки инвентаризаций: «Черновик · 37/190 · вводят: Иван, Азиз», «Отправлена 31.10 · Иван». Кнопка «Начать инвентаризацию» (`inventory.manage`): шаблон и период.
- Офис (`inventory.templates`): фильтр «период, организация» и таблица складов (статус, прогресс, кто и когда отправил, «не начата»). Клик открывает инвентаризацию только для чтения.

### 9.2 Ввод (`/<locale>/inventory/[id]`)
```
┌ Инвентаризация · Склад Les Юнусабад · Октябрь 2026 ─────────────┐
│ 🔍 поиск   [Все | Не посчитано | Мои]     37/190 ▓▓░░  ● онлайн │
├──────────────────────────────┬──────┬───────────────────────────┤
│ ▾ МЯСНЫЕ ПРОДУКТЫ  12/31     │      │                           │
│   Говядина                   │ кг   │ 4,2                       │
│   Куриное филе               │ кг   │ 5,5  ②                    │
│   Крылья                     │ кг   │ [+ ввести          ]      │
│ ▸ ОВОЩИ, ЗЕЛЕНЬ  20/20 ✓     │      │                           │
│ ▸ МОЛОЧНЫЕ  0/13             │      │                           │
├──────────────────────────────┴──────┴───────────────────────────┤
│ [+ товар не из списка]         не отправлено: 0     [Отправить] │
└─────────────────────────────────────────────────────────────────┘
```
- Одна таблица на всех устройствах. На телефоне колонки: позиция (перенос строки), единица, факт. Шрифт и высота строк рассчитаны на палец (строка не ниже 44 px).
- Группы — папки iiko, порядок «папка → название». Группу можно свернуть, в заголовке прогресс `посчитано/всего`, у завершённой группы ✓.
- **Ввод:** тап по ячейке, число, Enter (или «Готово» на клавиатуре). Число **добавляется записью**, поле очищается, фокус переходит на следующую непосчитанную позицию в порядке таблицы. Можно ввести `2,5+3`: это две записи. Запятая и точка обе считаются десятичным разделителем. Поле с `inputmode="decimal"`.
- Если у позиции уже есть записи, ячейка показывает сумму и бейдж с количеством записей. Тап по бейджу открывает список «2,5 — Иван 14:02 ✕». Ниже поле для новой записи.
- Меню строки: «Не считали» / «Вернуть в подсчёт».
- Фильтры «Все / Не посчитано / Мои» и поиск по названию (клиентский).
- «+ товар не из списка» открывает поиск по номенклатуре; позиция появляется в своей папке с меткой «добавлено».
- **Отправить** (`inventory.manage`) показывает сводку: «Посчитано 178, не считали 0, не заполнено 12». Если есть незаполненные, предлагается «Отметить все незаполненные как "не считали"» или «Вернуться». После отправки — только чтение.
- `submitted`: таблица только для чтения, кнопка «Вернуть в черновик» (`inventory.manage`, в разрешённом сроке).

### 9.3 Шаблоны (`/<locale>/inventory/templates`, `inventory.templates`)
- Список по организации: название, активен, количество позиций.

## 10. Ошибки и пограничные случаи

| Случай | Поведение |
|---|---|
| Два менеджера одновременно нажали «Начать» | Уникальный индекс: второй получает существующую инвентаризацию |
| Пачка синхронизации пришла дважды | `ON CONFLICT DO NOTHING`, без дублей |
| Удаление записи, которой ещё нет на сервере (`add` и `delete` в одной очереди) | Операции идут по порядку в одной пачке: сначала создаётся, потом удаляется |
| Инвентаризацию отправили, у участника остались офлайн-записи | 409, записи помечены «не принято», менеджер может вернуть в черновик |
| Товар удалили в iiko после старта | Строка остаётся (снимок названия), ввод разрешён |
| Шаблон изменили после старта | На начатые инвентаризации не влияет |
| Пользователь потерял доступ к складу | 403 на всех запросах, локальная очередь остаётся, но не отправляется |
| `qty` < 0, не число, больше 1 000 000 | Клиент не даёт ввести, сервер отклоняет с `invalid_qty` |

## 11. Проверки

- `bun test` в `backend/` (`bun:test`, по образцу `iiko_sync/job.test.ts`), на локальной БД:
  - `entries/sync`: повторный `add` с тем же `id` не создаёт дубля; `delete` идемпотентен; `add` + `delete` в одной пачке;
  - запись в `submitted` → 409, ничего не применено;
  - чужой склад → 403 на `GET counts/:id`, `sync`, `submit`;
  - `submit`: `fact_qty` = сумма живых записей, у `skipped` пусто, отказ, если есть незаполненные строки;
  - `POST counts` дважды → одна инвентаризация;
  - ответы модуля не содержат полей учёта iiko.
- `cd admin && bun lint`.
- Ручной прогон в браузере на ширине 390 px (телефон) и 1280×800 (планшет/POS): старт, ввод с переходом фокуса, `2,5+3`, удаление записи, «не считали», товар вне шаблона, два окна под разными пользователями (записи видны друг другу за ≤ 10 с), DevTools → Offline (ввести 5 записей, включить сеть, на сервере ровно 5), отправка и возврат в черновик.

## 12. Не входит

- Учётные остатки iiko, факт из инвентаризаций iiko, отчёт расхождений, разбор офисом и статус «принято» — подпроект 2.
- Фасовки и пересчёт единиц.
- Дедлайны и блокировка ввода после окончания периода (обсуждалось как защита от подсматривания в iiko, решается в подпроекте 2).
- Ручная сортировка позиций в шаблоне, зоны хранения.
- Печать и выгрузка в Excel.
- Офлайн-добавление позиций вне шаблона.
