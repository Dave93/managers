# Промежуточные пересчёты, книжное количество и «Остатки склада» — Design Doc

Дата: 2026-10-08. Статус: дизайн одобрен в чате по разделам, пользователь попросил сразу приступить к реализации.

Продолжение `2026-10-02-inventory-counts-design.md` (ввод) и `2026-10-06-inventory-reconciliation-design.md` (сверка). Опирается на правило возврата `inventory.reopen_rule` (спека сверки, §13).

## 1. Цель

1. **Промежуточные пересчёты** (раз в 10/15/20 дней): филиал вслепую пересчитывает выбранные позиции (шаблон, например «10 kun») или все товары за прошедший день; офис сравнивает факт с **книжным количеством iiko** («сколько должно быть по документам») на конец этого дня — как в форме инвентаризации iiko: «Факт / Книжн. к-во / Разница к-во».
2. **Книжное количество для любого пересчёта** — и месячного, и промежуточного: та же таблица на странице пересчёта.
3. **«Остатки склада»** — книжные остатки iiko по складу на сейчас, с движением по товару.

Суммы не показываются нигде — только количество.

## 2. Решения

| # | Вопрос | Решение |
|---|---|---|
| 1 | Как появляется промежуточный | Менеджер начинает сам: «Начать» → «Промежуточный» → дата → шаблон или все товары филиала |
| 2 | Дата промежуточного | Только прошедший день (вчера и раньше), сегодня — нельзя. По умолчанию — вчера. Диапазон: с 1-го числа прошлого месяца по вчера |
| 3 | Момент книжного количества | Конец даты пересчёта: 23:59:59; если дата — последний день месяца (месячный или промежуточный в этот день) — 23:58, до документа инвентаризации iiko в 23:59 |
| 4 | Хранение | Снимок по пересчёту (`inventory_count_book`) с разбивкой; обновляется по кнопке офиса |
| 5 | Кто видит «Сравнение с учётом» | Офис (`inventory.reconcile`) — всегда; филиал — по своему складу, когда пересчёт для него зафиксирован (отправлен и вернуть его по правилу возврата он не может) |
| 6 | «Остатки склада» у филиала | Закрыты, пока у склада есть пересчёт, который филиал ещё может менять (черновик или отправленный, который можно вернуть). Офис (`inventory.templates`) видит всегда |
| 7 | Месячная сверка с iiko | Учитывает только месячные пересчёты; промежуточные в неё не складываются |
| 8 | «Факт с учётом блюд и заготовок» (iiko) | Не делаем: ПФ — отдельные товары, книжное по ним отдельное |
| 9 | Возврат промежуточного (08.10.2026) | Промежуточный фиксируется сразу после отправки: вернуть в черновик может только офис, при любом `inventory.reopen_rule`. Иначе он был бы открыт до месячной сверки и «Остатки склада» у филиала были бы закрыты почти весь месяц |

## 3. Что известно об iiko (проверено 08.10.2026, только чтение)

- `GET v2/reports/balance/stores?timestamp&store` — книжное количество (`amount`) по товару на момент; ~50 мс на склад.
- OLAP `TRANSACTIONS`, фильтр `Account.Id = склад`, группировка `Product.Id × TransactionType`, агрегаты `Amount.In`, `Amount.Out` — движение по товару и типу; ~4 с.
- Тождество проверено на складе 21027 за 01–20.09: **остаток на 1-е 00:00 + Σ(In − Out) = остаток на 20-е 23:59** — 275 из 275 товаров.
- Типы проводок на складе филиала: `INVOICE` (приход), `SESSION_WRITEOFF` (реализация по сменам), `TRANSFER` (перемещения, In и Out), `WRITEOFF` (списания); прочие (производство, возвраты, `STORE_COST_CORRECTION` с нулевым количеством) — в «прочее» со знаком; `INVENTORY_CORRECTION` в движение не входит (см. §4).
- `StartBalance`/`FinalBalance` в OLAP не использовать (не остаток на момент).

## 4. Данные

### `inventory_counts` — новые колонки
| Колонка | Тип | Примечание |
|---|---|---|
| `kind` | varchar(16) not null default 'monthly' | `monthly` / `interim` |
| `count_date` | date not null | Месячный — последний день месяца (= `period`); промежуточный — выбранный день. `period` = последний день месяца `count_date` |
| `book_fetched_at` | timestamptz null | Когда загружен снимок книжного количества |

Миграция заполняет `count_date = period` у существующих.

Уникальность (частичные индексы, `status <> 'cancelled'`):
- месячный: (`store_id`, `period`, `template_id`) и «все товары» (`store_id`, `period`) — как сейчас, но `WHERE kind = 'monthly'`;
- промежуточный: (`store_id`, `count_date`, `template_id`) и «все товары» (`store_id`, `count_date`) `WHERE kind = 'interim'`.

### `inventory_count_book` — снимок книжного количества
PK (`count_id`, `product_id`), `count_id` → `inventory_counts` ON DELETE CASCADE.

| Колонка | Тип | Примечание |
|---|---|---|
| `product_id` | uuid | |
| `book_qty` | numeric(14,4) | `balance/stores` на `count_date 23:58` |
| `start_qty` | numeric(14,4) | `balance/stores` на 1-е число месяца `count_date`, 00:00 |
| `in_invoice` | numeric(14,4) | Σ In `INVOICE` |
| `out_sales` | numeric(14,4) | Σ Out `SESSION_WRITEOFF` |
| `transfer_in`, `transfer_out` | numeric(14,4) | `TRANSFER` In / Out |
| `out_writeoff` | numeric(14,4) | Σ Out `WRITEOFF` |
| `other_net` | numeric(14,4) | Σ(In − Out) прочих типов |
| `consistent` | boolean | `start + in − out ≈ book` (|разница| ≤ 0,0005) |

Снимок пишется для товаров: строки пересчёта ∪ ненулевое книжное ∪ ненулевое движение.

Движение берётся из OLAP за даты [1-е число месяца, `count_date`] **без проводок `INVENTORY_CORRECTION`** (фильтр `ExcludeValues`): так месячный документ инвентаризации iiko в 23:59 последнего дня не попадает в книжное на 23:58, а остаток на 1-е число 00:00 уже включает документ прошлого месяца. Если в середине месяца в iiko всё же проведут инвентаризацию, тождество для таких товаров не сойдётся — строка помечается `consistent = false` и показывается с пометкой «разбивка не сходится».

## 5. Получение снимка

- После отправки пересчёта ставится BullMQ-задача `inventory_count_book` (`jobId = book-<countId>`), её выполняет `cron/inventory_reconcile_worker.ts` (второй `Worker` в том же процессе, concurrency 1, один токен iiko на задачу, `logout` в `finally`).
- Кнопка офиса «Обновить книжное» на странице пересчёта ставит ту же задачу.
- Расчёт — чистая функция `buildBook(start, end, movements, productIds)` в `inventory/book/pure.ts`; клиент iiko — расширение `IikoClient` методом `movements(storeId, from, toInclusive)`.

## 6. API

| Маршрут | Право / доступ | Что делает |
|---|---|---|
| `POST /inventory/counts` | как сейчас + `kind`, `count_date` | Промежуточный: `count_date` в диапазоне решения 2 |
| `GET /inventory/interim-dates` | `inventory.count` | Допустимые даты промежуточного: `{ min, max, default }` |
| `GET /inventory/counts/:id/book` | офис `inventory.reconcile` — всегда; филиал со своим складом — если пересчёт зафиксирован | `{ fetched_at, lines: [{ product_id, code, product_name, unit_name, group_name, fact_qty, book_qty, diff_qty, start_qty, in_invoice, out_sales, transfer_in, transfer_out, out_writeoff, other_net, consistent }] }`; 403 `book_hidden`, если ещё нельзя |
| `POST /inventory/counts/:id/book/refresh` | `inventory.reconcile` | Ставит задачу снимка |
| `GET /inventory/stock?store_id=` | офис `inventory.templates` — любой склад; филиал — свой, если нет незафиксированного пересчёта | `{ hidden: boolean, at, lines: [{ product_id, code, name, unit_name, group_name, qty }] }` — `balance/stores` на сейчас |
| `GET /inventory/stock/movements?store_id&product_id` | те же | Разбивка с 1-го числа текущего месяца по сейчас |

«Зафиксирован для филиала» = `status = 'submitted'` и `mayReopen(филиал) = false`. «Незафиксированный пересчёт склада» = любой пересчёт склада в `draft` или `submitted` с `mayReopen = true` для этого пользователя.

`code` — `nomenclature_element.num`.

## 7. Экраны

- **«Начать»**: «Месячный / Промежуточный»; у промежуточного — дата (вчера по умолчанию, `min…max`), затем шаблон / все товары филиала.
- **Карточка и шапка пересчёта**: у промежуточного — «Промежуточный · 07.10.2026».
- **Страница пересчёта**: вкладки «Ввод» и «Сравнение с учётом» (вторая — если API отдаёт данные). Таблица «№ / Код / Товар / Ед. / Факт / Книжн. к-во / Разница к-во», сортировка по |разнице|; строка раскрывается: «На 01.MM → +приход → −реализация → +перемещ. приход → −перемещ. расход → −списание → ±прочее → книжное». Пока снимка нет — «Книжное количество загружается из iiko…». Офис — кнопка «Обновить книжное».
- **«Остатки склада»** (`/<locale>/inventory/stock`, меню «Инвентаризация» и «Ещё» у менеджера): склад, поиск, группы, «Товар / Ед. / Остаток», отрицательные подсвечены, «Только отрицательные»; клик — движение с 1-го числа. Если скрыто — «Идёт пересчёт — остатки откроются, когда пересчёт будет закрыт».

## 8. Изменения сверки с iiko

`adminAggregate`, область сверки и `refreshIfStale` учитывают только `kind = 'monthly'`. Блок «Пересчёты в админке» на странице сверки — только месячные.

## 9. Проверки

- Юнит: `buildBook` (разбивка, тождество, товары только с движением), допустимые даты промежуточного (сегодня нельзя, границы по Ташкенту).
- HTTP: создание промежуточного (дата сегодня/завтра/слишком ранняя → 422; два в разные дни, один и тот же день — тот же пересчёт); месячная сверка не складывает промежуточные; `book` — офис 200, филиал 403 до фиксации и 200 после, чужой склад 403; `stock` — скрыто при черновике, видно после фиксации, офис всегда.
- Сквозная: склад 21027, промежуточный за вчера → снимок → книжное совпадает с `balance/stores`, тождество для всех строк.

## 10. Не входит

- Расписание промежуточных пересчётов и задания от офиса (решение 1 — позже).
- Суммы, цены.
- «Факт с учётом блюд и заготовок».
