# Заявки (tickets) — дизайн подсистемы

Дата: 2026-09-12
Репозиторий: `/home/davr/managers` (монорепо office)
Статус: спека утверждена заказчиком, план реализации пишется отдельно

## 1. Зачем

Менеджер филиала сейчас сообщает о поломках голосом и в переписке: позвонил, написал в чат,
попросил кого-то передать. Результат никто не фиксирует, историю потом не поднять, а подрядчик
узнаёт о проблеме тогда, когда до него дозвонились.

Подсистема даёт заявке одно место жизни: менеджер создаёт её с планшета за три тапа, внешний
исполнитель получает уведомление в Telegram и работает в мини-аппе, офис видит всё и утверждает
суммы к оплате.

Первые два типа — проблема с рекламным телевизором и проблема с камерами. Оба обслуживают внешние
подрядные фирмы. Типы, которые исполняют свои сотрудники, появятся позже, и модель это учитывает
с первого дня.

## 2. Границы

Входит: реестр типов заявок, создание с планшета, захват и исполнение внешним подрядчиком,
переписка внутри заявки, акт выполненных работ с суммой, подтверждение работ филиалом,
утверждение суммы офисом, уведомления в Telegram, админка справочников.

Не входит (осознанно отложено): дедлайны и SLA с эскалацией; уведомления менеджеру в Telegram;
исполнители-сотрудники (модель готова, интерфейс появится вместе с первым таким типом);
видео во вложениях; выгрузка в бухгалтерию; аналитика по подрядчикам.

## 3. Принятые решения

| Вопрос | Решение |
|---|---|
| Кто исполнитель | Внешние подрядные фирмы; позже — свои сотрудники |
| Как назначается | Автоматически по типу: тип закреплён за фирмой, заявка уходит всем её людям, кто первый взял — тот и исполнитель |
| Людей в фирме | Несколько, бригада |
| Кто закрывает | Исполнитель сдаёт работу, менеджер филиала подтверждает или возвращает с комментарием |
| Дедлайны | Нет |
| Фото | Обязательны с обеих сторон, до 5 на фазу, только изображения |
| Поля типа | Реестр типов + схема полей в jsonb, новый тип без миграции |
| Приоритет | Обычная / срочная |
| Уведомления менеджеру | Только планшет, Telegram не трогаем |
| Наблюдатель офиса | Видит все заявки всех типов и филиалов |
| Сумма работ | Указывает исполнитель при сдаче, утверждает офис |
| Транспорт уведомлений | BullMQ, отдельный процесс-воркер |

## 4. Модель данных

Схема — `backend/drizzle/schema.ts` (не под `src/`), миграция через `drizzle-kit generate`.
Все таблицы с префиксом `ticket_`.

### ticket_contractors
Подрядные фирмы. Отдельно от `external_partners` — там портал франчайзи с email и паролем,
другая сущность с другим назначением.

- `id` uuid pk
- `name` varchar(255) not null
- `phone` varchar(50)
- `note` text
- `is_active` boolean default true
- `created_at`, `updated_at` timestamptz

### ticket_types
Реестр типов. Добавление третьего типа — строка здесь, без миграции, без правки бота и мини-аппа.

- `id` uuid pk
- `code` varchar(50) unique not null — `ad_tv`, `cameras`
- `number_prefix` varchar(5) not null — `TV`, `CAM`; отдельно от `code`, потому что `ad_tv`
  в человекочитаемый номер не превращается
- `name_ru`, `name_uz` varchar(255) not null
- `icon` varchar(50) — имя иконки для плитки на планшете
- `executor_kind` enum `ticket_executor_kind` (`external` | `staff`) not null
- `contractor_id` uuid → ticket_contractors, nullable (обязателен при `executor_kind='external'`)
- `fields_schema` jsonb not null default `[]`
- `requires_cost` boolean default true
- `active` boolean default true
- `sort` integer default 0
- `created_at`, `updated_at`

Формат `fields_schema` — массив описаний полей:

```json
[
  { "key": "tv_place", "type": "select", "required": true,
    "label_ru": "Какой телевизор", "label_uz": "Qaysi televizor",
    "options": [ { "value": "hall", "label_ru": "Зал", "label_uz": "Zal" } ] },
  { "key": "symptom", "type": "select", "required": true, "label_ru": "Что происходит", "…": "…" },
  { "key": "note", "type": "text", "required": false, "label_ru": "Описание", "…": "…" }
]
```

Типы полей на старте: `select` и `text`. Схема валидируется при сохранении типа — кривая схема
роняет форму на планшете в разгар смены, поэтому проверка на входе, а не на отрисовке.

Стартовое наполнение (сид):

- **Реклама ТВ** (`ad_tv`): какой телевизор (зал / кухня / витрина / другой), симптом
  (не включается / чёрный экран / нет картинки с плеера / зависла картинка / нет звука / другое),
  описание.
- **Камеры** (`cameras`): что сломано (конкретная камера / видеорегистратор / нет записи /
  нет удалённого доступа), зона (касса / зал / кухня / склад / улица), описание.

### ticket_executors
Люди в боте.

- `id` uuid pk
- `kind` enum `ticket_executor_kind` not null
- `contractor_id` uuid → ticket_contractors, nullable (для `external`)
- `user_id` uuid → users, nullable (для будущих `staff`)
- `full_name` varchar(255) not null
- `phone` varchar(50)
- `tg_user_id` bigint unique, nullable — заполняется при привязке
- `lang` varchar(10) default `ru` — на каком языке человеку писать; проставляется из
  `initData.language_code` при первом открытии мини-аппа, дальше редактируется в админке.
  В паспорте язык не сохранялся нигде, и узбекский стажёр читал русские вопросы
- `invite_code` uuid default gen_random_uuid()
- `invite_used_at` timestamptz
- `is_active` boolean default true
- `created_at`, `updated_at`

Ровно одно из `contractor_id` / `user_id` заполнено — check-констрейнт по `kind`.

### tickets

- `id` uuid pk
- `seq` bigserial — человекочитаемый номер, отображается как `TV-000123`
  (префикс из `number_prefix` типа)
- `type_id` uuid → ticket_types not null
- `terminal_id` uuid not null, `organization_id` uuid not null
- `status` enum `ticket_status` (`new` | `in_progress` | `done` | `closed` | `cancelled`) default `new`
- `priority` enum `ticket_priority` (`normal` | `urgent`) default `normal`
- `details` jsonb not null default `{}` — значения по `fields_schema` типа
- `description` text
- `created_by` uuid → users not null
- `assigned_executor_id` uuid → ticket_executors, nullable
- `assigned_at`, `done_at`, `closed_at`, `cancelled_at` timestamptz
- `closed_by`, `cancelled_by` uuid → users
- `reopen_count` integer default 0
- `work_total_amount` numeric(14,2) — итог акта, пересчитывается при сдаче
- `payment_status` enum `ticket_payment_status` (`pending` | `approved` | `rejected`) default `pending`
- `payment_approved_by` uuid → users, `payment_approved_at` timestamptz, `payment_comment` text
- `manager_seen_at` timestamptz — когда филиал последний раз открывал карточку; всё, что
  случилось позже, считается непрочитанным и даёт точку на карточке в списке
- `created_at`, `updated_at`

Индексы: `terminal_id`, `status`, `type_id`, `created_at`, `assigned_executor_id`,
плюс частичный по `(payment_status)` где `status='closed'` — под вкладку «К оплате».

### ticket_attachments

- `id` uuid pk, `ticket_id` uuid → tickets not null
- `phase` enum `ticket_attachment_phase` (`problem` | `result`) not null
- `file_path` text not null, `mime` varchar(100), `size_bytes` integer
- `uploaded_by_kind` enum (`manager` | `executor`), `uploaded_by_user_id` uuid, `uploaded_by_executor_id` uuid
- `created_at`

Лимит пять штук на пару (заявка, фаза) проверяется в коде.

### ticket_comments
Переписка внутри заявки, видна обеим сторонам. Внутренних заметок нет.

- `id` uuid pk, `ticket_id` uuid not null
- `author_kind` enum (`manager` | `executor` | `office`)
- `author_user_id` uuid, `author_executor_id` uuid
- `body` text not null
- `created_at`

### ticket_work_items
Акт выполненных работ.

- `id` uuid pk, `ticket_id` uuid not null
- `position` integer not null
- `title` text not null
- `qty` numeric(10,2) default 1, `unit` varchar(20)
- `amount` numeric(14,2) not null
- `created_at`

Итог схлопывается в `tickets.work_total_amount` в момент сдачи. Хранение суммы рядом с позициями
избыточно намеренно: вкладка «К оплате» листает сотни заявок и не должна для каждой строки
собирать агрегат.

### ticket_events
Таймлайн заявки и источник уведомлений.

- `id` uuid pk, `ticket_id` uuid not null
- `type` enum (`created` | `assigned` | `comment` | `done_submitted` | `reopened` | `closed` | `cancelled` | `payment_approved` | `payment_rejected`)
- `actor_kind` enum (`manager` | `executor` | `office` | `system`), `actor_user_id`, `actor_executor_id`
- `payload` jsonb
- `created_at`

### ticket_notifications
Журнал доставки и замок идемпотентности.

- `id` uuid pk
- `event_id` uuid → ticket_events not null
- `channel` varchar(20) default `telegram`
- `recipient_executor_id` uuid, `recipient_chat_id` bigint not null
- `kind` enum (`send` | `edit`) default `send` — `edit` гасит кнопку у остальных после захвата
- `target_message_id` bigint — что редактируем (для `edit`)
- `status` enum (`pending` | `sending` | `sent` | `failed`) default `pending`
- `attempts` integer default 0, `last_error` text
- `tg_message_id` bigint, `sent_at` timestamptz
- `created_at`
- **unique (`event_id`, `recipient_chat_id`, `kind`)**

## 5. Состояния

```
new ──(исполнитель «Беру»)──> in_progress ──(«Сдать работу»)──> done ──(менеджер принял)──> closed
                                   ^                              │
                                   └──(менеджер вернул с комментарием, reopen_count++)
new | in_progress ──(менеджер или офис отменил)──> cancelled
```

Захват — гонка между членами бригады, поэтому не «прочитать и записать», а один запрос:

```sql
UPDATE tickets SET status='in_progress', assigned_executor_id=$1, assigned_at=now()
WHERE id=$2 AND status='new' RETURNING *
```

Ноль строк означает, что кто-то опередил; мини-апп показывает «Заявку уже взял Азиз» и
обновляет карточку, а не выдаёт ошибку.

`payment_status` живёт отдельной веткой и на статус заявки не влияет. Филиал закрыл — телевизор
работает, заявка закрыта; деньги идут своим ходом и никого не держат.

## 6. Права

Выдаются **только через админку `/system/roles`**: SQL мимо Redis не сбросит кэш прав,
а форма стирает все права роли и пишет заново (грабли из паспорта).

| Право | Кому | Что даёт |
|---|---|---|
| `tickets.create` | менеджер филиала | создание заявки |
| `tickets.list` | менеджер филиала | список своих филиалов (terminal-scoping из `ctx`) |
| `tickets.close` | менеджер филиала | принять работу или вернуть в работу |
| `tickets.cancel` | менеджер, офис | отмена `new` и `in_progress` |
| `tickets.list_all` | офис | все филиалы, все типы |
| `tickets.payment.approve` | финансы | утверждение и отклонение сумм |
| `tickets.types.manage` | админ | реестр типов и схемы полей |
| `tickets.contractors.manage` | админ | фирмы и их люди, выдача инвайтов |

Исполнитель офисной сессии не имеет вообще. Отдельный макрос контекста проверяет `initData`
тикет-бота и резолвит `ticket_executors` по `tg_user_id`. Видит `new` по типам своей фирмы и то,
что взял сам. Чужой филиал, чужой тип, чужая заявка — 404, а не 403: 403 подтверждает, что объект
существует.

## 7. API

Модуль `backend/src/modules/tickets/`, обязательная регистрация в `backend/src/controllers.ts` —
без неё роутов просто не будет.

**Офисная часть** (cookie-сессия, макрос `permission`):

```
GET    /tickets                      список, limit/offset/sort/filters/fields
POST   /tickets                      создание, multipart: поля + photos[]
GET    /tickets/:id                  карточка с событиями, комментариями, вложениями, актом
POST   /tickets/:id/comments
POST   /tickets/:id/close            принять работу
POST   /tickets/:id/reopen           вернуть, комментарий обязателен
POST   /tickets/:id/cancel
POST   /tickets/:id/payment/approve  принимает ids[] — массовое утверждение одним запросом
POST   /tickets/:id/payment/reject   комментарий обязателен
GET    /tickets/attachments/:id/file поток с диска, проверка доступа
CRUD   /ticket_types, /ticket_contractors, /ticket_executors
POST   /ticket_executors/:id/invite  выдать ссылку-приглашение
```

Создание — **один multipart-запрос** с полями и фотографиями сразу (`t.Files`), а не «создать,
потом догрузить». Раздельные запросы означали бы, что событие `created` уходит в рассылку раньше
файлов, и подрядчик открывает заявку без единого фото — при том что фото объявлены обязательными.
Файлы ложатся на диск, затем в одной транзакции пишутся заявка, вложения и событие.

Утверждение оплаты принимает массив `ids[]` даже для одной заявки: финансист раз в неделю
закрывает пачку галочками, и `N` запросов вместо одного превратят это в мигающий экран.

**Исполнительская часть** (макрос `tgExecutor`, проверка `initData`):

```
GET    /tickets/tg/me
GET    /tickets/tg/feed?tab=new|mine
GET    /tickets/tg/tickets/:id
POST   /tickets/tg/tickets/:id/claim
POST   /tickets/tg/tickets/:id/comments
POST   /tickets/tg/tickets/:id/attachments   phase=result
POST   /tickets/tg/tickets/:id/submit        work_items[] + проверка ≥1 фото результата
GET    /tickets/tg/attachments/:id/file
```

**Приём от бота**: `POST /tickets/bot/webhook` с проверкой заголовка
`X-Telegram-Bot-Api-Secret-Token`. Обрабатывается ровно один случай — `/start inv_<uuid>`,
всё остальное отвечает 200 и игнорируется. Это единственный публичный роут подсистемы.

Списочные эндпоинты следуют конвенции репозитория: `limit`, `offset`, `sort`, `filters`
(JSON-массив `{field, operator, value}` через `parseFilterFields`), `fields` через
`parseSelectFields`.

## 8. Бот и мини-апп исполнителя

Бот делает две вещи: привязку и уведомления. Форм в чате нет.

Привязка: админ заводит человека, жмёт «Пригласить в бот», получает `t.me/<bot>?start=inv_<uuid>`
и отправляет подрядчику. Тот нажимает START, вебхук записывает `tg_user_id` и `invite_used_at`,
бот отвечает подтверждением с названием фирмы. Ссылка одноразовая.

Уведомление о новой заявке — главное в первых двух строках:

```
🔴 Срочная · Реклама ТВ
Чорсу · телевизор в зале
Не включается
                    [ Открыть заявку ]
```

Кнопка `web_app` открывает мини-апп сразу на карточке (`?ticket=<id>`), без промежуточного списка.
После захвата у остальных членов бригады сообщение редактируется: кнопка исчезает, появляется
строка «Взял Азиз, 14:32» — для этого хранится `tg_message_id`.

Мини-апп — три экрана.

**Список.** Две вкладки: «Новые» (свободные по типам своей фирмы) и «Мои». Карточка: филиал и тип
в заголовке, симптом одной фразой, слева цветная полоса приоритета, справа время. Фильтров нет:
у подрядчика в работе единицы заявок, а не сотни.

**Карточка.** Сверху лента фото проблемы (горизонтальный скролл, тап открывает полноэкранно),
под ней поля заявки плоским списком, дальше переписка. Внизу нативная `MainButton` телеграма,
меняющаяся по состоянию: «Беру» → «Сдать работу» → статус-строка «Ждёт подтверждения филиала».

**Сдача работы.** Отдельный экран: фото результата (до 5), строки работ «что сделали» + «сумма»
с кнопкой «+ ещё работа», итог крупно внизу и пересчитывается на лету. Числовое поле открывает
цифровую клавиатуру, суммы форматируются по ходу ввода (`1 200 000`). Отправка заблокирована,
пока нет хотя бы одного фото и одной строки работ, и кнопка сразу подписана причиной — не молчит
до нажатия.

Тема берётся из `themeParams`, светлая и тёмная бесплатно. Языки: русский и узбекский на латинице.

Фронт — `tickets_miniapp/`, клон `passport_miniapp/`: Vite + TS без фреймворка, `base: "/tickets-app/"`.

## 9. Планшет менеджера

Раздел «Заявки» в `ManagerLayout`. Планшет держат горизонтально, палец толстый: минимальная цель
44 px, выпадающих списков нет там, где влезают плитки.

**Создание — два шага.** Первый: выбор типа крупными плитками с иконкой. Второй: поля этого типа,
отрисованные из `fields_schema` — `select` превращается в ряд кнопок-пилюль, текст в одно поле
«опишите словами», приоритет в переключатель на два положения, фото в большую зону
«Снять / Выбрать» с превью и крестиками. Филиал, автор и дата не спрашиваются, подставляются
из сессии. Три тапа и фото — заявка ушла.

**Список.** Карточки, сгруппированные по состоянию, сверху то, что требует действия: «Ждут вашего
подтверждения», затем «В работе», затем «Новые»; закрытые за вкладкой. На карточке номер, тип,
симптом, кто взял, время в текущем статусе, превью фото маленькими квадратами.

Непрочитанное. Telegram менеджеру мы не шлём, значит комментарий исполнителя не должен теряться
в списке. События новее `manager_seen_at` дают точку на карточке и счётчик у группы; открытие
карточки сдвигает отметку. Без этого переписка работает в одну сторону: подрядчик спросил
«какой именно телевизор, их там три» и ждёт ответа, которого никто не увидит.

**Подтверждение.** Фото проблемы и фото результата в две колонки, между ними список выполненных
работ. Кнопки «Принять работу» и «Вернуть в работу»; вторая требует комментарий, иначе исполнитель
не узнает, что не так. Сумма видна, но не редактируется и подписана «на утверждении офиса».

Интерфейсы строятся дизайн-скиллами (`design-taste-frontend`, `aesthetic`) поверх существующей
базы admin-а (shadcn/ui + Tailwind). Вторая дизайн-система не заводится.

Референсы, с которых снят паттерн (dribbble, разделы field service ticket app и maintenance
request mobile app): карточки с фото-превью и счётчиком остатка, статус-чипы цветом, лента
активности «кто → что → когда», отдельный блок суммы внизу наряда.

## 10. Офис: наблюдение и оплата

Раздел в `AdminLayout`, право `tickets.list_all`. Здесь обычная таблица на существующем
`DataTable` с фильтрами по статусу, типу, филиалу и датам: у офиса сотни строк, и карточки,
уместные на планшете, тут превратятся в бесконечную прокрутку. Колонка «висит N часов»
с подсветкой после суток — единственная замена дедлайнам, которых мы не делаем.

**Вкладка «К оплате»** — главный экран для финансов. В ней заявки со `status='closed'` и
`payment_status='pending'`: номер, филиал, тип, фирма, сумма, дата закрытия. Раскрытие строки
показывает акт построчно и фотографии результата — утверждать вслепую по одной цифре нельзя.
Действия: «Утвердить» и «Отклонить» с обязательным комментарием, плюс галочки и массовое
утверждение выделенного (`ids[]` одним запросом).

**Справочники** под `tickets.types.manage` и `tickets.contractors.manage`:

- Типы заявок с редактором `fields_schema` — форма, где поля добавляются кнопкой, у каждого
  подписи на двух языках и список вариантов. Голого JSON в textarea здесь быть не должно:
  сломанная схема роняет форму создания на планшете, а чинить её будет некому.
- Фирмы и их люди. У человека кнопка «Пригласить в бот»: показывает ссылку и кладёт в буфер,
  чтобы отправить подрядчику в мессенджер.

## 11. Уведомления

Postgres — правда, Redis — транспорт.

**Запись.** Любое изменение заявки пишет `ticket_events` в той же транзакции, что и сам `UPDATE`.
Событие не теряется: либо заявка не изменилась, либо событие есть.

**Раскладка.** Чистая функция `route(event, ticket) → recipients[]`, без сети: `created` — все
активные исполнители фирмы этого типа; `assigned` — подтверждение взявшему и `edit` остальным;
`comment` от менеджера — исполнителю; `reopened` и `closed` — исполнителю; `cancelled` — правка
разосланных сообщений у тех, кто ещё видит живую кнопку, и отдельное сообщение исполнителю, если
заявку уже взяли. Отменённая заявка с работающей кнопкой «Открыть заявку» у пяти подрядчиков —
это выезд на объект, где чинить нечего. На каждого получателя строка в `ticket_notifications`
с уникальностью `(event_id, recipient_chat_id, kind)`.

События `payment_approved` и `payment_rejected` пишутся в журнал, но получателей не имеют:
подрядчик узнаёт об оплате не из бота. Функция маршрутизации возвращает для них пустой список,
и это поведение закреплено тестом — иначе первый же рефакторинг превратит внутреннее финансовое
решение в сообщение наружу.

**Постановка.** Сразу после коммита бэкенд кладёт задачу в очередь `tickets-notify`,
`jobId = <id строки>`. BullMQ отбрасывает повтор с тем же `jobId`, пока задача жива в Redis;
после её удаления страхует уникальный индекс в базе.

```js
{ attempts: 5,
  backoff: { type: "exponential", delay: 5000 },
  removeOnComplete: { age: 3600, count: 1000 },
  removeOnFail: { age: 86400 } }
```

`removeOnComplete` и `removeOnFail` обязательны: их отсутствие в arryt раздуло Redis до 3.41 ГБ.

**Воркер — отдельный процесс.** `office_tickets_worker` в pm2, `interpreter: "bun"`, рядом с
`iiko_document_worker` (исходник под bun, не компилируемый бинарь). Логику импортирует из
`@backend/modules/tickets/*` по корневому алиасу — код общий.

Проверено на сервере 2026-09-12: из `cron/` резолвится и `@backend/lib/*`, и глубокий модуль
со всеми зависимостями (`@backend/modules/credit/jobs` подтянул drizzle и ioredis), и бесхитростный
`backend/drizzle/schema` — `cron/tsconfig.json` наследует `paths` через `extends`, а `baseUrl: "."`
в корневом конфиге закрывает второй случай. У `cron/node_modules` есть собственные `drizzle-orm`,
`elysia`, `ioredis`, `pg`, `postgres`.

Расхождение, которое надо убрать до запуска: `backend` держит bullmq ^5.61.0, `cron` — ^5.80.9,
и каждый берёт свою копию. Внутри мажора v5 формат ключей в Redis общий, так что работать будет,
но ставить задачи одной версией и разбирать другой — это ровно тот класс расхождений, который
проявляется через полгода на редком типе задачи. Поднять backend до ^5.80.9 и пересобрать бинарь. Concurrency 5, лимитер
`{ max: 25, duration: 1000 }` при потолке телеграма около 30 сообщений в секунду.

Задача начинается с захвата строки:

```sql
UPDATE ticket_notifications SET status='sending', attempts=attempts+1
WHERE id=$1 AND status='pending' RETURNING *
```

Ноль строк — работа сделана, выходим молча. Перед сборкой сообщения воркер перечитывает текущий
статус заявки: рассылка о новой заявке могла пролежать в очереди те секунды, за которые её успели
взять или отменить. Заявка уже не `new` — сообщение уходит без кнопки, строкой «взял такой-то»
или «отменена». Иначе бригада получает живую кнопку на чужую работу. Дальше отправка или
редактирование, затем `sent` и `tg_message_id`. Ошибка уходит наружу, ретраями занимается BullMQ; `last_error` зеркалится
в строку для админки. На `429` читается `retry_after` и задача уходит в delayed ровно на это
время, без слепой экспоненты.

**Подметалка.** Один сценарий очередь не закрывает: Redis лежал в момент постановки, строка есть,
задачи нет. На это — репитбл `upsertJobScheduler("tickets-outbox-sweep", { pattern: "*/5 * * * *" })`
в той же очереди: ищет `pending` старше двух минут и ставит заново. `upsertJobScheduler`
перезаписывает расписание по ключу и не плодит осиротевшие репитблы при смене паттерна.

Эксплуатационное правило: правка текстов уведомлений требует рестарта `office_tickets_worker`,
иначе бот шлёт старые формулировки при уже новом бэкенде.

## 12. Файлы

Хранение: `uploads/tickets/<ticket_id>/<uuid>.<ext>`, по образцу `credit_admin` (`Bun.write`,
каталог `0750`, setgid). Раздача — только авторизованным роутом потоком с диска. Статики nginx
нет: по прямой ссылке подрядчик увидел бы чужие филиалы.

Приём: `t.File({ maxSize: "10m" })`, тип строго `image/jpeg` и `image/png`, не более пяти на фазу.
Клиент сжимает до 1600 px по длинной стороне перед отправкой — пять исходников с планшета это
40 МБ на заявку и забитый диск за полгода.

Порядок операций при загрузке повторяет `credit_admin`: файл на диск, потом строка в базу,
при падении вставки файл удаляется — сирот на диске не остаётся.

## 13. Тесты

`bun test`, по образцу паспорта (`state.test.ts`, `tg-auth.test.ts` уже лежат в его модуле).
Покрывается чистая логика, где ошибка дорогая:

- переходы состояний: все запрещённые пары отвергаются;
- гонка за захват: два параллельных «Беру» дают ровно одного победителя, второй получает
  осмысленный ответ;
- маршрутизация уведомлений: правильные получатели для каждого типа события;
- идемпотентность: повторный прогон события не создаёт вторую строку;
- валидация `details` против `fields_schema` и валидация самой схемы при сохранении типа;
- подсчёт итога акта, включая дробные суммы.

Проектного тест-раннера нет, счётчик — папка модуля.

## 14. Деплой

Пять артефактов, порядок не случаен: миграции → backend (бинарь) → воркер → admin →
мини-апп с nginx.

- `office_api` — компилируемый бинарь, `pm2 restart` без пересборки ничего не меняет.
  Сборка строго по `backend/DEPLOY.md`. В бинарь попадает рабочее дерево, а не HEAD:
  сверять mtime изменённых файлов с mtime `app`.
- Проверять деплой тремя вещами: роут снаружи отдаёт 401, а не 404; счётчик рестартов pm2
  сдвинулся; `readlink -f /proc/PID/exe` без «(deleted)». Однажды бинарь подменили без рестарта
  pm2 — снаружи всё работало на старом коде.
- Окно 502 при рестарте бэкенда около 40 секунд, старт бинаря примерно 21 секунда.
  Деплоить не в час пик.
- Админка собирается только под node20: `PATH=/root/.nvm/versions/node/v20.19.0/bin:$PATH`.
  `NEXT_PUBLIC_*` вшиваются на сборке, класть в `admin/.env` до неё.
- Мини-апп: `bun --bun run build` — без флага системный node16 роняет Vite.
- nginx: `location ^~ /tickets-app/` строго перед `location /` и обязательно со слэшем на конце.
  Бэкапы конфигов в `/root/nginx-backups/`, не в `sites-enabled/` — glob include ломает `nginx -t`.
- Права выдавать только через админку `/system/roles`.
- `uploads/tickets` — те же владелец и setgid, что у `uploads/credit`.
- Переменные: `TICKETS_BOT_TOKEN`, `TICKETS_BOT_WEBHOOK_SECRET`, `TICKETS_UPLOADS_DIR`.
  Дописывать в `.env` аккуратно: однажды файл без завершающего перевода строки склеил
  секрет с предыдущей переменной.
- `git push` не работает (протухший PAT). Спека и план живут в репозитории на сервере.

Шаги, которые делает человек, а не скрипт:

1. Завести бота в BotFather, забрать токен в `TICKETS_BOT_TOKEN`.
2. Там же привязать мини-апп к боту и поставить ссылку на `/tickets-app/` — в паспорте этот шаг
   делал владелец, автоматизации нет.
3. Зарегистрировать вебхук с секретом:
   `setWebhook?url=https://api.office.lesailes.uz/api/tickets/bot/webhook&secret_token=<…>`.
   Префикс `/api` обязателен: роуты живут под ним, и без него телеграм будет стучаться в пустоту,
   молча и без единой ошибки в логах.
4. Выдать права ролям через админку `/system/roles`.
5. Завести фирмы и людей, разослать приглашения.

Откат: копия бинаря `backend/app.bak_tickets_<ts>`, копия `admin/.next.bak_tickets_<ts>`,
копия конфига nginx в `/root/nginx-backups/`.

## 15. Риски

**Подрядчик не открывает телеграм.** Дедлайнов нет, заявка может висеть сутки, и никто не узнает.
Смягчение: в списке офиса колонка «висит N часов» с подсветкой после суток. Дёшево и закрывает
дыру без машинерии SLA.

**Тяжёлые фото.** Сжатие на клиенте до 1600 px, лимит 10 МБ на файл и пять файлов на фазу.

**Схема полей в jsonb.** Свобода, которой легко порезаться. Валидация схемы при сохранении типа
обязательна, редактор типов — форма с полями, а не голый JSON в textarea.

**Утечка данных чужого филиала.** Единственная поверхность, где подрядчик разговаривает с
системой, — `/tickets/tg/*`. Каждый её обработчик обязан фильтровать по фирме исполнителя;
отсутствие фильтра в одном месте открывает всё. Тесты на изоляцию обязательны, отсутствие
доступа отдаётся как 404.
