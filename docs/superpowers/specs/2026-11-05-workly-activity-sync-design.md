# Сверка Workly по журналу действий

Дата: 2026-11-05. Ветка `feature/workly-activity-sync` от `origin/main` (e3722c74).

## Зачем

Сотрудники обновляются из Workly один раз в сутки, ночью в 03:30. Принятого утром человека нет в KPI до следующей ночи, уволенный сутки остаётся активным. Вебхуков у Workly нет (проверено по dev.workly.io), зато есть журнал действий `GET /v1/user-activities`. Его опрос каждые 15 минут сокращает задержку с суток до четверти часа без полного обхода по таймеру.

## Что проверено

Документация: 50 записей на страницу, фильтры `start_date`, `end_date`, `action_name`; в записи нет описания изменений, только `action_name`, `object_id`, `person_id`, `user`, `message`, `created_at`. Живая проба с ключами Les Ailes (2026-11-05, только чтение, имена и тексты не выводились):

- `end_date` не входит в выборку: окно `2026-11-05..2026-11-05` дало 0 записей, `2026-11-05..2026-11-06` дало 15.
- Записи идут от новых к старым, `id` растёт со временем (по `id` порядок `created_at` не нарушается).
- За четыре дня пришли записи двух разных пользователей: журнал не ограничен учёткой ключа.
- 283 записи за 4 дня, из них 227 ручные отметки прихода и ухода (`clockInManual`, `clockOutManual`). Нужных нам действий около десяти в день.
- `person_id` есть в каждой записи, но `object_id` для `assignedLocation` — номер локации. Поэтому по записи нельзя выбрать сотрудника, и событие служит сигналом, а не данными.
- В живом журнале есть действия, которых нет в доках: `recoverEmployee`, `updateAssignedRole`, `clockOutManual`.

## Решение

Задача `workly-activity` в очереди `workly-sync` (`cron/kpi_worker.ts`), расписание `7,22,37,52 * * * *` по Ташкенту. По каждому подключению:

1. Прочитать журнал за окно «вчера .. завтра» (по Ташкенту), оставить `id` и `action_name`.
2. Сравнить с курсором (наибольший виденный `id`, Redis). Новое нужное событие запускает `syncAuto` с источником `activity`, но не на первом опросе, а на следующем, если новее нужных событий не появилось.
3. Записать курсор после сверки.

Всё остальное берётся от ночной сверки без изменений: предохранители, журнал `workly_sync_runs`, правило «связи по имени ждут человека». Ночной прогон остаётся страховкой.

Что уточнено при проектировании (решения исполнителя):

- **Курсор в Redis, не в таблице.** Миграции нет. Потеря ключа безопасна: первый опрос без курсора запоминает максимум и сверку не запускает.
- **Ожидание тишины (по ревью).** Перевод сотрудника в Workly это два шага («уволить старую запись», «завести новую»), а сверка применяет деактивацию и создание сразу. Снимок между шагами деактивировал бы человека без возврата (после этого нужна ручная связь) или создал бы дубль. Маркер «id самого нового нужного события, виденного прошлым опросом» держит сверку, пока новые нужные события появляются. Цена: 15–30 минут вместо 15.
- **Пауза при плане HR.** Любой новый прогон вытесняет прежний `planned` (`applyRun`, 409 `run_superseded`). Ночью это никому не мешает, днём HR мог бы потерять только что проверенный план. Поэтому при последнем завершённом прогоне, запущенном вручную, в статусе `planned` и моложе 6 часов сверка откладывается, курсор не двигается. `blocked` не держит опрос (`applyRun` принимает только `planned`), брошенный `planned` автоматического прогона тоже.
- **Когда курсор двигается.** `init`, `idle` и итог сверки — вперёд. Сбой обхода (`failed`, `blocked/crawl_short`) повторяется на следующих опросах, три попытки подряд, потом курсор уходит вперёд. `settling`, `hold`, `busy` (идёт другой прогон) и `error` (журнал не прочитан) — остаётся.
- **Список действий** построен по тому, что читает `buildPlan`: имя, табельный номер, должность (из неё выводятся роль, разряд, смена, стажёр), локации, список уволенных. `transferEmpDep` включён на случай, если смена отдела меняет локацию; отдел сам план не читает.
- **Не логируем и не храним** `message` и `user.full_name`: клиент отдаёт только `id` и `action_name`. Запись без годных `id`/`action_name` пропускается (одно испорченное событие остаётся в окне на трое суток и иначе глушило бы опрос); непустой список без единой годной записи — ошибка формата.
- **Выключатель** `WORKLY_ACTIVITY_POLL=0`, проверяется в самой задаче (расписание живёт в Redis).

## Решения по ревью, оставленные как есть

- **Предохранители за прогон, а не за сутки.** Лимит деактиваций `max(10, 10% активных)` рассчитан на сутки; опрос применяет его на каждый 15-минутный прогон, и медленный поток (по 8 увольнений каждые 10 минут) его не остановит. Оставлено: увольнения идут из Workly, источника правды, а предохранитель ловит резкий сбой данных, который видно в одном снимке. Откат одного прогона есть (`rollback-run`). Если нужен суточный лимит, он считается по `counts` автоматических прогонов за 24 часа и меняет поведение и ночного режима.
- **Откат без паузы опроса.** Прогон со статусом `rolled_back` опрос не удерживает; это описано в `workly-deploy.md` (раздел 4): воркер при откате останавливают.

## Не цели

- Точечная сверка одного сотрудника по событию: полный обход 70–100 секунд, но запускается только при событии (около десятка в день на организацию).
- Посещаемость и выходные по событиям (`createdTimeoff`, `assignedSchedule`): ночную посещаемость по-прежнему не включать без защиты от обрезанного T12.
- Дедупликация пустых прогонов: событие, не меняющее наши данные (правка профиля без нашего поля), даёт строку журнала с пустым планом.

## Риски

- Прогон по событию занимает единственный слот воркера на 70–200 секунд; ручное «Проверить» в это время ждёт.
- Если `id` в Workly перестанет расти со временем, курсор по максимуму пропустит события. Ночной прогон подберёт их; тогда курсор заменить на набор виденных `id`.
- Тексты `card.trigger.activity` в `uz-Latn` и `uz-Cyrl` ждут проверки носителем.
