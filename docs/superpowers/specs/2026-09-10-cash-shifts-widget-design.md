# Кассовые смены на дашборде — Design Doc

Дата: 2026-09-10. Статус: одобрен по секциям, ждёт финального ревью спеки.

## 1. Цель

Руководителю нужно видеть, когда каждая касса сети открывалась и закрывалась, кто открыл смену и кто за ней работал. Поздние открытия, незакрытые и слишком длинные смены должны бросаться в глаза. Сейчас этих данных в managers нет: OLAP-синки не запрашивают ни смены, ни кассира.

Виджет исторический. Данные приходят раз в сутки, live-режим не нужен.

## 2. Зафиксированные решения

| # | Вопрос | Решение |
|---|--------|---------|
| 1 | История или live | Только история, синк раз в сутки |
| 2 | Оценка нарушений | Факты плюс общие для всей сети пороги. Пороги настраиваются в самом виджете (шестерёнка → popover) и хранятся в zustand `persist` |
| 3 | Кассиры | Кассиры по смене из OLAP SALES в отдельной таблице. `orders` не трогаем |
| 4 | Глубина истории | 90 дней при запуске |
| 5 | Где живёт синк | Отдельный cron-бинарь `cron/cash_shifts_sync.ts`, а не шаг в `iiko_sync` и не BullMQ-джоба в `office_api` |

## 3. Что известно об источнике (проверено на данных за 09.09.2026)

**Смены.** `GET /resto/api/v2/cashshifts/list?openDateFrom=YYYY-MM-DD&openDateTo=YYYY-MM-DD&status=ANY` на `les-ailes-co-co.iiko.it`. Документация: ru.iiko.help, раздел «Работа со сменами» (`kassovye-smeny-v2`).

- Реальные имена полей расходятся с документацией: `responsibleUserId`, `pointOfSaleId`, `conceptionId` вместо `responsibleUser`, `pointOfSale`, `conception`.
- Время приходит без зоны и по факту ташкентское (`2026-09-09T09:01:17.073`). Дробная часть бывает из двух и трёх цифр.
- За 09.09 было 78 смен на 62 кассах. У 15 касс по две смены: дневная примерно 09:00–19:00 и ночная примерно 19:00–03:00. Круглосуточные филиалы открывают смены и в 01:31, и в 03:07.
- Ночные смены закрываются следующим днём, одна закрылась в 10:19. Фильтр API работает только по дате открытия.
- `payOrders` совпал с суммой OLAP `DishDiscountSumInt` по `SessionID` во всех 77 сменах, у которых были заказы.
- `responsibleUserId` совпадает с `managerId` в 73 сменах из 78: смену открывает менеджер.
- `cashshifts/closedSessionDocument/{id}` создаёт документ принятия, если его нет. Синк этот эндпоинт не вызывает.

**Кассиры.** В OLAP SALES есть `Cashier`, `Cashier.Id`, `Cashier.Code` и `SessionID`. У одной смены бывает несколько кассиров (так было в 17 сменах из 77). Роли почти всегда MN1, часть логинов общие («Узбегим», «Diyor kassir Chilonzor»), поэтому имя кассира не всегда указывает на конкретного человека.

**Привязка к филиалу.** `pointOfSaleId` → `GET /resto/api/corporation/groups` (XML, `groupDto/pointOfSaleDtoes/pointOfSaleDto/id`) → `groupDto.id` = `credentials.key` при `model='terminals'`, `type='iiko_id'` = `orders.restaurant_group_id`. Сопоставились 77 смен из 78. У «Les Ailes Ekopark» нет `iiko_id` в credentials.

**Имена.** `GET /resto/api/employees` (XML, 444 записи) содержит все 35 id ответственных и менеджеров за 09.09.

**Лицензия.** Каждый токен resto API держит лицензионный слот. Синк обязан вызывать `/resto/api/logout?key=` в `finally`.

## 4. Данные

Обе таблицы обычные, не hypertable. За 90 дней это около 7 тыс. смен, дальше рост около 30 тыс. в год.

### `cash_shifts`

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | uuid PK | id смены в iiko |
| `terminal_id` | uuid null | терминал managers, null если связки нет |
| `iiko_group_id` | uuid null | `groupDto.id` |
| `iiko_group_name` | text null | для строк без терминала |
| `point_of_sale_id` | uuid not null | |
| `cash_reg_number` | integer not null | совпадает с OLAP `CashRegisterName.Number` |
| `cash_register_name` | text null | из OLAP `CashRegisterName`, иначе имя точки продаж из `groups` |
| `session_number` | integer not null | совпадает с OLAP `SessionNum` |
| `open_at` | timestamptz not null | наивное время iiko + `+05:00` |
| `close_at` | timestamptz null | null, пока смена открыта |
| `business_date` | date not null | дата `open_at` по Ташкенту |
| `status` | text not null | OPEN, CLOSED, ACCEPTED, UNACCEPTED, HASWARNINGS |
| `responsible_user_id`, `responsible_user_name` | uuid, text | имя снимком из `/employees` |
| `manager_id`, `manager_name` | uuid, text | то же |
| `pay_orders`, `sales_cash`, `sales_card`, `sales_credit`, `pay_in`, `pay_out`, `cash_diff` | numeric | как в iiko |
| `synced_at` | timestamptz not null | |

Индексы: `(business_date)`, `(terminal_id, business_date)`.

### `cash_shift_cashiers`

| Колонка | Тип |
|---|---|
| `shift_id` | uuid, FK → `cash_shifts.id` on delete cascade |
| `cashier_id` | uuid |
| `cashier_name` | text |
| `cashier_code` | text null |
| `orders_count` | integer |
| `revenue` | numeric |

PK `(shift_id, cashier_id)`.

### Миграция

`drizzle-kit generate` из `backend/`. Рабочее дерево грязное, в диф может попасть чужое изменение схемы. Перед применением SQL сверяется руками, в миграции должны остаться только эти две таблицы и их индексы.

## 5. Синк `cron/cash_shifts_sync.ts`

Скрипт компилируется в бинарь (`bun build --compile --outfile cash_shifts_sync cash_shifts_sync.ts` из `cron/`), как `iiko_sync`. Правка `.ts` без сборки ничего не меняет.

Аргументы: `--from YYYY-MM-DD --to YYYY-MM-DD`. Без аргументов окно равно «сегодня − 3 дня … сегодня» по Ташкенту.

Шаги:

1. Auth, в `finally` logout.
2. `corporation/groups` даёт карту `pointOfSaleId → (groupId, groupName, posName)`. Из credentials строится карта `groupId → terminal_id`. `employees` даёт `id → name`.
3. Для каждого 7-дневного куска окна вызывается `cashshifts/list?status=ANY`.
4. OLAP SALES за окно ±1 день по `OpenDate.Typed`, группировка `SessionID, Cashier.Id, Cashier, Cashier.Code, CashRegisterName`, агрегаты `UniqOrderId.OrdersCount, DishDiscountSumInt`, фильтры `OrderDeleted` и `DeletedWithWriteoff` = `NOT_DELETED`. Лишний день с каждой стороны нужен потому, что заказы ночной смены могут попасть в соседний учётный день. Строки со `SessionID`, которых нет среди синкнутых смен, отбрасываются.
5. Одна транзакция на кусок: upsert смен по `id`, затем для этих смен delete и insert кассиров.
6. Сверка: для каждой смены сумма `revenue` кассиров сравнивается с `pay_orders`. Расхождения больше 1 сума, смены без терминала и неизвестные `pointOfSaleId` пишутся в лог отдельными строками.
7. Итоговая строка лога: окно, число смен, кассиров, расхождений, несопоставленных касс. При ошибке запроса к iiko или БД скрипт выходит с кодом 1.

Запуск: root crontab, `30 4 * * *`, лог `/root/cash_shifts_sync.log`. К 04:30 ночные смены обычно закрыты, а поздно закрытые догоняются в следующие три ночи.

Бэкфилл: тот же бинарь с `--from` за 90 дней до даты запуска и `--to` на дату запуска. Запускать в окне работ, как остальные бэкфиллы.

## 6. API

Новый модуль `backend/src/modules/cash_shifts/controller.ts`, регистрируется в `backend/src/controllers.ts`. Устроен так же, как `/stoplist/by-day`: `permission: "charts.list"`, выборка ограничена резолвленными терминалами пользователя, параметр `terminals` сужает её дальше.

- `GET /api/cash_shifts?startDate&endDate&terminals` возвращает лёгкий список смен за период без кассиров: `id, terminal_id, terminal_name, iiko_group_name, cash_reg_number, cash_register_name, business_date, open_at, close_at, status, pay_orders`. Период ограничен 92 днями, больше даёт 400.
- `GET /api/cash_shifts/day?day&terminals` возвращает смены одного `business_date` со всеми полями и вложенным массивом кассиров.

Строки без `terminal_id` видит только пользователь без ограничения по терминалам.

Бэкенд работает скомпилированным бинарём `backend/app`. Деплой описан в `managers-backend-binary-deploy`: сборка, бэкап старого бинаря, `pm2 restart office_api`, около 40 секунд до готовности порта 6761.

## 7. Виджет `CashShiftsByDay.tsx`

Файл лежит в `admin/app/[locale]/dashboard/` и подключается в `page.client.tsx` после `StoplistByDay`. Фильтры общие для дашборда: `useDateRangeState` и `useTerminalsFilter`. Запросы идут через same-origin `fetch`, как в `StoplistByDay`.

**Полоса дней.** По одной ячейке на день периода: число смен и число смен с нарушениями, последнее красным. Клик по дню открывает таймлайн.

**Таймлайн дня.** Строка соответствует филиалу. Если у филиала несколько касс, у каждой своя подстрока с номером и именем кассы. Ось подстраивается под данные: от первого открытия до последнего закрытия с округлением до часа, в пределах от 00:00 дня D до 12:00 дня D+1. Бар обычной смены нейтральный, смены с нарушением янтарный, незакрытой смены штрихованный. Строки без терминала подписаны `iiko_group_name` с меткой «не привязан».

**Детали смены.** Клик по бару открывает popover: время открытия и закрытия, длительность, статус, кто открыл, список кассиров (имя, заказы, сумма), наличные, карта, `cash_diff`.

**Настройки.** Иконка шестерёнки в шапке открывает popover. Значения хранит zustand-стор `admin/store/states/cash_shift_settings.ts` с `persist`, ключ `cash-shift-widget-settings`. Кнопка «Сбросить» возвращает значения по умолчанию.

| Настройка | По умолчанию | Правило |
|---|---|---|
| Позднее открытие после | 10:30 | первая смена филиала за `business_date` открыта позже порога |
| Позднее закрытие после | 05:00 | смена закрыта позже порога следующего дня |
| Максимальная длительность | 16 ч | смена длиннее порога |
| Скрывать смены короче | 5 мин | такие смены не рисуются и не считаются; так уходят пустые смены вроде 17:41:26–17:41:48 |

Правило «не закрыта» порога не имеет: смена с `close_at = null` за прошедший `business_date` отмечается всегда.

«Первая смена филиала» считается по терминалу, а не по кассе. Ночная смена, открытая в 18:44 после дневной, поздним открытием не считается. Круглосуточный филиал, у которого первая смена открылась в 01:31, позднего открытия тоже не получает. Смену 01:31–17:59 длиной 16,5 ч порог «максимальная длительность» всё равно отметит.

Нарушения считает чистая функция `computeFlags(shifts, settings)` в отдельном файле рядом с виджетом.

**Вне задачи:** мобильная версия (`_mobile/MobileDashboard`), алерты, отдельная страница, кассир в `orders`.

## 8. Проверка

Тестового раннера в проекте нет, поэтому проверки такие:

- `computeFlags` покрывается `bun test` на фикстурах: круглосуточный филиал, дневная и ночная смены одной кассы, смена через полночь с закрытием в 10:19, незакрытая смена за вчера, пустая 22-секундная смена, две кассы одного филиала.
- Синк за 09.09.2026 должен дать 78 смен, 77 привязанных к терминалам и ноль расхождений `revenue` против `pay_orders`. Число смен за день сверяется с прямым вызовом `cashshifts/list`.
- API проверяется curl: без cookie 401 `{"message":"User not found"}`, с сессией 200. Пользователь с ограничением по терминалам не видит чужих смен.
- Виджет проверяется на проде за 09.09.2026: бары совпадают с таблицей смен, изменение порогов сразу меняет подсветку и сохраняется после перезагрузки страницы.

## 9. Риски

- Если iiko начнёт отдавать поля под именами из документации, синк получит `undefined`. Парсер проверяет наличие `id`, `openDate`, `pointOfSaleId` и при их отсутствии завершает прогон с ошибкой, не записывая null в таблицу.
- Новая касса без `iiko_id` у терминала попадёт в «не привязан». Лог синка перечисляет такие кассы каждый прогон.
- Токен iiko живёт ограниченное время. Синк за 3 дня укладывается в секунды, бэкфилл 90 дней кусками по 7 дней при 401 делает повторный auth, как `fetchWithRetry` в `iiko_sync`.
