# Workly: заметки к деплою

Здесь описано, как выложить интеграцию с Workly на прод и провести первый запуск. Документ ничего не выполняет сам: деплой делается только по прямой просьбе владельца. Каталог проекта на проде: `/home/davr/managers`. Спека: `docs/superpowers/specs/2026-10-29-workly-sync-design.md`, разделы 5.5, 5.8, 5.9 и 7. Стиль команд и особенности сервера те же, что в `docs/superpowers/kpi-deploy.md`.

## Состояние прода (31 октября 2026)

Ничего из этого документа на проде не выполнено. По данным на 29 октября последняя применённая миграция там `0040_kpi_tg_dual`, таблиц `workly_*` и колонок `employees.workly_*` нет. Таблицы `kpi_attendance` и `kpi_attendance_imports` 29 октября были пусты, но этот замер устарел: мастер файловой загрузки посещаемости работает на проде с 27 октября, и импорты могли появиться. После миграции у таких импортов `organization_id` пуст, и замена по организации их не трогает. Их проверяет шаг 0, а убирает шаг 10.

## Что добавляет релиз

- Сверку сотрудников с Workly: план по кнопке «Проверить», применение по кнопке «Применить», ночной автопрогон в пределах предохранителей (связи по имени ночью не ставятся) и откат прогона из командной строки.
- Посещаемость «Приход и уход» для KPI из API Workly: по кнопке за месяц; ночной режим есть, но выключен.
- Экран «Синхронизация Workly» в группе KPI админки (виден с правами `kpi_layout` и `kpi.manage`) и выбор организации в мастере файловой загрузки посещаемости.

Backend и админка выходят вместе, одним PR и одним деплоем. Файловая загрузка посещаемости теперь требует `organization_id`, а его передаёт только новый мастер админки. Новый backend со старой админкой отвечает на загрузку файла 422 `organization_required`; старый backend не знает маршрутов `/api/workly/*`, которые вызывает новая админка. Окно длится от перезапуска `office_api` (шаг 5) через пересоздание воркера (шаг 6) до конца сборки и перезапуска `office_admin` (шаг 7). В начале окна API ещё и отвечает 502, пока прогревается. Эти три шага идут подряд, без пауз: проверку `curl` из шага 5 можно отложить до конца шага 7.

## Особенности сервера

- `backend/.env` нельзя загружать в оболочку (`. ./.env`): одно из значений записано без кавычек и выполняется как команда. Переменные читать по одной через `grep`; скрипты на bun читают `.env` сами.
- `bun` лежит в `/root/.bun/bin/bun`. Штатный `node` 16-й; `drizzle-kit` и сборке админки нужен `PATH=/root/.nvm/versions/node/v20.20.2/bin:$PATH`.
- После `pm2 restart office_api` бинарник прогревается больше двух минут (27 октября 135 секунд), всё это время API отвечает 502. Откатывать в эти минуты не нужно.
- `pm2 restart` запускать без `--update-env`. Из неинтерактивной ssh-сессии этот флаг подменяет окружение процесса, процесс теряет Node 20 и падает (так однажды лёг `office_admin`).
- Redis общий для всех сервисов. BullMQ при старте воркера предупреждает про `maxmemory-policy`; это известно, политику в рамках деплоя не менять.

## 1. Переменные окружения

| Переменная | Что это |
|---|---|
| `WORKLY_BASE_URL` | адрес API Workly (раздел 2 спеки) |
| `WORKLY_LES_CLIENT_ID`, `WORKLY_LES_CLIENT_SECRET` | ключи приложения Workly компании 1237 (Les Ailes) |
| `WORKLY_LES_USERNAME`, `WORKLY_LES_PASSWORD` | служебная учётка Workly той же компании |
| `WORKLY_CHOPAR_CLIENT_ID`, `WORKLY_CHOPAR_CLIENT_SECRET` | ключи приложения компании 1238 (Chopar) |
| `WORKLY_CHOPAR_USERNAME`, `WORKLY_CHOPAR_PASSWORD` | служебная учётка Workly компании 1238 |
| `WORKLY_ATTENDANCE_NIGHTLY` | ночная посещаемость; на этом релизе `0` |

Подключение считается настроенным, только если заданы все пять его переменных: `WORKLY_BASE_URL` и четыре своих. Имена без компании (`WORKLY_CLIENT_ID`, `WORKLY_USERNAME`, `WORKLY_PASSWORD`) остались от локальных опытов, код их не читает. `WORKLY_QUEUE` не задавать: имя очереди по умолчанию `workly-sync`, у backend и воркера оно должно совпадать.

Все десять переменных вносятся в оба файла:

- `backend/.env`: маршруты экрана в `office_api` (состояние подключений, поиск сотрудника Workly для ручной связи);
- `cron/.env`: «Проверить», «Синхронизировать посещаемость» и ночной прогон, их выполняет воркер `office_kpi_worker`.

Воркеру в `cron/.env` нужны ещё `PROJECT_PREFIX`, `DATABASE_URL`, `REDIS_HOST` и `REDIS_PORT` с теми же значениями, что в `backend/.env`. Для воркера KPI они там уже есть. Проверить, какие имена заданы (значения при этом не печатаются):

```bash
cd /home/davr/managers
grep -oE '^WORKLY_[A-Z_]+=' backend/.env | sort
grep -oE '^(WORKLY_[A-Z_]+|PROJECT_PREFIX|DATABASE_URL|REDIS_HOST|REDIS_PORT)=' cron/.env | sort
```

Значения вписывать редактором, а не через `echo`: так секреты не попадут в историю оболочки. Перед дописыванием в конец файла выполнить `tail -c 1 backend/.env | od -c` (и то же для `cron/.env`): в выводе должно быть `\n`, иначе новая переменная приклеится к последней. Оба процесса читают переменные только при старте, поэтому правка `.env` требует перезапуска (шаги 5 и 6).

## 2. Порядок выкладки

### Шаг 0. Проверки до деплоя

1. Владелец прямо попросил деплой. Без этого прод не трогать.
2. Источник правды — checkout на проде, а не `origin/main`. Забрать прод-`main` в `refs/remotes/prod/main` и сравнить с `origin/main`. Если на проде есть коммиты, которых нет в ветке релиза, переносить релиз поверх `prod/main`, собрать и прогнать тесты локально.
3. На прод-`main` нет своей миграции `0041`. Если есть, файл, `meta/0041_snapshot.json` и запись в `meta/_journal.json` переименовываются до `migrate`.
4. Метка последней применённой миграции. `drizzle-kit migrate` сравнивает только `created_at` последней строки `drizzle.__drizzle_migrations`, и файл с меньшим `when` молча пропускается:

```bash
cd /home/davr/managers/backend
export DATABASE_URL=$(grep -E '^DATABASE_URL=' .env | cut -d= -f2- | tr -d "\"'")
psql "$DATABASE_URL" -c "select max(created_at) from drizzle.__drizzle_migrations;"
```

Ожидается `1793010443424` (поле `when` записи `0040_kpi_tg_dual` в `meta/_journal.json`). У `0041_workly_sync` `when` равен `1793364850851`, он больше. Число строк в таблице с числом записей журнала не совпадает (для idx 0–8 записей нет), это нормально.

5. Действующие импорты посещаемости. До миграции у импортов нет организации, поэтому любой найденный здесь импорт после релиза станет «прежним без организации»:

```bash
psql "$DATABASE_URL" -c "select period, count(*) as imports, sum(rows_matched) as rows from kpi_attendance_imports where status = 'committed' group by period order by period;"
```

Пустой результат значит, что шаг 10 не нужен. Если запрос вернул строки, остановиться и до деплоя договориться с владельцем о плане. Новая версия заменяет импорт только в пределах (месяц, организация), а импорт без организации не трогает. Без чистки в таком месяце останутся два действующих импорта, и дни «прогул» из старого файла останутся там, где Workly про день ничего не знает. План по умолчанию такой: после деплоя HR заново синхронизирует или перезаливает файлом каждый найденный месяц отдельно для каждой организации, затем оператор выполняет шаг 10.

### Шаг 1. Резервная копия

Миграция `0041` меняет `employees` и `kpi_attendance_imports`, синхронизация посещаемости переписывает дни месяца в `kpi_attendance`. Копию этих трёх таблиц снять до миграции:

```bash
mkdir -p /root/backups
TS=$(date +%Y%m%d-%H%M%S); echo $TS
cd /home/davr/managers/backend
export DATABASE_URL=$(grep -E '^DATABASE_URL=' .env | cut -d= -f2- | tr -d "\"'")
pg_dump "$DATABASE_URL" -Fc -t employees -t kpi_attendance_imports -t kpi_attendance -f /root/backups/workly_db_$TS.dump
ls -l /root/backups/workly_db_$TS.dump
cp -p app app.bak_$TS
cp -a ../admin/.next /root/backups/admin_next_workly_$TS
```

Значение `TS` записать: по нему в шагах 5 и 7 и при откате релиза находятся копии бинарника и сборки админки. Полный дамп базы тоже подходит, только дольше. Если `pg_dump` откажется работать из-за версии сервера, нужен `pg_dump` той же major-версии (`select version();`). Копия `.next` занимает около 180 МБ.

### Шаг 2. Доставка кода

Код попадает на прод пушем ветки релиза в прод-репозиторий и перемоткой `main` там. Пушить нужно в новую ветку: в выгруженную на сервере `main` git пуш не примет. На своей машине, где remote `prod` указывает по ssh на репозиторий `/home/davr/managers` на сервере:

```bash
git fetch prod main:refs/remotes/prod/main
git rev-parse prod/main origin/main
git push prod <sha релиза>:refs/heads/release-workly
```

`git rev-parse` печатает два одинаковых sha, иначе сначала перенести релиз поверх `prod/main` (шаг 0). На сервере:

```bash
cd /home/davr/managers
git status --short
git rev-parse HEAD
git merge --ff-only release-workly
```

`git status --short` должен быть пуст: при локальных правках остановиться и разобраться. Sha из `git rev-parse HEAD` записать, это прежний `main` для отката релиза. После перемотки на диске новые исходники, но работающие процессы их ещё не видят: `office_api` и админка работают из сборок, воркер подхватит код при пересоздании в шаге 6.

### Шаг 3. Миграция 0041

Прочитать SQL до запуска: `cat drizzle/migrations/0041_workly_sync.sql`. Миграция создаёт таблицы `workly_locations` и `workly_sync_runs`, добавляет в `employees` колонки `workly_company_id`, `workly_id`, `workly_tab_number` и частичный уникальный индекс `employees_workly_uq`, добавляет `kpi_attendance_imports.organization_id` и снимает `NOT NULL` с `kpi_attendance_imports.uploaded_by`. Она не идемпотентна: повторный запуск падает на `CREATE TABLE`. Прежний код с новыми колонками работает, поэтому миграция идёт до перезапуска.

```bash
cd /home/davr/managers/backend
export DATABASE_URL=$(grep -E '^DATABASE_URL=' .env | cut -d= -f2- | tr -d "\"'")
PATH=/root/.nvm/versions/node/v20.20.2/bin:$PATH ./node_modules/.bin/drizzle-kit migrate
psql "$DATABASE_URL" -c "select column_name from information_schema.columns where table_name = 'employees' and column_name like 'workly%';"
```

Последний запрос печатает три колонки.

### Шаг 4. Переменные окружения

Внести переменные по разделу 1 в `backend/.env` и `cron/.env`. `WORKLY_ATTENDANCE_NIGHTLY` в обоих файлах равен `0`.

### Шаг 5. Backend: сборка и перезапуск office_api

`office_api` работает из скомпилированного бинарника `backend/app`, правка исходников без сборки ничего не меняет. Зависимости backend в релизе не менялись.

```bash
cd /home/davr/managers/backend
/root/.bun/bin/bun build --compile --minify-whitespace --minify-syntax --target bun --outfile app.new src/index.ts
mv app.new app
pm2 restart office_api
```

Прежний бинарник лежит в `app.bak_<TS>` из шага 1. Ждать здесь прогрева не нужно: сразу идти к шагам 6 и 7, а после них проверить, что маршрут появился:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://api.office.lesailes.uz/api/workly/status
```

`401` значит, что работает новый бинарник (маршрут есть, сессии в запросе нет). `502` значит, что прогрев ещё идёт, `404` значит, что запущен старый бинарник.

### Шаг 6. Воркер office_kpi_worker

В `cron/pm2.config.js` у `office_kpi_worker` `kill_timeout` вырос с 10 до 130 секунд: при остановке воркер должен успеть закончить обход Workly. Обычный `pm2 restart` берёт сохранённые настройки процесса, а не новый файл, поэтому процесс пересоздаётся.

Этот шаг выполняется в новой ssh-сессии. `pm2 start` запоминает окружение оболочки, и `DATABASE_URL`, экспортированный в шагах 0, 1 и 3, попал бы в окружение воркера и в сохранённый список pm2. Воркер берёт переменные из `cron/.env` сам.

```bash
cd /home/davr/managers/cron
pm2 delete office_kpi_worker
PATH=/root/.bun/bin:$PATH pm2 start pm2.config.js --only office_kpi_worker
pm2 logs office_kpi_worker --lines 40 --nostream
pm2 jlist | grep -o '"kill_timeout":[0-9]*'
```

В логе должны быть строки `kpi worker started (queue kpi-notify, token: есть)` и `workly worker started (queue workly-sync)`. Очередь `workly-sync` и ночное расписание создаёт сам воркер. Среди значений `kill_timeout` должно быть `130000`. Только после этих двух проверок выполнить `pm2 save`. Пока воркер остановлен, уведомления KPI ждут в базе, после старта их подберёт подметалка.

### Шаг 7. Админка: сборка и перезапуск office_admin

cd /home/davr/managers/admin
/root/.bun/bin/bun install --frozen-lockfile
PATH=/root/.nvm/versions/node/v20.20.2/bin:/root/.bun/bin:$PATH bun run build

Обычный `pm2 restart office_admin`, без `--update-env`. Админка отвечает 200 через пару секунд. Копия прежней сборки лежит в `/root/backups/admin_next_workly_<TS>`. Проверить в браузере: в группе KPI есть пункт «Синхронизация Workly» (группа видна с правом `kpi_layout`, сам пункт с правом `kpi.manage`), а мастер файловой загрузки посещаемости просит выбрать организацию. Теперь можно сделать проверку `curl` из шага 5.

### Шаг 8. Первый запуск: сотрудники

Первый прогон каждой организации ручной. Сначала Les Ailes, затем Chopar, по одной.

1. Экран «Синхронизация Workly»: у обеих организаций подключение настроено. «Не настроено» значит, что в `backend/.env` не хватает переменной или `office_api` не перезапущен. Прогон, упавший с `not_configured`, указывает на `cron/.env` и воркер. Код `client_invalid` значит, что Workly отверг `client_id`/`client_secret` (они меняются после обновлений платформы).
2. Карта локаций. HR подтверждает предзаполненные пары. Склад, офис и подобные локации остаются без филиала: их сотрудники попадают в отчёт «не привязан к филиалу» и не создаются. Локация Chopar `SERGELI` по сверке соответствует филиалу `Chopar pizza Golden life`, это подтверждает HR. Ошибка `company_mismatch` при загрузке локаций значит, что в переменных этой организации лежат ключи другой компании Workly (у Les Ailes должна быть компания 1237, у Chopar 1238). Ничего не записано; исправить `WORKLY_LES_*` или `WORKLY_CHOPAR_*` в обоих `.env` и перезапустить `office_api` и воркер.
3. «Проверить». Обход идёт 70–100 секунд в воркере, экран опрашивает журнал каждые две секунды.
4. Сравнить план с ожиданием по сверке на 2026-10-29:

| Организация | связать | деактивировать | не найден |
|---|---|---|---|
| Les Ailes | около 137 | около 133 | 1 |
| Chopar | около 69 | около 46 | 0 |

   Остальное составляют создания (активные в Workly люди, которых у нас нет, с филиалом по карте) и отчёт «не привязан к филиалу»: у Les Ailes 69 человек на SKLAD, у Chopar 20 на OFIS. Неоднозначных тёзок среди активных 29 октября не было. Если числа сильно расходятся с таблицей (деактиваций вдвое больше, «не найден» десятки), план не применять: остановиться и разобраться. Ключи одной компании в переменных другой давали именно такое расхождение (когда Chopar сверяли с компанией Les Ailes, получилось 87 «не найден»), но теперь такой прогон до плана не доходит и падает с `company_mismatch`.
5. Сомнительные пункты можно исключить из плана перед применением, тёзок связать вручную. Исключение действует один раз, на это применение. После первого применения ночной прогон каждую ночь строит план заново и применяет его в пределах предохранителей, в том числе пункты, исключённые днём: создания, обновления, переносы, возвраты и деактивации. Связи по имени (`link`, `relink`) и переносы этих сотрудников ночь не применяет никогда, они ждут человека в следующем ручном «Проверить». Если исключённый пункт не должен примениться и ночью, причину исправляют в Workly.
6. Владелец смотрит план и даёт явное «применить». Только после этого нажимается «Применить».
7. Экран показывает итог: сколько пунктов применено и какие пропущены с причиной (`excluded` исключён, `stale` сотрудник изменился после плана, `conflict` запись Workly уже связана с другим). Записать id прогона: он нужен для отката (раздел 4).

Ответ «План устарел» (409 `run_superseded`) значит, что после этого плана появился более новый прогон той же организации. Нужно снова нажать «Проверить» и смотреть новый план.

### Шаг 9. Первый запуск: посещаемость

1. «Синхронизировать посещаемость за месяц» отдельно для каждой организации и каждого нужного месяца. Обход идёт в воркере, 70–100 секунд. Закрытый для KPI месяц даёт `period_closed`, месяц без прошедших дней даёт `period_not_started`.
2. Синхронизация пишет обычный импорт: строку в `kpi_attendance_imports` с `file_name = "Workly API"` и дни в `kpi_attendance`. Она заменяет прежний импорт той же организации за тот же месяц, в том числе файловый. Последующая загрузка файла так же заменяет данные API.
3. HR смотрит блок качества данных: долю прогулов по филиалам за месяц и сотрудников с прогулами больше чем в 90% дней. Блок считается по записанным дням, поэтому смотреть его после синхронизации. По октябрю 1–28 невыходов было около 20% у Les Ailes (C-5 57%) и 26% у Chopar (BOCHKA 100%). Верить ли этим данным, решает HR. Если нет, месяц можно перезалить файлом.
4. Балл посещаемости остаётся подсказкой в форме оценки: оценщик может поставить другой с заметкой.
5. `WORKLY_ATTENDANCE_NIGHTLY` остаётся `0` (раздел 3).

### Шаг 10. Прежние импорты без организации

Шаг нужен, только если проверка 5 в шаге 0 нашла импорты. Месяц чистится после того, как его заново записали обе организации: синхронизацией или файлом, отдельно для Les Ailes и для Chopar. Раньше нельзя. Запись организации переносит на свой новый импорт только дни своих сотрудников, которые есть в новых данных. Дни другой организации и дни, о которых Workly ничего не знает, остаются на прежнем импорте, и удаление до второй загрузки стёрло бы месяц второй организации.

Перед чисткой снять копию обеих таблиц:

```bash
TS=$(date +%Y%m%d-%H%M%S); echo $TS
cd /home/davr/managers/backend
export DATABASE_URL=$(grep -E '^DATABASE_URL=' .env | cut -d= -f2- | tr -d "\"'")
pg_dump "$DATABASE_URL" -Fc -t kpi_attendance_imports -t kpi_attendance -f /root/backups/workly_legacy_imports_$TS.dump
ls -l /root/backups/workly_legacy_imports_$TS.dump
```

Затем для каждого месяца (`<YYYY-MM-01>`, например `2026-10-01`) одной транзакцией пометить прежние импорты `replaced` и удалить их дни:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -c "begin; update kpi_attendance_imports set status = 'replaced' where organization_id is null and status = 'committed' and period = '<YYYY-MM-01>'; delete from kpi_attendance where import_id in (select id from kpi_attendance_imports where organization_id is null and status = 'replaced' and period = '<YYYY-MM-01>'); commit;"
```

`psql` печатает `UPDATE <n>` и `DELETE <n>`. После этого действующих импортов без организации за месяц нет: `select count(*) from kpi_attendance_imports where organization_id is null and status = 'committed' and period = '<YYYY-MM-01>';` возвращает 0.

## 3. Ночной прогон

Воркер `office_kpi_worker` запускает его в 03:30 по Ташкенту. Подключения идут по очереди, сначала Les Ailes, затем Chopar; сбой одного не останавливает другое.

Сверка сотрудников ночью идёт только у организации, у которой уже есть применённый прогон сотрудников, применивший хоть один пункт. Применение, где HR исключил всё, ночную сверку не включает. До первого такого ручного «Применить» ночной прогон эту организацию не трогает и строк в журнал не пишет, поэтому ручной план до применения ночью не устаревает.

Ночной прогон строит план и применяет его сам, только если план проходит все предохранители:

- деактиваций не больше `max(10, 10% активных сотрудников организации у нас)`;
- новых сотрудников не больше 50;
- активных в Workly не меньше 90% от числа в последнем применённом прогоне.

Ночью применяются создания, обновления должности и табельного номера, переносы, возвраты (`reactivate`) и деактивации, в том числе пункты, которые HR днём исключил из ручного применения: исключение действует один раз. Связи по имени (`link`, `relink`) и переносы этих сотрудников ночь не применяет никогда. Они остаются в журнале прогона как пропущенные с причиной `excluded` и ждут человека: ручное «Проверить» и «Применить». Предохранители считают план целиком, вместе с этими связями.

Если предохранитель сработал, план сохраняется без применения со статусом `blocked` и причиной (`too_many_deactivations`, `too_many_creations`, `crawl_short`). Такой план не применяется кнопкой: нужно нажать «Проверить», посмотреть свежий план и применить его вручную. Сбой обхода или применения даёт статус `failed` с кодом. Тревога означает строку журнала со статусом `failed` или `blocked` и заметный статус на экране «Синхронизация Workly»; отдельного канала нет. В лог воркера пишется строка вида `workly nightly LES employees <run_id> <код>`.

`WORKLY_ATTENDANCE_NIGHTLY` должен оставаться `0`. Защиты от обрезанного обхода отчёта T12 пока нет. Если Workly отдаст T12 не целиком, ночной прогон заменит импорт месяца неполными днями: часть сотрудников потеряет дни, прогон при этом закончится успешно, и тревоги не будет. Ручную синхронизацию HR запускает сам и видит её итог (`days`, `unknown`, `carried`) и блок качества, поэтому она остаётся единственным способом. Флаг можно включать только после того, как такая защита появится в коде.

### Коды на экране «Синхронизация Workly» и в логе воркера

- `company_mismatch`: учётка в переменных подключения принадлежит другой компании Workly (у Les Ailes должна быть 1237, у Chopar 1238). Ничего не записано: ни локаций, ни плана, ни импорта. Ответ 422 на экране указывает на `backend/.env`, упавший прогон в журнале на `cron/.env`. Вписать ключи нужной компании и перезапустить `office_api` или воркер.
- `empty_crawl`: Workly не отдал ни одного активного сотрудника (у посещаемости: пустой T12 или нечего записать). План не построен, прежний импорт не тронут. Проверить, работает ли Workly и видит ли учётка компанию, и повторить позже.
- `crawl_failed`: обход упал по другой причине (сеть, неожиданный ответ, ошибка базы). Повторить «Проверить» или синхронизацию; при повторении смотреть `pm2 logs office_kpi_worker --lines 100 --nostream`, там только коды.
- `crawl_short`: ночной прогон получил меньше 90% активных от последнего применённого и ничего не применил. Нажать «Проверить», сравнить число активных с Workly и применить вручную, только если люди в Workly действительно ушли.
- `apply_failed`: ночное применение упало, всё откатилось, прогон `failed`. Нажать «Проверить» и «Применить» вручную; если ручное применение тоже падает, передать id прогона разработчику.
- `not_configured`: у подключения не хватает переменных. На экране это `backend/.env` и `office_api`, у прогона в журнале `cron/.env` и воркер. Дописать переменные и перезапустить процесс.
- `client_invalid`: Workly отверг `client_id`/`client_secret` (код 7003, они меняются после обновлений платформы). Получить новые ключи, внести их в оба `.env`, перезапустить `office_api` и воркер.
- `force_update`: Workly ответил 426 и требует обновить приложение. Повтор не поможет: узнать у Workly, что изменилось, и передать разработчику.
- `auth_failed`: Workly не принял логин или пароль служебной учётки (код 7002) или дважды подряд отверг только что выданный ключ (7008). Проверить `WORKLY_<КЛЮЧ>_USERNAME` и `WORKLY_<КЛЮЧ>_PASSWORD`, войти этой учёткой в Workly вручную.
- `http_error`: Workly или Redis ответили не так, как ожидалось: сбой сети, ожидание дольше 30 секунд, HTTP 5xx, ответ не в том формате. Повторить позже; если повторяется, смотреть лог воркера или `office_api`.
- `stale`: строка прогона больше 15 минут оставалась `running` (воркер упал или был убит посреди обхода), её закрыл следующий запуск. Повторить «Проверить» или синхронизацию.
- `enqueue_failed`: строка прогона создана, но задача не встала в очередь (Redis недоступен). На экране это ответ 503 `queue_unavailable`. Проверить Redis и повторить.
- `queue_unavailable`: ответ маршрута на `enqueue_failed`, см. выше.
- `run_in_progress`: прогон той же организации и вида уже идёт (409). Дождаться его конца; зависшую строку через 15 минут закроет `stale`.
- `run_superseded`: после этого плана появился более новый прогон. Нажать «Проверить» и смотреть новый план.
- `period_closed`: месяц закрыт для KPI, посещаемость за него не синхронизируется. Делать ничего не нужно.
- `period_not_started`: в выбранном месяце ещё нет прошедших дней (окно идёт по вчерашний день по Ташкенту). Делать ничего не нужно.

## 4. Откат прогона сотрудников

Откат возвращает изменения одного применённого прогона сверки сотрудников.

Откат, который должен сохраниться, делается при остановленном воркере. Иначе ближайший ночной прогон в 03:30 соберёт план по тем же данным Workly и применит его снова, то есть отменит откат (если у организации есть другой применённый прогон). Пока воркер остановлен, не работают уведомления KPI в Telegram, «Проверить», синхронизация посещаемости (задачи ждут в очереди) и ночной прогон. Ночная задача, пропущенная за это время, может выполниться сразу после запуска воркера, поэтому запускать его только после того, как причина исправлена в Workly.

1. Остановить воркер и снять копию `employees`. `pm2 stop` может ждать до 130 секунд, если воркер в этот момент обходит Workly (`kill_timeout`):

```bash
pm2 stop office_kpi_worker
mkdir -p /root/backups
TS=$(date +%Y%m%d-%H%M%S); echo $TS
cd /home/davr/managers/backend
export DATABASE_URL=$(grep -E '^DATABASE_URL=' .env | cut -d= -f2- | tr -d "\"'")
pg_dump "$DATABASE_URL" -Fc -t employees -f /root/backups/workly_rollback_employees_$TS.dump
ls -l /root/backups/workly_rollback_employees_$TS.dump
```

2. Откатить прогон:

```bash
cd /home/davr/managers/backend
/root/.bun/bin/bun run src/modules/workly/rollback-run.ts <run_id>
```

Скрипт печатает одну строку `restored=<n> deleted=<n> deactivated=<n> skipped=<n>` и по строке `skipped <ключ> changed_since` на каждый пропущенный пункт:

- `restored`: пункты связи, перепривязки, обновления, переноса, деактивации и возврата, которым вернули прежние значения полей;
- `deleted`: созданные прогоном сотрудники, на которых ничто не ссылается; они удалены;
- `deactivated`: созданные прогоном сотрудники, на которых ссылается хоть одна строка (медосмотры, посещаемость, оценки KPI, паспорт стажёра); они не удалены, а выключены (`active = false`);
- `skipped`: пункты, которые откат не тронул.

`changed_since` значит, что поля сотрудника изменились после применения: их поменял более поздний прогон, HR или ручная связь, либо сотрудник теперь в филиале другой организации. Откат таких сотрудников не трогает, чтобы не затереть более поздние правки. Пропущенные пункты при необходимости исправляются вручную.

Откат касается только пунктов, которые прогон действительно применил: исключённые, устаревшие и конфликтные он не трогает. Всё выполняется одной транзакцией: при любой неожиданной ошибке не меняется ничего, прогон остаётся `applied`, а скрипт печатает `error <код>` и завершается с кодом 1. Если откат остановила ошибка конкретного пункта, в stderr дополнительно выводится `failed_item <ключ пункта>`: по ключу видно, какой сотрудник мешает. После успешного отката прогон получает статус `rolled_back`, повторный откат отвечает `error run_not_applied`.

Откат работает только для прогонов сотрудников. Импорт посещаемости им не откатывается: месяц синхронизируется заново или перезаливается файлом.

3. Когда причина в Workly исправлена, запустить воркер из новой ssh-сессии. При откате релиза этот шаг не выполняется (см. «Откат релиза»). Процесс остановлен, но не удалён, поэтому достаточно имени:

```bash
pm2 start office_kpi_worker
```

Если процесс был удалён (`pm2 delete`), запускать его из конфига, как в шаге 6: `cd /home/davr/managers/cron && PATH=/root/.bun/bin:$PATH pm2 start pm2.config.js --only office_kpi_worker`, затем `pm2 save`.

Найти id прогона можно на экране «Синхронизация Workly» или запросом:

```bash
cd /home/davr/managers/backend
export DATABASE_URL=$(grep -E '^DATABASE_URL=' .env | cut -d= -f2- | tr -d "\"'")
psql "$DATABASE_URL" -c "select r.id, o.name, r.kind, r.trigger, r.status, r.created_at, r.applied_at from workly_sync_runs r join organization o on o.id = r.organization_id order by r.created_at desc limit 5;"
```

Что происходит после отката:

- Если у организации остался другой применённый прогон сотрудников, ночной прогон в 03:30 соберёт план по тем же данным Workly и применит его снова в пределах предохранителей. Поэтому воркер стоит, пока причина не исправлена (см. выше).
- Созданный сотрудник, которого откат выключил, сохраняет связь с Workly, и следующий план вернёт его пунктом `reactivate`. Возвраты предохранители не ограничивают.
- Если откатан единственный применённый прогон, применивший хоть один пункт, ночная сверка этой организации останавливается до следующего ручного «Применить».
- Более старый план, построенный до откатанного прогона, не применяется: он получает 409 `run_superseded`. После отката нужно нажать «Проверить» и работать с новым планом.

## 5. Известные ограничения

- Для посещаемости нет защиты от обрезанного обхода T12 (раздел 3), поэтому ночная посещаемость выключена.
- `kill_timeout` 130 секунд рассчитан на один обход. Ночная задача длиннее: сверка сотрудников обходит обе организации подряд (у Les Ailes обход около 75 секунд), а с включённой посещаемостью обходов до шести. Перезапуск или остановка воркера около 03:30 может не уложиться в 130 секунд, и pm2 убьёт процесс посреди обхода. BullMQ считает такую задачу зависшей и один раз выполняет её заново при следующем старте воркера; организация, чья строка ещё `running`, при этом получит `run_in_progress`.
- После обрыва воркера (SIGKILL) строка прогона остаётся `running` до 15 минут. Пока она не закрыта, новый прогон той же организации и вида получает 409 `run_in_progress`, ночной в том числе. Следующий запуск после 15 минут закрывает её как `failed` с кодом `stale`.
- План, после которого появился более новый прогон (`planned`, `applied`, `blocked` или `rolled_back`), не применяется: 409 `run_superseded`, нужно снова нажать «Проверить». После первого применения ночной прогон создаёт новый прогон каждую ночь, поэтому план, построенный вечером, к утру устаревает.
- Первая синхронизация посещаемости через API заменяет файловый импорт этой организации за месяц, и наоборот: источник данных за (месяц, организация) всегда один, побеждает последняя запись.
- Имена сверяются по нормализованному тексту (верхний регистр, без апострофов, набор слов). Тёзки уходят в список «требует решения» и связываются вручную. Постоянной пометки «не синхронизировать» нет.
- Откат помечает прогон `rolled_back`, даже если часть пунктов пропущена. Повторить откат для этих пунктов нельзя, их исправляют вручную.
- Значение из Workly длиннее колонки у нас (табельный номер длиннее 32 символов, должность длиннее 150) роняет применение пункта ошибкой базы. Ночной прогон тогда каждую ночь заканчивается `apply_failed`, ручное «Применить» тоже падает, пока значение не исправят в Workly.
- Сотрудник, переведённый в другую организацию посреди месяца, теряет дни прежней организации при её пересборке месяца: перенос дней берёт только сотрудников с филиалом этой организации, а новая организация пишет только свои дни.
